Problem Statement

An AI agent returns inconsistent results in production compared to staging. Walk through your debugging approach end-to-end.

我的思路与解法

题目（verbatim）

"An AI agent returns inconsistent results in production compared to staging. Walk through your debugging approach end-to-end."

出处: fde.academy 列出的高频技术 round 题. OpenAI / Anthropic / Google FDE 都问过.

Round: Technical Integration / Debug (45-60 min)

这道题在考什么

考你 production deployment 的诊断套路. AI deployment 大多数失败都是这个 shape:

  1. 能不能 reproduce — production-only bug 是最难的, 没 reproduce 就没 fix
  2. 诊断顺序对不对 — cheap 先于 expensive, hash diff 先于 GPU profile
  3. 7 类 diff sources 知道几个 — data / config / model / dep / scale / state / time
  4. Don't blame the model first — 9/10 root cause 不是 model 本身
  5. 有没有 instrumentation 让你能 trace — 没 trace_id 一切都靠猜

考的不是「OpenAI bug 长啥样」, 是「你 production 用 LLM 部署过, 解决过几个 silent failure」.

Part 1 · 教学讲解 — 先把概念讲透

1. 四个术语先解释

Staging vs Production: 两个环境 (environment). Staging 是 prod 的镜像 — 同样代码、同样架构、同样 deploy pipeline, 但流量是合成的、数据是 sanitized 的. 理想情况它们一模一样, 实际永远存在 drift. 这道题考的就是: 当 drift 显现成 bug 时, 怎么定位.

Inconsistency (不一致): 一个 ambiguous 的词, 必须先 clarify. 有 3 种含义:

  • Wrong: 输出错误 (staging "对" → prod "错")
  • Different: 同一个 input, prod 多次跑结果不一样 (non-determinism)
  • Slower: 输出正确, 但 latency / timeout 引发 truncation

90% 的初学者直接开始 debug "wrong", 但很多 production bug 其实是 "slower → truncated → wrong".

Reproducibility (可复现性): 给定一个 production failure case, 能不能在 staging 或本地原样再跑出同样错. 能 reproduce 等于成功了 80%.

Trace_id propagation (链路追踪 ID 传递): 每个请求一个 unique trace_id, 在所有 service / log / DB 操作里都带上. 没有这个, 你就只能靠时间戳 + IP 猜哪条 log 对应哪个请求, 在 high-QPS prod 里就是 garbage.

2. 这个问题的核心是什么

设想一个没有 trace / 没 hash 校验 / 没 shadow eval 的 AI deployment 灾难:

14:32  客户反馈: "你们的 agent 今天回复全是乱的"
14:35  你: "我刚 staging 跑了一遍, 都好啊?"
14:50  你看 prod log: 一堆 "I can't help with that" — 但同样 prompt 在 staging 是正常回复
15:00  你: "应该是 model 版本? 配置? GPU? 还是用户输入变了?"
15:30  你 hypothesize 之一然后试着 fix, 改坏了另一个 dimension
16:00  事态扩散, customer escalate 到 VP
17:00  你 emergency rollback. Postmortem: 4h MTTR, root cause unclear.

问题:

  • 没 trace 没法找到具体 failing request 的全部 context
  • 没 deploy artifact hash 不知道两边到底跑的是不是同一个 model + tokenizer + system prompt
  • 没 distribution monitor 不知道 prod 输入是不是真的和 staging 不一样
  • 没 canary 一次性 deploy 100%, 出问题影响所有用户
  • 没 shadow eval 不知道 silent drift 已经累积多久

Production-grade debug 解法:

1. trace_id 端到端 (每个 service / log / DB 都带)
2. Deploy artifact 全 hash 校验 (model + tokenizer + prompt + dep + image)
3. Per-request observability (region, GPU, batch_size, seed, temperature)
4. Shadow eval 每天对比 prod vs staging 同 input 输出
5. Canary deploy + auto-rollback on error budget breach
6. Replay tool: 任意 prod trace_id 一键在 staging 复现

3. 7 类 diff source 决策树

Staging 和 Production 可能在以下 7 个维度 drift, 诊断顺序按 cheap → expensive:

请求出现 inconsistency
         ↓
   ┌─────┴─────┐
   是否能 reproduce?
   ├─ 能 ─→ 找 1 个 minimal failing input
   └─ 不能 ─→ 先加 trace + per-request log, 等 24h 收样本
         ↓
   ┌────────────────────────────────────────┐
   │  D1 Data        — 输入数据本身变了?       │
   │  D2 Config      — 模型 / 提示词 / 参数差? │
   │  D3 Model       — checkpoint hash 差?    │
   │  D4 Dependency  — vLLM / torch 版本差?   │
   │  D5 Scale       — prod 100x QPS, 触发 batch / KV cache? │
   │  D6 State       — cache warm / cold? Multi-replica state divergent? │
   │  D7 Time        — DST / timezone / token expire / data freshness? │
   └────────────────────────────────────────┘
         ↓
   按 cheap → expensive 依次排除:
   D2 (1h diff) → D3 (1h hash) → D4 (2h dep list) →
   D1 (4h distribution) → D7 (4h time audit) →
   D6 (1d state introspect) → D5 (3d load test)

关键: 不要跳到最后一类去查. 30% 的人直接怀疑 GPU 非确定性, 但 90% 的真实 root cause 在 D2/D3 (config / model hash).

  • D2 (config drift) 35%
  • D3 (model version) 20%
  • D7 (time) 15%
  • D1 (data) 12%
  • D6 (state) 10%
  • D4 (dependency) 5%
  • D5 (scale) 3%

先查 D2/D3 不是迷信, 是基于真实分布的策略.

5. 具体业务场景

场景 A: 你的 TikTok Voice Agent 7 markets (你工作背景)

症状: 周一早上, 你的 BD 同事在群里说 "印尼客户反馈 agent 突然听不懂 Bahasa, 回复全是英文了". 但你 staging 测试 Bahasa Indonesia 完全正常.

真实 root cause (D2 + D7 复合):

  • 周末 release: system prompt 加了一句 "Respond only in English unless explicitly asked otherwise"
  • 这句 deploy 到 prod 但没在 staging eval suite 里跑过
  • + 印尼周一是 public holiday, 流量比平时高 3 倍, 触发了更多 batch 路径
  • 双重作用下 30% 印尼用户看到英文回复

怎么发现: prod log 里 system_prompt 没有版本号, 你靠对比 staging git 和 prod deploy 配置 diff 才看到差异.

场景 B: ConvFinQA RL Alignment (你的研究项目)

症状: 你训练了一个 RL-aligned model, eval 在 staging 上准确率 78%, deploy 到 prod 同样 eval set 跑出来 71%.

真实 root cause (D3):

  • 你 deploy 用的是 model_v2.bin
  • 你 eval 用的是 model_v2_quantized.bin (FP16 → INT8 量化版)
  • 量化引入 ~7% 准确率损失, 但你没注意 .bin 文件名差异

教训: 部署必须 hash 校验, 不能信文件名.

场景 C: 跨区域 deploy 不一致

症状: Singapore region 准确率 OK, India region 同一个 query 准确率掉 15%.

真实 root cause (D4 + D6):

  • Singapore vLLM 是 v0.5.0, India 是 v0.4.8 (运维不同步)
  • v0.5.0 默认 enable_prefix_caching=True, v0.4.8 默认 False
  • 长上下文 query 在 India 因为没 prefix cache, 每次重新跑 attention, KV cache fragment 更严重 → 偶发 quality drop

场景 D: BNPL Chatbot tool calling 错乱

症状: 用户问 "我的下个还款是多少", staging 永远调 get_next_payment(user_id) 工具, prod 偶尔会调 get_payment_history(user_id) 然后总结错.

真实 root cause (D1 + D5):

  • Staging 测试 prompt 都比较短 (< 100 tokens)
  • Prod 用户实际会带很长的对话历史 (> 2000 tokens) 进入 router
  • 长上下文下 tool selection 的 next-token distribution 被稀释, 偶发选错 tool
  • 在 staging 永远复现不出来, 只在 prod long-context tail 出现

场景 E: Indonesia refund tier confirmation broken

症状: 你的 Indonesia refund tier 系统 (按金额触发 confirmation), 周二开始 staging 一切正常, prod 大额 refund 不弹 confirmation.

真实 root cause (D7):

  • Confirmation logic 依赖一个 feature_flag_service 拉的 flag
  • Flag 的 cache TTL 是 24h
  • Staging 每天 redeploy 自动 invalidate cache
  • Prod 不 redeploy, cache 一直拿的是周一改过期的 flag
  • "时间 + cache" 双 victim

6. 工程上要做什么 — 诊断 checklist

Stage 0: Stabilize (< 30 min)

  1. 评估 blast radius: 多少 % 流量受影响? 用户体感是 "wrong / different / slower"?
  2. 如果 > 50% → immediate rollback to last known good (LKG)
  3. 如果 < 5% 但持续 → 不 rollback, 收 sample 找 RCA
  4. Set up war room: incident channel, ICs assigned, status page updated
  5. Pause downstream automation (e.g., auto-billing based on agent output)

Stage 1: Reproduce (< 2 hours)

  1. 捞 10 个 prod failing trace_id, 拿到完整 request payload + headers + timestamps
  2. 在 staging 一字不差 replay 同样 input — 能复现就跳 Stage 2, 不能复现就跳 Stage 3
  3. 如果 staging 100% 复现 → 是input-driven, D1 / D2 嫌疑大
  4. 如果 staging 0% 复现 → 是env-driven, D3-D7 嫌疑大

Stage 2: Cheap diffs first (< 4 hours)

  1. D2 config diff: diff <(prod config get) <(staging config get)
  • model_id, system_prompt, temperature, top_p, max_tokens, stop sequences, tool definitions
  1. D3 artifact hash: deploy log 里抓 model SHA, tokenizer SHA, image SHA, 两边对比
  2. D4 dependency: diff <(prod pip freeze) <(staging pip freeze), 特别盯 vLLM / torch / transformers
  3. 配置 / hash / dep 全对得上 → 进 Stage 3

Stage 3: Expensive diffs (4-24 hours)

  1. D1 distribution: 过去 24h prod input 的 length / language / topic 分布 vs staging eval 分布. 找 staging 没覆盖的 segment
  2. D7 time audit: 检查 token expire, cache TTL, scheduled job, DST window, data freshness SLA
  3. D6 state: dump prod replica 内存 vs staging, 看 cache / counter / 任何 stateful counter
  4. D5 load: 把 staging QPS 拉到 prod 同等水平, 看是否复现

Stage 4: Fix + Prevent

  1. 写 minimal repro test, 加进 regression suite
  2. 写 postmortem (Five Whys), 至少 1 个 prevent action
  3. 部署 fix 走 canary (1% → 10% → 50% → 100%)

7. 几个容易踩的坑

#坑后果 / 应对
1立刻怀疑 model90% root cause 不是 model 本身, 是 config / version / env. 先 cheap diff
2没 trace_id 就开始 debug在 high QPS prod 里你根本找不到 specific failing request 的完整上下文
3没 reproduce 就开始 fix改完一个 dimension, 引入另一个, 修不完. No repro = no fix
4跳过 cheap diffs直接怀疑 GPU 非确定性, 但配置文件 1 行不一样
5Ship fix without RCA临时 patch 经常 mask 真因, 1 周后另一个 manifest 又出
6Customer 压力下 cave"立刻 fix" 比 "1h 内 rollback + 24h 找 RCA" 通常错. Negotiate workaround
7忽略 "recently changed"Recent change = recent break. 最近 deploy / config update / 依赖升级永远先查
8盯个例不看 segmentAggregate metric 看不到 5% 用户 100% 失败 (per-segment 才能看到)

一句话总结 (Part 1)

Staging vs Prod inconsistency debug = "先 reproduce, 再按 cheap → expensive 顺序排查 7 类 diff source, 最后用 hash + canary + shadow eval 防 recurrence".

这道题考的不是某个具体技巧, 是你有没有真的部署过 LLM 产品, 解决过 silent failure.

Part 2 · 5 个深度工程问题

⚙️ Problem 1: 7 类 diff source 怎么系统排查

Diff sources 是这道题的骨架. 系统讲清楚每一类的诊断手段 + 自动化方式.

1.1 D1 Data Drift — 用户输入变了

症状: 同样 model, 同样 config, 但 prod 输入分布和 staging eval 不一样.

诊断:

# 简化版 distribution monitor
from collections import Counter
from scipy.stats import ks_2samp

def compare_distributions(prod_inputs, staging_inputs):
    """对比关键维度的 distribution drift."""
    report = {}

    # Length distribution
    prod_len = [len(x) for x in prod_inputs]
    staging_len = [len(x) for x in staging_inputs]
    stat, p = ks_2samp(prod_len, staging_len)
    report['length_ks_p'] = p  # p < 0.05 → significantly different

    # Language distribution
    prod_lang = Counter(detect_lang(x) for x in prod_inputs)
    staging_lang = Counter(detect_lang(x) for x in staging_inputs)
    report['lang_diff'] = {
        lang: prod_lang.get(lang, 0) / sum(prod_lang.values()) -
              staging_lang.get(lang, 0) / sum(staging_lang.values())
        for lang in set(prod_lang) | set(staging_lang)
    }

    # Token-level: PSI (Population Stability Index)
    report['psi'] = compute_psi(prod_inputs, staging_inputs)

    return report

生产细节:

  • PSI > 0.25 → significant drift, 调查
  • Tail 维度 经常被忽略: 99th percentile length, 罕见 character set, 特殊 emoji
  • 多语言场景 尤其难: staging 只测 English, prod 用户 30% 是 Bahasa

1.2 D2 Config Drift — 配置不一样

最常见, 也最容易查:

# 一键 diff
diff <(kubectl get cm prod-agent-config -o yaml) \
     <(kubectl get cm staging-agent-config -o yaml)

自动化: 每次 deploy 出报告:

deploy_diff_report:
  changes:
    - field: system_prompt
      old_hash: abc123
      new_hash: def456
      diff: |
        +Respond only in English unless explicitly asked otherwise
    - field: temperature
      old: 0.0
      new: 0.7
      blast_radius: HIGH  # temperature 0 → 0.7 是大事

用工具:

  • Argo CD / Flux 自动 audit deploy diff
  • OpenFeature / LaunchDarkly flag changes 走变更管理
  • Git 任何 prompt / config 走 PR + eval-on-merge

1.3 D3 Model Version

最常见 silent bug:

# Deploy 时强制 assert hash 一致
def assert_artifact_consistency():
    declared = config['model_sha256']
    actual = sha256_of_file('/models/current/checkpoint.bin')
    if declared != actual:
        raise DeployError(f"Model hash mismatch: declared {declared}, actual {actual}")

    # 同样校验 tokenizer
    declared_tok = config['tokenizer_sha256']
    actual_tok = sha256_of_file('/models/current/tokenizer.json')
    if declared_tok != actual_tok:
        raise DeployError("Tokenizer hash mismatch")

真实 trap: model file 用了 symlink, symlink 没更新, 文件名对了但内容不对.

1.4 D4 Dependency

# Image-level diff
docker run --rm prod-agent:latest pip freeze > /tmp/prod.txt
docker run --rm staging-agent:latest pip freeze > /tmp/staging.txt
diff /tmp/prod.txt /tmp/staging.txt

特别盯:

  • vllm, sglang, transformers, torch, torchvision
  • CUDA driver / cuDNN 版本 (nvidia-smi)
  • 系统库 (libssl, libstdc++)

1.5 D5 Scale — Concurrency 触发的 bug

只在 production 高 QPS 下复现, 罕见但真实:

  • vLLM batch size: 同 input 在 batch=1 和 batch=32 下输出可能不一样 (paged attention 实现细节)
  • KV cache eviction: prod 内存压力下 cache 频繁 evict, 导致 prefix recompute, FP16 rounding 累积
  • Request scheduling order: 请求顺序影响 batch composition

复现工具:

  • vegeta / wrk 打 staging 模拟 prod 流量
  • 把 staging instance 缩容到 prod 同等内存压力

1.6 D6 State

# Per-replica state dump
def snapshot_state(replica):
    return {
        'kv_cache_used_bytes': replica.gpu_kv_cache.used,
        'prefix_cache_entries': len(replica.prefix_cache),

# 不同 replica state divergence

1.7 D7 Time

# Time-sensitive things audit
def audit_time_dependencies():
    checks = []
    # Token expire
    for token in active_tokens():
        checks.append(('token_expire', token.id, token.expires_at - now()))
    # Cache TTL
    for key in cache.scan():
        checks.append(('cache_ttl', key, cache.ttl(key)))
    # Scheduled jobs
    checks.append(('scheduler_next_run', scheduler.next_run()))
    # Data freshness
    checks.append(('data_max_updated_at', db.max_updated_at('orders')))
    return checks

真实事故: Vault token 12h TTL, prod 高峰期一直没 idle 触发 refresh, 12:01 同时过期, 大量 401.

⚙️ Problem 2: Reproducibility Instrumentation — trace_id / Snapshot / Replay

没 reproducibility 就是盲人摸象. 三件套缺一不可.

2.1 trace_id Propagation (端到端追踪)

目标: 任何 prod request, 给一个 trace_id, 能在所有 log / DB / metric / blob storage 里找到所有相关记录.

# 用 OpenTelemetry 标准
from opentelemetry import trace
from opentelemetry.propagate import inject, extract

tracer = trace.get_tracer(__name__)

@app.middleware
async def trace_middleware(req, call_next):
    # 从 header 提取或新建
    ctx = extract(req.headers)
    with tracer.start_as_current_span("http_request", context=ctx) as span:
        trace_id = format(span.get_span_context().trace_id, '032x')
        req.state.trace_id = trace_id
        response = await call_next(req)
        response.headers['X-Trace-Id'] = trace_id
        return response

# 所有 log 自动带 trace_id
import structlog
log = structlog.get_logger()

def agent_handler(req):
    log.info("agent_invoked", trace_id=req.state.trace_id, user_id=req.user_id)
    # 调 LLM
    log.info("llm_request",
             trace_id=req.state.trace_id,
             model=cfg.model_id,
             prompt_hash=sha256(prompt))

关键:

  • trace_id 一定要进 LLM API call 的 metadata 字段, 这样 OpenAI / Anthropic 的 dashboard 也能查
  • trace_id 进 response header, 让 client 错误报告能带上
  • trace_id 进 audit log (合规)

2.2 Snapshot Capture (快照捕获)

目标: 任何 request 失败时, 自动 snapshot 完整 reproduce context.

@dataclass
class RequestSnapshot:
    trace_id: str
    timestamp: int
    user_id: str
    region: str
    request_body: dict
    request_headers: dict

    # Environment
    model_id: str
    model_sha: str
    tokenizer_sha: str
    image_sha: str
    pod_id: str
    gpu_type: str

    # Runtime
    feature_flags: dict
    config_snapshot_sha: str

    # LLM-specific
    system_prompt_hash: str
    temperature: float
    top_p: float
    max_tokens: int
    seed: Optional[int]

    # Result
    response_body: dict
    latency_ms: int
    error: Optional[str]

def capture_snapshot(req, resp, err):
    snap = RequestSnapshot(
        trace_id=req.trace_id,
        # ... fill all fields
    )
    # 失败的全存, 成功的 1% 抽样
    if err or random() < 0.01:
        s3.put(f'snapshots/{req.trace_id}.json', snap.to_json())

存储:

  • 失败请求 100% 存, 保留 30 天 (合规)
  • 成功请求 1% 抽样, 保留 7 天 (debug 用)
  • 敏感字段 (PII) 加密或 hash

2.3 Replay Tool

# 一键 replay
class ReplayTool:
    def __init__(self, target_env='staging'):
        self.target = target_env

    def replay(self, trace_id):
        snap = s3.get(f'snapshots/{trace_id}.json')

        # 用 prod 当时的 config 调 staging
        cfg = self.fetch_config(snap.config_snapshot_sha)

        # 在 staging 重放, 用 prod 的 system prompt / temperature
        result = self.target_env.invoke_agent(
            request_body=snap.request_body,
            override_config=cfg,
            override_seed=snap.seed,
        )

        return {
            'prod_response': snap.response_body,
            'staging_response': result,
            'match': snap.response_body == result,
            'env_diff': self.diff_env(snap),
        }

# Usage
tool = ReplayTool('staging')
result = tool.replay('abc123def456')
print(result['match'])  # True/False
print(result['env_diff'])  # what's different

自动化: 每天 cron 拿前一天的 prod failing traces, 在 staging replay, 算 reproduce rate. 如果 < 50% 一致 → "我们的 staging 已经不能代表 prod 了, 需要修复 parity".

⚙️ Problem 3: Environment Parity Strategies

让 staging "更像" prod 的三个策略:

3.1 Golden Traces (黄金样本集)

思想: 维护一组 representative prod requests + expected outputs, 每次 deploy 必须先跑过.

# Golden trace 数据集
golden_traces = [
    {
        'name': 'indonesia_refund_above_threshold',
        'request': {...},  # 一个真实的印尼大额退款请求
        'expected_response_contains': ['请确认', 'Indonesia rules require'],
        'last_updated': '2026-04-15',
        'business_owner': 'wei@bytedance',
    },
    # ... 200-500 个 case
]

# CI gate
def gate_deploy(candidate_image):
    fails = []
    for trace in golden_traces:
        actual = candidate_image.invoke(trace.request)
        if not match(actual, trace.expected_response_contains):
            fails.append(trace.name)
    if fails:
        block_deploy(f"Golden trace failures: {fails}")

维护:

  • 每个 production incident → 加 1 个 golden trace 防 regression
  • 季度 review, 删除过时的 case
  • Cover all segment (per market, per user type, per topic)

3.2 Shadow Mode (影子模式)

思想: Prod 请求同时发给 prod 和 staging, 对比输出, 只用 prod 的, 但记录 staging 的 diff.

User → API Gateway → Fork
                       ├──► Prod Agent  → Return to user (used)
                       └──► Staging Agent → Compare, log diff (shadow)

实现要点:

  • Shadow path 必须 async, 不能阻塞 user
  • Diff 用 semantic similarity, 不要 exact match (LLM 输出有合理变化)
  • 抽样 1-10% 流量做 shadow, 不要 100% (cost)
  • Shadow diff 日报: "今日 staging 和 prod 的 disagreement rate: 3.2%"
async def shadow_invoke(req):
    # 真正服务
    prod_task = asyncio.create_task(prod_agent.invoke(req))
    # 影子
    if random() < shadow_sample_rate:
        staging_task = asyncio.create_task(staging_agent.invoke(req))
    else:
        staging_task = None

    prod_resp = await prod_task

    if staging_task:
        try:
            staging_resp = await asyncio.wait_for(staging_task, timeout=5)
            log_shadow_diff(req, prod_resp, staging_resp)
        except asyncio.TimeoutError:
            pass

    return prod_resp

3.3 Canary Deployment + Auto Rollback

思想: 新版本先 1% 流量, 没问题再 10%, 再 50%, 再 100%. 同时监控错误预算, 一旦超就自动 rollback.

# Argo Rollouts spec
strategy:
  canary:
    steps:
    - setWeight: 1
    - pause: { duration: 10m }
    - analysis:
        templates:
        - templateName: error-rate
        - templateName: latency-p99
        - templateName: agent-success-rate
    - setWeight: 10
    - pause: { duration: 30m }
    - analysis: [...]
    - setWeight: 50
    - pause: { duration: 1h }
    - setWeight: 100

自动 rollback 条件 (示例):

  • error rate > 1% (vs baseline 0.1%)
  • p99 latency > 2x baseline
  • agent_success_rate < 95%
  • 5xx > 0.5%

工具: Argo Rollouts / Flagger / 自研.

⚙️ Problem 4: Stateful vs Stateless Differences

很多 inconsistency 来自 state, 不是 logic.

4.1 Cache Warm-up

Staging:    Cache 总是 cold (低流量, 经常 LRU 驱逐)
Production: Cache 永远 hot (高流量, 重复 query 多)

→ Prod 大量 cache hit, 走 fast path
→ Staging 大量 cache miss, 走 slow path  
→ Slow path 有个 bug, staging 永远看不到 (因为 hot path 把 bug 绕过去了)
→ 或反过来: hot path 有 race condition, staging 因为 cold 永远不触发

应对: 测试时主动 warm up cache 或主动 invalidate, 两种状态都跑.

4.2 In-memory State Divergence

# Reproducibility killer: 单例 / 全局变量随时间累积
class AgentMetrics:
    """单例, 每个 replica 各一份, 状态随时间 drift."""
    _instance = None

    def __init__(self):
        self.total_requests = 0
        self.consecutive_failures = 0  # ← 这个会影响 retry 策略!

# Replica A 累积 1000 个 consecutive_failures (因为 down 过), 进入降级模式
# Replica B 永远 0, 正常模式
# 同样 input 到 A 走降级, 到 B 走正常, "inconsistency"

应对:

  • 状态外置到 Redis / DB
  • 或定期 reset 全局状态
  • Per-replica health endpoint 暴露状态

4.3 KV Cache Effects (vLLM / SGLang)

LLM inference 的 KV cache 是 stateful 的:

Request 1: "今天天气怎么样" → prefix [今天, 天气, 怎么样] 进 KV cache
Request 2: "今天我心情很差" → prefix [今天] 复用上次 cache 的 K/V
                                ↓
                            如果上次 cache 计算时 batch size = 32
                            这次 cache 复用时 batch size = 1
                            FP16 rounding 微妙不同
                            → 同 input 不同输出 (罕见但真实)

应对:

  • 关键场景禁用 prefix cache (enable_prefix_caching=False)
  • 或接受非确定性, 在 eval 用 multiple-runs + 取中位
  • 实际生产: 99% 用户不在乎这点差异, 但 audit / regression test 要注意

4.4 Multi-replica State Divergence

# 监控 replica 之间状态差
def replica_consistency_check():
    snapshots = []
    for r in replicas:
        snapshots.append(r.fetch_state())

    # 找出 outlier
    medians = {}
    for key in snapshots[0]:
        values = [s[key] for s in snapshots]
        medians[key] = statistics.median(values)

    outliers = []
    for r, snap in zip(replicas, snapshots):
        for key, val in snap.items():
            if isinstance(val, (int, float)) and val > 3 * medians[key]:
                outliers.append((r.id, key, val))

    if outliers:
        alert(f"Replica state outliers: {outliers}")

⚙️ Problem 5: Time-Dependent Bugs

时间相关 bug 是最难复现的一类, 因为它们只在特定时间窗口出现.

5.1 DST (Daylight Saving Time)

症状: 每年 3 月、11 月美国 DST 切换那天系统全坏.

典型 bug:

# 错: 用 local time 做调度
schedule = "0 2 * * *"  # 每天凌晨 2 点
# DST 切换日, 凌晨 2 点跳过了 (spring forward) 或重复 (fall back)
# → 这一天任务跑 0 次或 2 次

# 对: 用 UTC
schedule = "0 6 * * *"  # UTC 6:00, 对应美东标准时间 1:00 (永远存在)
# 显示给用户时再转换 local

预防: 所有内部 timestamp 用 UTC, 用户显示再转 local.

5.2 Timezone

症状: 印尼用户在 23:30 提交一个 "明天还款", system 解析成下下周 (because server 算的是 UTC 的明天).

典型 bug:

# 错: 服务端 datetime.now() 不带 tz
deadline = datetime.now() + timedelta(days=1)

# 对: 显式传 user timezone
def parse_relative(user_input, user_tz):
    user_now = datetime.now(tz=ZoneInfo(user_tz))
    if "明天" in user_input:
        return user_now + timedelta(days=1)

5.3 Data Freshness

症状: Agent 拉用户余额 API, prod 缓存 1h, staging 缓存 1min, prod 经常给过时数据.

# Cache TTL parity 校验
def assert_cache_parity():
    for cache_name in ['user_balance', 'user_status', 'loan_terms']:
        prod_ttl = prod_redis.config_get(f'ttl_{cache_name}')
        staging_ttl = staging_redis.config_get(f'ttl_{cache_name}')
        assert prod_ttl == staging_ttl, f"{cache_name} TTL mismatch"

5.4 Expired Tokens (你 OAuth 题的延续)

症状: 第三方 API token 12h TTL, prod 在 12h 那一刻所有 worker 同时刷新, 触发 thundering herd, 部分请求超时.

# 预过期 + 分布式锁 (前面 OAuth 题讲过)
def get_token(tenant_id):
    cached = cache.get(f"token:{tenant_id}")
    # 提前 5 min 视为过期, 避免边界
    if cached and cached.expires_at - now() > 300:
        return cached.token

    with distributed_lock(f"refresh:{tenant_id}"):
        # 再查一次 (singleflight)
        cached = cache.get(f"token:{tenant_id}")
        if cached and cached.expires_at - now() > 300:
            return cached.token

        new = oauth.refresh(cached.refresh_token)
        cache.set(f"token:{tenant_id}", new, ttl=new.expires_in - 600)
        return new.token

5.5 Scheduled Job / Cron Misalignment

典型 bug: data pipeline 每天 02:00 跑, agent 每天 02:30 启动, 但 pipeline 因为依赖 03:00 才 ready, agent 在 02:30-03:00 拿到 stale data, 给错误答案.

预防:

  • 数据 freshness signal: agent 启动前 check MAX(updated_at) 是不是足够新
  • 如果不够新, fail loudly, 不要默默用 stale

Part 3 · 把 5 个问题串起来看

这 5 个问题是同一件事的 5 个 viewpoint:

  1. 7 类 diff source 是「root cause 空间」
  2. Reproducibility instrumentation 是「搜索这个空间的工具」
  3. Environment parity 是「让搜索空间变小的预防」
  4. State 是「搜索空间中最隐蔽的一片暗区」
  5. Time 是「搜索空间中第二隐蔽的一片暗区」

面试场或事故复盘上, 能讲出这套系统化诊断方法, 而不是只讲「我看 log 然后 fix」, 是 staff-level 工程师的标志.

必问 clarifying questions

1. Define "inconsistent"

"What kind of inconsistency — wrong answers, different answers each time (non-determinism), or slower answers that get truncated? They have completely different RCA paths."

2. Frequency

"All requests, or specific ones? Percentage? Same input always reproduces, or stochastic?"

3. Same artifact?

"Are staging and prod running the identical model + tokenizer + system_prompt + image SHA? Has anyone verified by hash?"

4. Same input shape?

"Are users in prod sending the same distribution of input as staging eval? Length, language, topic, edge cases?"

5. Recent change

"Has anything changed in last 7 days — new release, feature flag, upstream API, infra migration, model upgrade, deps?"

6. Time/segment pattern

"Does inconsistency cluster by region, time-of-day, user segment, request length? Pattern guides hypothesis."

5 步框架

时长阶段
0-5 minClarify + reproduce attempt
5-15 minD2/D3 cheap diffs (config + artifact hash)
15-25 minD4/D1 medium (dep diff + input distribution)
25-40 minD6/D7 hard (state introspect + time audit)
40-50 minD5 expensive (load test if all else fails)
50-60 minFix + Prevent (golden trace + canary + shadow)

"I've debugged exactly this shape. Rolling our voice agent from Singapore-only to multi-region, we got 25% inconsistency rate on Thai customers — Bahasa replies were defaulting to English. I went cheap-first: D2 config diff caught it immediately — the release before added Respond only in English unless explicitly asked otherwise to the system prompt, and that change had never been in our staging eval suite. 5 follow-ups

Q1: "We've checked configs identical, can't reproduce on staging, but it reproduces 30% on prod. What now?"

A: 这是经典 D5/D6 嫌疑. Steps:

  • 加 trace_id + per-request snapshot, 收 24h 样本
  • Bucket failing traces by: region, GPU type, replica_id, batch_size, time_of_day, request_length
  • 看哪个 bucket 失败率显著高 → 是 hypothesis
  • 典型 finding: 某个 replica 状态 stale / 某个 GPU type 库版本不同 / 某个 batch_size 触发 paged attention bug
  • 不能反过来 "我猜 GPU 然后试着 fix", 必须让数据说话

Q2: "We can't reproduce even with same input on prod replay. Is it a ghost?"

A: Non-determinism 是 prime suspect:

  • temperature=0 enforced? top_p < 1? top_k 设了吗?
  • seed 参数固定了吗? (OpenAI API 有 seed, vLLM 也有)
  • Tokenizer 顺序: BPE merges might differ between versions
  • GPU kernel non-det: torch.use_deterministic_algorithms(True), set CUBLAS_WORKSPACE_CONFIG=:4096:8
  • Batch composition: vLLM 在 batch 内的 attention 是 deterministic 但和 batch_size 有关
  • 实战: 接受 5% 输出有合理变化, 用 semantic similarity 而不是 exact match 衡量

Q3: "Bug is intermittent. Just ship a fix?"

A: 不行. Without RCA:

  • 高概率 fix 不 address actual bug
  • 高概率 fix 引入 new bug
  • Workaround: ship observability first (trace + snapshot + region tags), 等 24h 收 sample 找 pattern. Patience > hasty patch.
  • 如果客户压力大: temporary rollback to LKG, 给自己时间找 RCA

Q4: "Customer demands immediate fix. We don't know root cause."

A: Negotiate workaround:

  • "Roll back to last-known-good (4h MTTR) — restores consistency at cost of new feature X. Acceptable?"
  • "Disable agent for input types that fail — partial coverage but 100% consistent"
  • "Move 100% traffic to known-good region, accept higher latency for non-local users"
  • 诚实的 workaround 永远好过盲 fix. 盲 fix 通常延长事故.

Q5: "If staging is so unreliable a predictor of prod, why have it?"

A: Staging 不是 prod 的 100% mirror, 它是:

  • Catch catastrophic bugs (语法错, 服务起不来, API 不兼容) — staging 抓 70%
  • 提供 regression test harness
  • 给 PM / QA review 新 feature 的地方
  • The remaining 30% 要靠 canary + shadow + golden traces + per-request observability 兜底
  • "Staging unreliable" 不是放弃 staging 的理由, 是升级到 staging + canary + shadow 三件套的理由

❌ 易错点

  1. 立刻怀疑 model — 90% root cause 不是 model 本身
  2. 没 trace_id 就 debug — 在 high QPS 里找不到 specific failing request
  3. 没 reproduce 就 fix — 改完一个 dimension, 引入另一个
  4. 跳过 cheap diffs — 直接怀疑 GPU 非确定性, 但配置 1 行不同
  5. Ship fix without RCA — temporary patch 通常 mask 真因
  6. 没 instrumentation 就 deploy — 没 region tag / GPU tag / version tag, 一切靠猜
  7. Customer 压力下盲 fix — 通常延长事故
  8. 忽略 "recently changed" — recent change = recent break

✅ 加分项

  1. 7 类 diff source 清晰分类
  2. Cheap-first 诊断顺序
  3. trace_id + snapshot + replay 三件套
  4. Per-request artifact provenance log as preventive
  5. Shadow eval at 1-10% traffic 防 future drift
  6. Canary auto-rollback on error budget standard SRE
  7. GPU non-determinism awareness (cuBLAS, paged attention)
  8. Golden trace gate at deploy
  9. State divergence monitoring across replicas
  10. Time / timezone / DST awareness
  11. System prompt as code + eval-on-PR
  12. Negotiate workaround under pressure instead of blind fix

一句话总结

Staging vs Prod inconsistency debug = "先 reproduce (trace + snapshot + replay), 再按 cheap → expensive 排查 7 类 diff source (config / version / dep / data / time / state / scale), 然后用 hash + canary + shadow + golden trace 防 recurrence".

这道题考的不是「我会用 Datadog 看 log」, 是「我有没有真的 own 过一个 LLM 产品的 production lifecycle」.

Cheat Sheet (印 1 页)

7 diff sources (cheap → expensive):
  D2 Config drift     (model_id / prompt / temp / top_p)
  D3 Model version    (artifact + tokenizer SHA)
  D4 Dependency       (vLLM / torch / cuDNN / lib)
  D1 Data             (input distribution shift)
  D7 Time             (DST / TZ / token expire / freshness)
  D6 State            (cache warm / in-mem / KV cache / replica)
  D5 Scale            (batch / concurrency / KV evict)

Real-world distribution of root cause:
  D2  35% — recently-changed config
  D3  20% — wrong artifact deployed
  D7  15% — time/cache TTL
  D1  12% — long-tail input
  D6  10% — replica state divergence
  D4   5% — dep upgrade silent
  D5   3% — only at peak QPS

Diagnostic flow:
  1. Clarify "inconsistent" (wrong / different / slow)
  2. Stabilize (rollback if > 50% impact)
  3. Reproduce (10 prod traces → replay staging)
  4. Cheap diff (config + hash + dep) ← 60% RC here
  5. Medium diff (data dist + time audit) ← 27% here
  6. Hard diff (state introspect + load test) ← 13%
  7. Fix + golden trace + prevent

Reproducibility 三件套:
  trace_id propagation (OpenTelemetry)
  Per-failure snapshot (S3, 30d retain)
  Replay tool (prod trace → staging run)

Env parity strategies:
  Golden traces (200-500 case CI gate)
  Shadow mode (1-10% fork to staging)
  Canary + auto-rollback (1→10→50→100%)

State traps:
  Cache warm vs cold (test both)
  In-memory singleton drift (externalize state)
  vLLM KV cache + batch_size (FP16 rounding)
  Per-replica divergence (monitor outliers)

Time traps:
  DST (use UTC everywhere)
  Timezone (per-user tz, not server tz)
  Token expire (preempt 5min + dlock)
  Data freshness (assert MAX(updated_at) recent)
  Cron misalignment (depend on signal, not clock)

Quick wins (deploy hardening):
  - Per-request observability (region/gpu/lib SHA)
  - Hash-versioned deploy artifacts (assert pre-deploy)
  - Shadow 1% prod → staging-mirror
  - Canary + auto-rollback every deploy
  - Golden trace CI gate
  - System prompt as code + eval-on-PR

Workarounds while diagnosing:
  - Route 100% to known-good region
  - Disable agent for specific input types
  - Roll back infra (4-6h)
  - DO NOT patch blindly

红线:
  - Don't blame model first
  - Don't ship fix without RC
  - Don't ignore "recently changed"
  - Don't debug without trace_id
  - Don't trust file names (use SHA)
