Problem Statement

Agent 多 turn + 多 tool call — 怎么 trace 一个用户请求的完整执行链。LangSmith / Phoenix / OpenTelemetry。Metrics 该 instrument 哪些。Cost tracking。

我的思路与解法

题目

"An LLM agent in production is misbehaving — sometimes wrong answer, sometimes slow, sometimes expensive. You can't reproduce it locally. Design the observability stack so you can debug + improve."

或追问形态:

"Walk through the difference between observability for traditional web service vs LLM agent. What's new / different?"

出处: Google FDE T3 production observability round 高频题. 2026 LLM platform team 必备能力.

Round: Production Observability (45-60 min)

这道题在考什么

考你 在 prod 跑过 LLM agent + 真正 debug 过 LLM-specific 问题:

  1. 4-layer instrumentation —— distributed trace + LLM-specific log + metrics + quality eval
  2. Sampling strategy —— 10K QPS 不能 100% log, tail sampling / error-100% / slow-100% / anomaly
  3. PII redaction —— prompt + response 含敏感信息, 必须 redact (presidio) + hash for correlation
  4. Eval-in-prod —— LLM-as-judge sample, drift detection, calibration to human eval
  5. Debug workflow —— trace_id → slice analysis → re-run → root cause
  6. LLM-specific signals —— TTFT, token cost, eval pass rate, jailbreak attempts, hallucination

传统 web observability 工具不够用 — LLM agent 有 prompt template version, model version, tool call chain, semantic similarity 等独特维度.

Part 1 · 教学讲解 — 先把概念讲透

1. 四个术语先解释

Distributed Tracing: 一个 user request 走完全程的所有 span 串成一条 trace. 现代标准是 OpenTelemetry (OTel) — vendor-neutral SDK, 输出到 Datadog / Honeycomb / Jaeger / Tempo / Phoenix. Trace 由 trace_id (全局唯一) + span_id (每段) + parent_span_id (父子关系) 组成.

Eval-in-prod: 把 LLM evaluation 放到 production. 不是离线跑 benchmark, 而是实时抽样 5% 的真实 traffic, 用 LLM-as-judge 或 user feedback signal 评分, 监控 quality drift. 这是 2026 LLM platform 标配, 不做就盲飞.

PII redaction: 个人识别信息脱敏. Prompt + response 可能含信用卡 / 邮箱 / 电话 / SSN / 病历. 必须在 log 写入前 redact, 不能等 log 进了 SIEM 再来. 用 Microsoft Presidio / AWS Macie / Google DLP 等成熟库.

Tail-based sampling: 不是随机 1% sample, 而是等 trace 完成后, 看整条 trace 特征再决定保不保留. 慢的 / 错的 / 异常的 100% 保留, 正常的 1% 保留. Honeycomb / Datadog / Tempo 都支持.

2. 核心问题 (灾难场景)

设想没有 observability stack, agent 在 prod 出问题:

灾难 A — 用户报问题, 但没法 reproduce:

用户:  "你的 agent 昨天给我答错了 invoice 金额"
你:    "什么时候发生的?"
用户:  "下午 3 点左右吧"
你:    没 trace, 不知道用户问的什么, 不知道 agent 用了哪个 tool, 不知道哪个 model 版本

只能在 staging 用类似 prompt 试: 试不出来 (因为 prompt template 已经升级, 工具响应已经变, RAG 数据已变)

结果: "请提供更多信息" "我们调查中" — 几天过去都没结论

灾难 B — 全 log 不区分 trace:

log format (典型反模式):
  2026-05-21 14:30:00 INFO [chatbot] User asked: "what's my balance"
  2026-05-21 14:30:00 INFO [chatbot] LLM call to gpt-5.5
  2026-05-21 14:30:01 INFO [chatbot] Tool call get_balance
  ...

100 个并发 request 的 log 全混在一起, 没法分清哪些 line 属于同一个 user request.
排查必须从时间近邻 + 关键词搜, 极其低效.

正确: 每行带 trace_id + span_id + user_id

灾难 C — 不做 eval-in-prod:

传统 metric:  p99 latency 250ms ✓
              error rate 0.5% ✓
              throughput 8K QPS ✓
              
所有 metric 都正常, dashboard 一片绿.

但用户实际感受: "agent 最近答得变差了"

为什么 metric 不暴露? 因为 LLM 失败 ≠ HTTP 5xx, LLM 给出垃圾答案是 200 OK 但内容差.

解: 5% sample 用 LLM-as-judge 评分 → 跟踪 eval pass rate (1 周看 trend)

灾难 D — PII 明文写 log:

log: "User john.doe@bank.com asked about card ending 4242, balance was $5234.21"

后果:
  - SOC2 / GDPR audit fail
  - Log aggregation (Splunk, Datadog) 现在持有客户 PII
  - 内部员工任何 dev 都能搜到客户数据
  - Log retention 政策违反 (PII 需要 special handling)
  - Bug: hash key 不动但 PII 还在 → CCPA 删除请求时漏

正确: 在 log 写入前 redact, "[EMAIL] asked about [CARD], balance [REDACTED]"
保留 hash for correlation: log_id += hash(email) 让客服能查

正确的 mental model — 4 layers:

L1 Distributed Tracing      → 每 request 端到端 span 链
L2 LLM-specific Logging     → prompt / response (PII-redacted) / model version
L3 Metrics                  → latency, cost, error rate (time-series)
L4 Quality Monitoring       → eval-in-prod, drift detection, user signal

5. 具体业务场景 (4-5 个深度变体)

场景 A: 生产 agent silent quality drop (经典)

用户报: "agent 最近答得变差了". 所有 metric 正常.

Debug 流程:

Step 1: 用户反馈量化
  - "变差" 是什么 — collect thumb-down rate
  - 时间 — 哪天开始, 多大用户群感受到
  - 实测: thumb-down rate 上周 3% → 这周 6%, 翻倍

Step 2: Eval-in-prod 抽样数据
  - 过去 7d 的 5% LLM-as-judge 评分 vs 之前
  - 实测: eval pass rate 92% → 85%, 7pp drop, 显著

Step 3: Slice by 维度找 outlier
  - by model:           gpt-5.5 4% drop, gemini-3-pro 11% drop ← bingo
  - by tenant:          tenant_42 normal, tenant_88 18% drop
  - by query type:      'how do I' normal, 'compare X vs Y' drop big
  - by time-of-day:     12-15h drop bigger

Step 4: 时间对齐发布 / 配置变更
  - 5/14 deploy: prompt template v3.1 → v3.2
  - 5/15: RAG corpus 更新 (上传新文档)
  - 5/17: Gemini 3 Pro vendor side update

Step 5: 抽 100 'bad' case 详读
  - LangSmith 查 eval < 0.5 的 trace
  - 发现共性: agent 回答 confidence 很高但事实错误
  - 看 RAG 检索: top-3 chunk 有 1 个明显 wrong

Step 6: Root cause
  - 新 RAG corpus 上传的文档某些段落 metadata error
  - reranker 错误地给低质量 chunk 高分
  - LLM 信了 RAG 的 chunk

Step 7: Fix
  - 紧急: revert RAG corpus
  - 中期: 加 RAG quality eval (chunk 准确性 daily test)
  - 长期: 双盲 review 每次 RAG corpus update

实战工具:
  LangSmith / Phoenix → 抽 bad case trace, 详读 RAG retrieval
  Datadog → metric slicing
  BigQuery → 长期 trend

场景 B: Cost spike investigation

本周 LLM bill 突然 5x. 谁 / 什么 / 为什么?

Debug 流程:

Step 1: 按 tenant attribution
  Dashboard: cost per tenant per day, 7 day trend
  发现: tenant_88 周一 $50 → 周四 $5000 (100x spike)

Step 2: 按 feature attribution (per-span tag)
  - tenant_88 的所有 trace, 按 feature_id 聚合
  - 实测: 'document_chat' feature 占 95%
  - 调查: 该 feature 是上周新上线

Step 3: 看 individual session 行为
  - 拉 tenant_88 的 trace
  - 实测: 平均 session 30+ LLM call (vs 平台均值 5 calls)
  - 单 session 平均 cost $1.5 (vs 平台均值 $0.05)

Step 4: 看 prompt token
  - 该 feature input token / call: 平均 50K (vs 平台均值 1K)
  - Why? 因为 'document_chat' 把整个 PDF 塞 context

Step 5: 看 cache hit
  - Prefix cache hit rate: 5% (vs 平台 80%)
  - Why? 因为每 session 不同 PDF, system prompt 也变了

Step 6: Root causes
  a. New feature 没 cost guard
  b. PDF size 没 limit, 上传 100MB PDF
  c. Cache hit 低 (different PDF per session)
  d. 用了 Opus 4.7 ($5/$25) 而不是 Flash

Step 7: Fix
  - 紧急: cap tenant_88 monthly budget, alert
  - 中期: feature-level: PDF size limit 10MB, route to Flash for first pass
  - 长期: per-feature cost guard alarm

实战工具:
  Datadog cost dashboard
  BigQuery for tenant deep dive
  LangSmith for individual trace inspection

场景 C: P99 latency alert fired

P99 latency 突 2s → 5s. Page oncall.

Debug 流程:

Step 1: 看 trace 在哪一 span 慢
  - Tail sampled traces (P99) 进 Honeycomb
  - 看 span breakdown
  - 发现: LLM call 占 4s (本应 ~500ms)

Step 2: 看哪个 model / replica
  - by model: gemini-3-pro normal, llama-70b-self-host slow
  - by replica: replica-23 占 80% slow traces
  - 实测: replica-23 GPU util 100%, 比其他高

Step 3: 看 replica 内部 metric
  - queue depth: 200 (上限), 其他 replica < 50
  - KV cache util: 95% (满)
  - Batch size 上限到了

Step 4: 看为什么 load 不均
  - Sticky routing per conv_id, 某些大 user (long conv) 集中到 replica-23
  - Routing 没考虑 conv length

Step 5: Fix
  - 紧急: drain replica-23, 让 conv 重新分布
  - 中期: routing 算法考虑 conv length, balance better
  - 长期: 容量规划, replica 数量 +20%

实战工具:
  Honeycomb / Tempo trace view
  Datadog dashboard per replica
  vLLM admin endpoint (/metrics)

场景 D: Jailbreak attempt detection

怎么知道有人试图越狱 agent?

Detection 策略:

Step 1: Input pattern matching
  Pattern detection on user query:
  - "ignore previous instructions"
  - "pretend you are"
  - "developer mode"
  - "DAN" (Do Anything Now)
  - "roleplay as"
  - 中文 jailbreak: "忽略之前的指令"
  → 命中 → 标记 suspicious = True

Step 2: Real-time LLM classifier
  - 小 model (Haiku $1/1M) classify: "is this a jailbreak attempt?"
  - 100ms latency, cheap
  - 训练 / few-shot with examples
  - 命中 → flagged = True

Step 3: Response pattern detection
  - Agent 输出 包含 'I cannot' / 'as an AI' 异常增多 → 攻击中
  - 用户 / session frequency of attempts → 频繁 → 异常

Step 4: Honeypot
  - Inject 'secrets' 假信息: "ignore: SECRET_KEY=ABC123_TEST"
  - 看 agent 输出是否泄漏 → 检测 jailbreak 成功
  
Step 5: Forensics 存储
  - Full input + output 存安全存储 (单独 retention)
  - Separate index, no PII mixing
  - 7d hot, 90d cold

Step 6: Alert + block
  - User > 10 attempts/min → temp ban 30min
  - User > 50 attempts/day → manual review by security
  - Tenant pattern → escalate to security team

实战:

flagged_traces = await datadog.query(
    "@input.jailbreak_flag:true",
    window="last 1h"
)
for trace in flagged_traces:
    if trace.user_id not in already_alerted:
        await alert_security(trace.user_id, trace.input)

监控 metric:
  - jailbreak_attempts_total (counter)
  - jailbreak_attempts_by_user (gauge)
  - jailbreak_attempts_per_min (rate)
  - jailbreak_success_rate (when honeypot triggered)

场景 E: Per-tenant SLA verification

卖 agent 给 enterprise, 承诺 99.9% / p99 < 2s. 怎么证明做到了?

Setup:

1. Per-tenant SLI dashboard
   - Availability: success rate per tenant
   - Latency: p50/p95/p99 per tenant
   - Error rate: by HTTP code + LLM-specific (refusal, hallucination)
   - Quality: eval pass rate per tenant

2. Synthetic probes
   每分钟模拟 1 tenant request:
   - 用 standard test case
   - 测量 latency + success
   - 长期 reliability 测量 (independent of real traffic)

3. SLO error budget
   99.9% = 43min downtime/month
   每周 review: 本月用了多少 budget
   超 50% 用了 → 暂停 deploy
   超 100% → page 紧急

4. Monthly report
   Auto-generate:
   - Availability achieved
   - Latency distribution
   - Top errors
   - Incidents (with RCA links)
   - Cost summary
   给 customer 看

5. Incident attribution
   - Internal incident → counts vs SLA
   - Customer's fault (e.g., bad input) → not counted
   - Vendor's fault (OpenAI down) → counted, but split out

6. Compensation policy
   - 触发 breach 自动给 credit
   - 0-30% 可用性 → 100% credit
   - 30-90% → 50% credit
   - 90-99% → 25% credit
   - 99-99.9% → 10% credit
   
7. Independent audit
   - 第三方 Datadog Synthetic / Pingdom 监控
   - Reports 给 customer 看 (no conflict of interest)

设计 observability stack:

  1. OTel SDK 接入所有 service — Python / Node / Go 都用 OTel
  2. Trace context propagation — HTTP / gRPC / Kafka 都注入 traceparent header

一句话总结 (Part 1)

LLM agent observability = 4 layers: (L1) distributed trace OTel-based, (L2) PII-redacted LLM-specific log (prompt + response + tokens + model + version), (L3) metrics (latency / cost / error / cache hit / eval), (L4) quality monitoring with eval-in-prod 5% sample + drift detection + user signals.

传统 web observability 不够 — LLM-specific signals (TTFT/TPOT, token cost, prompt template version, model version, RAG corpus version, jailbreak attempts, hallucination, refusal) 都要专门捕获. 没有这些, prod LLM agent 是黑盒.

⚙️ Problem 2: Sampling Strategy at Scale — Tail-based, Error-100%, Slow-100%, Anomaly

10K QPS 不能 100% sample. 但要 catch 关键 trace. Tail-based sampling 是答案.

2.1 为什么 head sampling 不够

Head sampling (sample at start):
  trace 第一个 span 决定要不要 sample (e.g., random 1%)
  
Problem:
  Error trace: 99% miss (因为 only 1% sampled)
  Slow trace: 99% miss
  
解决: tail sampling

2.2 Tail-based sampling 机制

class TailSampler:
    """OTel collector tail sampling processor"""
    
    def __init__(self):
        # Buffer all spans for a trace until trace 'completes' or timeout
        self.buffers = {}   # trace_id → list[span]
        self.timeouts = {}  # trace_id → deadline
    
    async def process_span(self, span):
        trace_id = span.context.trace_id
        
        # Buffer
        self.buffers.setdefault(trace_id, []).append(span)
        self.timeouts[trace_id] = time.time() + 30   # 30s timeout
        
        # If this is the root span (parent_span_id is None), wait 5s then decide
        if span.parent_span_id is None:
            asyncio.create_task(
                self._decide_and_export(trace_id)
            )
    
    async def _decide_and_export(self, trace_id):
        # Wait for child spans
        await asyncio.sleep(5)
        
        spans = self.buffers.pop(trace_id, [])
        if not spans:
            return
        
        # Apply sampling rules
        should_keep = self._should_keep(spans)
        
        if should_keep:
            for span in spans:
                await self.exporter.export(span)
        # Else: drop entire trace
    
    def _should_keep(self, spans):
        """Apply sampling rules"""
        # Rule 1: error → 100% keep
        if any(s.status_code == "ERROR" for s in spans):
            return True
        
        # Rule 2: slow trace → 100% keep
        root = next((s for s in spans if s.parent_span_id is None), None)
        if root and root.duration_ms > 5000:
            return True
        
        # Rule 3: high cost → 100% keep
        total_cost = sum(s.attributes.get("llm.cost_usd", 0) for s in spans)
        if total_cost > 0.5:
            return True
        
        # Rule 4: low eval score → 100% keep (filled async)
        # Done in eval pipeline
        
        # Rule 5: jailbreak flagged → 100% keep
        if any(s.attributes.get("security.jailbreak_flag") for s in spans):
            return True
        
        # Rule 6: VIP user → 100% keep
        if any(s.attributes.get("trace.tenant_tier") == "vip" for s in spans):
            return True
        
        # Rule 7: anomaly detected → 100% keep
        if self._anomaly_score(spans) > 0.9:
            return True
        
        # Default: random 1%
        return random.random() < 0.01
    
    def _anomaly_score(self, spans):
        """Detect anomaly based on span pattern"""
        # E.g., unusual number of LLM calls in 1 trace
        llm_calls = sum(1 for s in spans if s.name == "agent.llm.call")
        if llm_calls > 20:   # avg is 2-5
            return 0.95
        return 0.0

# 你需要保留 PII 的 hash, 让客服查询 (不暴露 PII 本身)

class PIIHasher:
    """Salted hash for correlation"""
    
    def __init__(self, salt):
        self.salt = salt
    
    def hash_pii(self, value, entity_type):
        # Per-entity-type salt
        full_salt = f"{self.salt}:{entity_type}"
        return hashlib.sha256(
            (value + full_salt).encode()
        ).hexdigest()[:16]  # 16-char prefix sufficient for correlation
    
    def correlate(self, plaintext_email):
        # 客户报问题, 给你 plaintext email
        # 你计算 hash, 在 log 里查
        h = self.hash_pii(plaintext_email, "EMAIL")
        return h

4.2 Calibration to human eval

LLM-as-judge 可能有 bias, 必须 calibrate:

class JudgeCalibration:
    """Compare LLM judge to human eval"""
    
    async def weekly_calibration(self):
        # 1. Sample 100 examples from past week
        samples = await self.sample_diverse_traces(n=100)
        
        # 2. Get LLM judge scores
        llm_scores = await asyncio.gather(*[
            self.llm_judge(s) for s in samples
        ])
        
        # 3. Get human eval (from labeling platform)
        # Show same samples to 2 human reviewers blind
        human_scores = await self.send_to_human_labelers(samples)
        # human_scores: avg of 2 reviewers per sample
        
        # 4. Compute agreement
        correlation = pearsonr(llm_scores, human_scores)
        cohen_kappa = cohen_kappa_score(
            [self.bucket(s) for s in llm_scores],
            [self.bucket(s) for s in human_scores],
        )
        
        # 5. Find systematic bias
        diffs = [l - h for l, h in zip(llm_scores, human_scores)]
        mean_diff = mean(diffs)
        
        if abs(mean_diff) > 0.1:
            # LLM judge systematically high/low
            await alert(
                f"Judge calibration off: LLM avg {mean(llm_scores):.3f}, human avg {mean(human_scores):.3f}",
                channel="ml-team",
            )
        
        # 6. Find disagreement patterns
        large_disagreement = [
            (s, l, h) for s, l, h in zip(samples, llm_scores, human_scores)
            if abs(l - h) > 0.3
        ]
        # 分析这些 case, 改 judge prompt
        
        return {
            "n": len(samples),
            "correlation": correlation.statistic,
            "kappa": cohen_kappa,
            "mean_diff": mean_diff,
            "large_disagreement_count": len(large_disagreement),
        }

class UserSignalEval:
    """Use user behavior as quality signal"""
    
    async def collect_signals(self, trace_id):
        signals = {}
        
        # 1. Thumb up/down (explicit)
        thumb = await self.get_thumb_feedback(trace_id)
        signals["explicit_thumb"] = thumb  # -1, 0, +1
        
        # 2. Copy / share (positive)
        copies = await self.get_copy_events(trace_id)
        signals["copied"] = copies > 0
        
        # 3. Regenerate click (negative)
        regen = await self.get_regen_events(trace_id)
        signals["regenerated"] = regen > 0
        
        # 4. Follow-up that contradicts (negative)
        followups = await self.get_followup_queries(trace_id)
        if followups:
            contradiction = await self.detect_contradiction(
                trace_id, followups
            )
            signals["contradicted_by_followup"] = contradiction
        
        # 5. Session abandonment (mild negative)
        next_action = await self.get_next_action(trace_id)
        signals["abandoned"] = next_action is None  # user left
        
        # 6. Time on response (engagement)
        time_spent = await self.get_dwell_time(trace_id)
        signals["dwell_seconds"] = time_spent
        
        # Aggregate to user_score (0-1)
        score = self._aggregate(signals)
        return score, signals
    
    def _aggregate(self, signals):
        score = 0.5  # neutral
        if signals["explicit_thumb"] == 1:
            score = 0.9
        elif signals["explicit_thumb"] == -1:
            score = 0.1
        elif signals["copied"]:
            score = 0.8
        elif signals["regenerated"]:
            score = 0.3
        elif signals["contradicted_by_followup"]:
            score = 0.2
        elif signals["abandoned"]:
            score = 0.4
        elif signals["dwell_seconds"] > 30:
            score = 0.7  # engaged
        return score

5.1 Standard debug runbook

Step 1: User report intake
  Customer success → ticket with:
  - User ID / email
  - Approximate time of incident
  - What user saw
  - What user expected
  - Error ID (if shown to user)

Step 2: Find trace
  If error_id (trace_id): direct lookup in Honeycomb
  Else: search by user_id + time window
  Tools: Honeycomb / Datadog APM / LangSmith
  
  Filter:
    @user.id:"u_42" AND @timestamp:[2026-05-21T14:00 TO 14:30]

Step 3: Read trace top-down
  Root span → child spans → identify slow / errored span
  
  Common patterns:
  - LLM call returned refusal (check response content)
  - Tool call failed (check tool error)
  - RAG retrieval bad (check retrieved chunks)
  - State load wrong (check conv state)

Step 4: Compare to good cases
  Find similar trace where it worked (same prompt template, similar query)
  Diff:
  - Different RAG chunks?
  - Different tool args?
  - Different prompt parameters?
  - Different model version?

Step 5: Re-run with same input
  Extract from trace:
  - User query
  - Conversation state at that time
  - Tool results (if 'replay mode')
  
  Replay tool:
  GET /admin/trace/{trace_id}/replay
  Returns: same setup, runs LLM again
  
  See if reproduces.

Step 6: If reproduces → narrow
  - Try with different model → does it persist?
  - Try with previous prompt template → does it persist?
  - Try with previous RAG corpus → does it persist?
  - Try with simplified context → minimal repro?

Step 7: Root cause classification
  Common categories:
  - Prompt template regression (recent change)
  - Model version regression (vendor side)
  - RAG corpus issue (bad chunk, wrong rerank)
  - Tool API drift (response format changed)
  - Edge case in user input (unusual phrasing)
  - LLM hallucination (no signal, just bad luck)
  - Cache stale (showing old answer)

Step 8: Fix + verify
  - Hot fix (if regression): revert
  - Add eval case to suite (prevent recurrence)
  - Document in post-mortem

class TraceReplayTool:
    """Replay a trace deterministically"""
    
    async def replay(self, trace_id, options):
        # Fetch trace
        trace = await self.honeycomb.get_trace(trace_id)
        
        # Extract original inputs
        original_request = self._extract_request(trace)
        original_state = await self.store.get_at_version(
            original_request.conv_id,
            timestamp=trace.start_ts,
        )
        
        # Replay options
        config = {
            "model": options.model or original_request.model,
            "prompt_template": options.prompt_version or original_request.prompt_version,
            "rag_corpus_version": options.rag_version or original_request.rag_version,
            "temperature": 0.0,  # deterministic
            "seed": original_request.seed,  # if available
            "use_mock_tool_results": options.mock_tools,
        }
        
        if options.mock_tools:
            # Use exact tool results from original trace (deterministic replay)
            mock_tool_results = self._extract_tool_results(trace)
            return await self._replay_with_mocks(
                original_request, original_state, config, mock_tool_results
            )
        else:
            # Re-execute fully
            return await self._replay_full(
                original_request, original_state, config
            )
    
    async def _replay_with_mocks(self, req, state, config, mock_results):
        # Override tool execution to return mock_results
        with mock_tool_calls(mock_results):
            return await self.agent.run(req, state, config)
    
    async def diff(self, original_trace_id, replay_result):
        original = await self.honeycomb.get_trace(original_trace_id)
        
        diff = {
            "original_response": original.response,
            "replay_response": replay_result.response,
            "response_diff": diff_text(original.response, replay_result.response),
            "original_tools_used": original.tools_used,
            "replay_tools_used": replay_result.tools_used,
            "original_eval_score": original.eval_score,
            "replay_eval_score": await self.eval.score(replay_result),
        }
        return diff

-- Find slices with anomalous quality / cost / latency
WITH baseline AS (
    SELECT
        tenant_id,
        model,
        prompt_template_version,
        AVG(latency_ms) as baseline_latency,
        AVG(eval_score) as baseline_eval,
        AVG(cost_usd) as baseline_cost
    FROM traces
    WHERE timestamp BETWEEN ts_start AND ts_baseline_end
    GROUP BY tenant_id, model, prompt_template_version
),
recent AS (
    SELECT
        tenant_id,
        model,
        prompt_template_version,
        AVG(latency_ms) as recent_latency,
        AVG(eval_score) as recent_eval,
        AVG(cost_usd) as recent_cost,
        COUNT(*) as n
    FROM traces
    WHERE timestamp > ts_recent_start
    GROUP BY tenant_id, model, prompt_template_version
)
SELECT
    r.*,
    b.baseline_latency,
    b.baseline_eval,
    b.baseline_cost,
    (r.recent_latency - b.baseline_latency) / b.baseline_latency as latency_delta_pct,
    (r.recent_eval - b.baseline_eval) as eval_delta,
    (r.recent_cost - b.baseline_cost) / b.baseline_cost as cost_delta_pct
FROM recent r
JOIN baseline b USING (tenant_id, model, prompt_template_version)
WHERE r.n > 100   -- min sample size
  AND (
    abs(latency_delta_pct) > 0.2 OR
    abs(eval_delta) > 0.1 OR
    abs(cost_delta_pct) > 0.5
  )
ORDER BY abs(eval_delta) DESC
LIMIT 20

5 follow-ups

Q1: "Trace volume — 10K QPS × full spans = expensive. Cost optimization?"

A:

  • Tail-based sampling: 1% baseline + 100% errors + 100% slow + 100% high-cost + 100% VIP
  • Span aggregation: similar spans (e.g., DB query type) merged at storage
  • Retention tiers: hot 7d full, warm 90d aggregated, cold 1y metric-only
  • Adaptive per-route: high-traffic low-value routes 0.1%, low-traffic high-value 100%
  • Vendor: Honeycomb tail-based (sample whole trace if ANY span anomalous), Datadog APM
  • Cost target: ~30x reduction vs 100% sampling

Q2: "Can't reproduce user-reported issue. What's in your trace that helps?"

A:

  • Full input + full response (PII-redacted) sampled at 10%
  • Model version + prompt template version + RAG corpus version
  • All tool calls with inputs/outputs (full)
  • LLM parameters: temperature, top_p, seed (if available)
  • Conversation state at request time (Redis snapshot)
  • Re-run script: extract inputs from trace → replay deterministic with same state + mocked tool results
  • Comparison to good case: find similar trace where it worked, diff inputs/outputs

Q3: "Eval-in-prod — who decides ground truth?"

A:

  • LLM-as-judge: Sonnet 4.6 / Opus 4.7 as judge. Multi-dim score (helpfulness, accuracy, safety, etc.). Calibrated against human eval set weekly.
  • Human labeled set: 200-500 examples curated, "gold standard". Judge accuracy measured against this.
  • User signals: thumbs up/down, copy, regenerate, follow-up correction. Aggregate to user_score.
  • Heuristic checks: response is on-topic, no refusal markers, no hallucination markers (e.g., "I don't know" + factual claim).
  • Production triangulation: LLM judge + user signal + heuristic. Disagreement triggers human review.

Q4: "Jailbreak detection — log everything for security?"

A:

  • Inline detection: pattern matching (keywords like "ignore previous") + LLM-classifier on input → flag
  • Logged: full input (in separate secure store, not main logs), trace, user_id, severity score
  • Alerting: > 10 attempts/min from same user → temp ban; > 50 / day → security review
  • Forensics retention: 7d hot, 90d cold, separate from regular logs (compliance: need ability to fully delete on RTBF)
  • Honeypot: inject 'secrets' to detect successful exfiltration, alert if leaked
  • Pattern library: maintain known jailbreak patterns, update weekly

Q5: "Cost observability — how attribute to features?"

A:

  • Tag each span with feature_id (which product feature triggered this LLM call)
  • Tag with tenant_id, user_id, model
  • Cost per span: input_tokens × input_price + output_tokens × output_price
  • Per-feature dashboard: sum costs by feature_id, time-series
  • Per-tenant attribution: sum costs by tenant_id
  • Daily cost report: top 10 expensive features, week-over-week trend
  • Identify expensive features for: optimization, pricing decision, deprecation

Q6 (bonus): "If you could only have 3 metrics for an LLM agent, which?"

A:

  1. Eval pass rate (sampled 5%, LLM-judge multi-dim). Without this you're blind to quality drift.
  2. TTFT p99 (per model, per tenant). Latency is user-perceived quality.
  3. Cost per user per day (per feature). Without this, runaway customer can burn budget overnight.

Honorable mention: jailbreak attempts/min, cache hit rate, tool error rate.

LLM agent observability = 4 layers (trace OTel + LLM-specific log PII-redacted + metric Prometheus + quality eval-in-prod) + smart sampling (tail-based) + drift detection + debug workflow (trace_id → slice → re-run → root cause).

传统 web observability 不够 — LLM-specific signals (TTFT, token cost, prompt/model/RAG version, jailbreak, hallucination) 必须专门 instrument. 5% LLM-judge eval-in-prod 是 2026 LLM platform 标配, 不做就是盲飞.

Cheat Sheet (印 1 页)

4 observability layers:
  L1 Distributed Traces  (OTel + Honeycomb / Datadog / Tempo)
  L2 LLM-specific Logs   (prompt/response PII-redacted, tokens, cost, version)
  L3 Metrics             (Prometheus / Mimir, latency / cost / error / cache)
  L4 Quality monitoring  (LangSmith / Phoenix, eval-in-prod 5%, drift)

Span attributes (LLM-specific):
  llm.model
  llm.prompt_template_version
  llm.prompt_hash
  llm.input_tokens (+ cached_input_tokens)
  llm.output_tokens
  llm.cost_usd
  llm.ttft_ms / total_ms
  llm.finish_reason
  llm.refused
  tools.used
  cache.prefix_hit_ratio
  quality.eval_score (populated async)
  security.jailbreak_flag

Key LLM metrics:
  TTFT / TPOT p50/p95/p99
  Input/output tokens (cached vs not)
  Cost per (tenant, feature, model)
  Cache hit rate per tier
  Tool call success rate
  Eval pass rate (sampled)
  Jailbreak attempts / min
  User thumbs ratio

Sampling strategy (10K QPS):
  Tail-based:
    1% random baseline
    100% errors
    100% slow (>5s)
    100% high cost (>$0.5)
    100% VIP tenant
    100% jailbreak flagged
  Cost: ~30x reduction vs 100%

PII redaction:
  Presidio (spaCy NER + custom recognizers)
  Apply at log-write time
  Entities: PERSON / EMAIL / PHONE / CREDIT_CARD / SSN / LOCATION
  Hash for correlation (sha256 + per-type salt)
  Right-to-be-Forgotten via hash deletion

Eval-in-prod:
  5% random sample + force-eval flagged
  LLM-as-judge (Sonnet 4.6)
  Multi-dim: helpfulness / accuracy / tool / safety / refusal / conciseness
  Calibrate vs human weekly
  Alert on eval drop > 5pp

Drift detection (daily):
  MMD test on prompt embeddings
  Eval score baseline vs recent
  Cost mean baseline vs recent
  Tool error rate baseline vs recent

Alerting tiers:
  P0 PagerDuty: p99 > SLO 5min, error > 2%, jailbreak > 100/min, eval drop > 5pp
  P1 Slack ML: eval < 90% 1h, cost trend up 50%, drift detected
  P2 Email weekly: model mix shift, usage trend

Debug workflow:
  Trace_id from user report → find trace
  Read trace top-down → identify failed span
  Compare to good case (same template, similar query)
  Re-run with replay tool (deterministic mocks)
  Slice analysis (by tenant / model / template / time)
  Root cause: prompt / tool / model / RAG / input / cache stale

Tools 2026:
  OpenTelemetry (vendor-neutral SDK)
  Datadog / Honeycomb / Tempo (trace + log + metric)
  LangSmith / Phoenix / Langfuse (LLM-specific)
  Braintrust (eval suite)
  Presidio / AWS Macie (PII redaction)
  Mimir (Prometheus-compatible TS)

Cost attribution:
  Per-span tag: feature_id, tenant_id, model
  Aggregate: per-feature dashboard, per-tenant report
  Catch: feature with bad prompt → 100x token spike

Per-tenant SLA:
  Dashboard: availability, p99, eval pass
  Synthetic probes 1/min
  SLO error budget tracking
  Monthly auto-report to customer
  Credit policy for breach

红线:
  - Raw PII in logs
  - 100% sample everything (cost)
  - No LLM eval (quality blind)
  - No tool spans (debug stuck)
  - Single pillar
  - No alerting
  - Trace context not propagated
  - No version tracking
  - No cost attribution
  - No PII deletion workflow
