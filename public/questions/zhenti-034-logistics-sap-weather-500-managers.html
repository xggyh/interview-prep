Q34 · 物流公司自动重路由 Agent (SAP + 天气 + 500 仓库经理)

"A large logistics company wants to build an AI agent that can automatically re-route shipments based on SAP data, weather API, and input from 500 warehouse managers. Design the end-to-end architecture. You have 60 minutes."

Round: Decomposition Case (60 min) 出处: Exponent 2026 FDE · Palantir Foundry-style + OpenAI Enterprise Agents 行业: Logistics / supply chain

📖 术语速查 (本题用到的)

物流 / SAP / agent / 工会词都在这. 5 min 看完后面跟得上.

物流 / 供应链行业

术语解释
Re-route (重路由)临时改变 shipment 的路径 / 时间 / 车辆 — 因为 weather / 设备坏 / 仓库爆仓 / 客户改单. 这题的核心动作.
Carrier承运商 — FedEx, UPS, 自营车队等. 一个 shipment 走哪个 carrier 是 routing 决策之一.
Hub / hub overflow中转仓库 + 爆仓 — hub 同时来太多 shipments 处理不过来. 触发 re-route 之一.
Lane物流术语 — 一对 origin-destination 之间的路线. "LA → Chicago lane" 是一条 lane.
SLA (Service Level Agreement) ⭐合同里承诺的服务水平 — 比如 "next-day delivery". 违 SLA = 罚款 + customer churn. Hard constraint.
Hazmat (Hazardous Materials)危险品运输 — 有严格法规 (DOT, FMCSA), 哪种车能装哪种 hazmat 是 hard constraint. 路由错 = $50K+ + 监管处罚.
HOS (Hours of Service) ⭐驾驶员服务时长法规 — FMCSA 规定司机每天 / 每周最多开多久, 必须休息多久. 违规 = 公司被审计. Hard constraint.
FMCSA (Federal Motor Carrier Safety Administration)美国交通部下属 — 监管商业卡车. HOS 是它管的.
Teamsters (国际卡车司机工会) ⭐美国最大物流工会 — 在 30% 美国物流公司有合同, 限制 algorithmic dispatch 必须 driver opt-in. 这题最大政治风险.
Dispatcher / Central Dispatch调度员 / 中央调度 — 这题 5 人小团队负责 regional 重路由决策. 不是替换对象, 是 co-designer.
Warehouse manager仓库经理 — 本地决策 + 提供 local context (dock 坏了 / 当地天气等). 这题 500 人, 个体 tenure 差异大.

SAP / 系统集成

术语解释
SAP德国 ERP 巨头 — 大企业必备. 物流公司用 SAP 各种模块.
SAP TM (Transportation Management) ⭐SAP 的运输管理模块 — 这题主集成对象, schema 复杂 100+ 字段, 每个客户的 customization 不同, 80% 集成成本在 mapping 客户特定字段.
SAP EWM (Extended Warehouse Management)SAP 仓库管理模块 — dock 状态 + 库容数据来源.
IDocSAP 的标准数据交换格式 — 跟 SAP 系统 write/read 走 IDoc. 这题 SAP 写回路由必走 IDoc.
BAPISAP 业务接口 — 类似 API, 比 IDoc 更结构化.
Telematics车联网数据 — 车的实时位置 / 速度 / 状态. 厂商: Lytx, Samsara, 各区域不同.
DVR (Driver Vehicle Recorder)车载记录仪 — 司机分配 + HOS 数据来源.

数据 / 信号源

术语解释
NOAA美国国家海洋大气管理局 — 免费 + 权威天气 API.
INRIX / Google Maps API商业实时交通数据 SaaS.
CRM (Customer Relationship Management)客户管理系统 — Salesforce 之类. 这题客户偏好数据在 CRM.
Manager-input local context仓库经理输入的本地信息 ("dock 4 broken until Tuesday") — 目前没有任何系统记录这个, 在 email + Slack + 经理脑子里. 这题需要新建结构化输入 app.

Agent / AI 部署模式

术语解释
Autonomous agent全自动 agent — 自己决策 + 执行, 不需要人. 这题第一坑就是冲去 build 这个.
Trust ladder (信任阶梯) ⭐渐进部署模式: shadow → recommend → opt-in autonomy → full autonomous. 这题核心方法论.
Shadow modeAI 跟人并跑, AI 决策不生效只记录. 12 周最少.
Recommend modeAI 推荐, 人审批 + 执行. Override rate 是关键指标.
Opt-in autonomy仅 low-risk 场景 (e.g. 区域内天气) AI 自动决策, 但 5 min 内可被 override.
Per-manager calibration不同 manager 不同信任阈值 — veteran (10+ yr) 可给更高 autonomy, junior 必须保守.
Hard constraint vs soft preference ⭐Hard = 法规 / 合同 (HOS / hazmat / SLA), 必须确定性规则引擎. Soft = 客户偏好 / 成本, 可 ML. 混在一起 = 灾难.
LangGraph / Multi-agentLLM 编排框架 — 候选人冲这个第一坑.
Tool useLLM 调用外部工具 (查 SAP / 写 IDoc 等).
Kill switch一键禁用 AI 回 manual mode. < 60s 触发. Safety-critical 必备.

角色 / 政治

术语解释
COOChief Operating Officer — 这题 sponsor.
VP Ops运营副总 — owns daily risk.
CIOChief Information Officer — 管 SAP 集成成本.
CISOChief Information Security Officer — 管数据安全.
Driver union rep ⭐工会代表 — unionized 区域 veto holder, 必 week 1 engage.
Champion / Skeptic / Fence-sitter用户态度三分: 10% 拥护者, 70% 观望, 20% 怀疑. 先攻 champion.

这道题在考什么

不是: 考你能不能 design 一个 multi-agent system.

是: 考你能不能克制冲动不 build autonomous agent from day 1, 而是用 shadow → recommend → auto-with-override → autonomous 的渐进 trust ladder.

4 个 signal:

  1. Don't build autonomous agent from day 1 — 90% 候选人冲去讲 LangGraph / multi-agent / tool use. 真实部署是 shadow mode 12 周 + opt-in 12 周 + 渐进 autonomy
  2. 500 managers are users, not data sources — 候选人把 "500 manager input" 当训练数据. 实际他们是 决策权持有者, agent 要赢得他们信任, 不是 fit 他们历史
  3. Define trust thresholds explicitly — 哪个时机系统可 auto-decide vs 必须 ask manager? 哪些 case 永远 ask?
  4. Per-manager calibration matters — 一个 manager 是 10-yr veteran, 另一个是 6-month junior. Agent's confidence threshold per manager 不同

❌ 最常见的挂法

挂法 #1: 立刻 build autonomous multi-agent system

"I'd use LangGraph with a planner agent, weather agent, SAP agent, routing agent, with tool use to talk to the warehouse system..."

死. 你没问:

  • 当前重路由谁做? (Dispatcher / manager / 自动?)
  • 重路由的决策约束 (合同 SLA / 客户偏好 / hazmat 限制 / 货车类型) 是什么?
  • 错误的代价 — 路由错一次 = $X loss + customer churn risk?
  • 500 个 manager 各自的 trust level?
  • 工会 / 司机协议是否限制 algorithmic dispatch?

挂法 #2: 把 manager 当数据源

"We'd ingest manager inputs as training data and have the agent learn their patterns."

死. Manager 们正在做决策. 你 ingest 他们 = 把活的决策者当死数据. 反应: managers 不输入了, 因为他们觉得自己在 train replace themselves.

挂法 #3: 一步到 fully autonomous

"Phase 1 we'll launch shadow mode for 2 weeks, then go autonomous in week 3."

死. 仓库 manager + dispatcher + 司机的 trust takes months, 不是 weeks. 跳级 = silent sabotage (managers ignore agent, agent gets stale).

完美答案架构 (5 步)

Step 1: 澄清问题 (10 min)

"Before I sketch, 10 questions. The architecture depends on what 'auto-route' actually means — degree of autonomy is THE design decision."

10 个 clarifying questions:

Q1: "What's the scope of re-routing — change carrier? Change route within a carrier? Reschedule pickup/delivery? Re-stage in a different warehouse? Different decisions have different stakeholders + risks."

Q2: "Who decides today — dispatcher? Warehouse manager? Central operations? Customer service when problem reported? The current decision-maker is the agent's primary stakeholder."

Q3: "What's the error cost — wrong route = how much $? Mis-routed shipment = customer claim? Late delivery = SLA penalty? This dictates how conservative we must be."

Q4: "What's the trigger for re-routing — weather event, equipment failure, customer change, hub overflow? Different triggers have different urgency + data."

Q5: "What's the decision constraint set — contract SLA, customer preferences (some refuse certain carriers), hazmat restrictions, driver hours of service (HOS regulation), vehicle capabilities? These are hard constraints."

Q6: "What's the role of 500 warehouse managers — they input ad-hoc info ('dock 4 broken'), they approve agent recommendations, they override agent decisions, they request re-routes? Different roles imply different UX."

Q7: "Are there union / driver protocols limiting algorithmic dispatch? (Some US Teamsters contracts restrict algorithmic re-routing without driver concurrence.)"

Q8: "What's the integration with SAP — read access to TM / EM modules? Write access to update routes? Custom IDocs? This is THE integration pain."

Q9: "What's the scale + latency — N shipments / day, peak QPS, real-time decision required vs daily batch? Different operating modes."

Q10: "Stakeholder map: COO? CIO? VP of Ops? Each region's Operations Director? Driver union rep? 500 managers themselves? Veto holders?"

面试官 likely 回答:

  • Re-routing scope: change route within carrier + reschedule pickup, NOT change carrier
  • Current decisioning: central dispatch (5-person team) handles regional, warehouse manager handles local
  • Error cost: avg $300 per mis-route + customer trust impact. Catastrophic mis-routes (hazmat) = $50K+
  • Triggers: weather (60%), equipment failure (20%), hub overflow (15%), customer change (5%)
  • Constraints: SLA (next-day, 2-day), customer "no overnight near my building", hazmat compatibility, driver HOS, vehicle type
  • Manager role: input local info (dock broken, weather impact local), approve agent suggestion (initially), eventually monitor agent
  • Union: Teamsters contract in 30% of regions restricts auto-dispatch without driver opt-in
  • SAP: read TM (Transportation Mgmt), write back through IDoc framework. Notoriously painful integration
  • Scale: 50K shipments/day, peak 6K/hr, target 5-minute decision latency
  • Veto: COO + VP Ops + Driver Union rep (in unionized regions)

→ Real scope: in 90 days, build an agent that recommends re-routes for weather + hub overflow triggers, with shadow → recommend → opt-in autonomy trust ladder. NOT fully autonomous in 90 days.

Layer 1 — Operational KPIs (VP Ops daily view):

  • % of shipments on-time (target: maintain or improve current baseline)

  • Decision latency (current ~30 min for weather event, target < 5 min)
  • Manager satisfaction (NPS, quarterly)

Layer 2 — Trust KPIs (process metrics):

  • Agent recommendation acceptance rate by central dispatch (target 60-80%, NOT > 95% which means rubber stamp)
  • Override rate by warehouse managers (target 20-40%)

  • Time to detect bad recommendation

  • Total logistics cost trend
  • Customer SLA breach rate
  • Driver retention rate (don't break it!)

  • Hazmat mis-routes (must be 0)
  • Union grievances filed
  • Manager complaints ("agent overrides me, doesn't listen")
  • Driver complaints (HOS violation, unreasonable schedule)

The framing:

"90 days is NOT 'fully autonomous re-routing across the network'. It's 'weather + hub-overflow triggered recommendations for the central dispatch team to approve, with a clear ladder to expand to opt-in autonomy in month 6-12'."

Key gaps + dirty data fights:

  1. Manager local context is critical but ad-hoc: "dock 4 broken until Tuesday" — no structured field for this. Currently lives in email + Slack + manager memory. Need a structured input app.
  2. SAP TM schema is the deep end: each customer's SAP TM customization is different. 80% of integration cost is mapping their specific implementation.

Walking-skeleton has ZERO autonomy in v1. It's a passive observer + logger. Builds trust by:

  • Central dispatch sees AI's reasoning daily without risk
  • Compare to what they would do, comment on disagreements
  • Union rep sees agent's reasoning, understands logic

Phase 2 (Week 5-12) — Shadow Mode:

  • Agent shadows real-time decisions
  • Dispatcher still controls
  • Weekly retro on agreement rate + outcome

Success criteria to graduate to phase 3:

  • Agreement rate with dispatcher > 70%
  • For disagreements, AI's predicted outcome (cost, on-time) matches actual within 10%
  • 0 hazmat / HOS violations in shadow recommendations
  • Union rep signs off on shadow log review

Phase 3 (Month 4-6) — Recommend Mode:

  • Central dispatch sees AI recommendation in UI
  • Dispatcher approves / overrides
  • Override rate target 20-40%

Phase 4 (Month 7-12) — Opt-in Autonomy with Manager Override:

  • For low-risk re-routes (within-region weather, hub overflow only, NO hazmat, NO HOS-tight), agent acts automatically
  • Manager + dispatcher can override within 5-min window
  • Union regions still require driver opt-in

Phase 5 (Year 2) — Tiered Autonomy:

  • Per-manager autonomy levels based on track record
  • Veteran managers' regions = more autonomy
  • Junior managers' regions = manual default

Gao Xin 简历专属 reframe

"I shipped exactly this trust ladder pattern at TikTok PayLater. The voice agent for debt collection started in shadow mode (recommends what to say to customer, human collector still spoke), then recommend mode (human picked from agent's suggestions), then opt-in autonomous (agent talks to specific tiers of accounts, human can break in), then autonomous with override for the safest segments.

It took 9 months from shadow to first autonomous segment, and that was for a use case much less consequential than mis-routing shipments. Logistics with HOS regulation + union veto + customer SLA is MORE conservative than I was, not less.

Specific transferable lessons:

  1. Shadow mode log review with the humans you're 'augmenting': in PayLater, I sat with collectors every Friday and reviewed disagreements between agent's suggested response and what they actually said. They taught me what the agent was missing. In logistics: weekly retro with central dispatch reviewing disagreement cases.
  1. Per-segment autonomy graduation: not all accounts get same autonomy. Veteran customers, simple repayment patterns → more agent autonomy. Disputed / multi-party / law-mentioned accounts → human always. For logistics: per-region (unionized vs not), per-trigger (weather low risk vs equipment failure higher), per-shipment (hazmat = never autonomous).
  1. Hard constraints are deterministic, soft preferences are ML: in PayLater, regulator-mandated disclosure text was a hard-coded string (no ML). Empathy + persuasion was LLM-generated. We never mixed them. In logistics: HOS / hazmat / SLA = rule engine. Customer 'no overnight near building' = learned.
  1. The first 4 weeks is about trust-building infrastructure, not value: in PayLater, weeks 1-4 we shipped audit log + replay tool + Slack-bot dashboard for collectors to see agent's reasoning. ZERO model improvement in 4 weeks. By week 5 we had trust to ship the real thing.

The pattern: infrastructure for trust ships before product for value."

5 个 Follow-ups

Q1: "Why not just build fully autonomous from day 1 with a high confidence threshold?"

A: 3 reasons it fails:

  1. Confidence is not calibrated on day 1. You don't know what "0.9 confidence" actually means until you've measured against ground truth on YOUR data. Shadow mode is how you measure.
  2. Edge cases are 80% of the value. Easy cases agent handles fine. The cases that matter (driver near HOS limit, customer-mentioned-law account, unusual weather) need human judgment until model is trained on enough of them.
  3. Union + regulatory exposure. Even if model were perfect, deploying autonomous without union opt-in = grievance + work stoppage in unionized regions. Even one HOS violation = FMCSA audit.

The cost of going-too-fast is much higher than the cost of phased rollout. Phased is the optimal path, not the safe path.

Q2: "How do you get 500 warehouse managers to actually input local context?"

A: This is the UX challenge. Approach:

  • Make input dead-simple: Slack bot or mobile app, structured but quick ("dock 4 broken, expected back Tuesday")
  • Show value to them: their input shows up as a tag on affected shipments, agent recommends differently. They see "my input changed the route" — that's the carrot.
  • Segment managers by attitude:
  • Champions (~10%): power users, give them advanced features, name them in launch readme
  • Fence-sitters (~70%): need to see colleagues use it, show stats "your team's average usage"
  • Skeptics (~20%): don't fight them, but track and engage personally
  • Don't penalize non-input: if a manager doesn't input, agent operates as if no context — that's fine. We're not making it mandatory.
  • Quarterly review: present "input → outcome" stories at all-hands. Managers see their input matters.

Q3: "Driver union rep refuses to allow shadow mode even, says any algorithmic logging is grievance-worthy."

A: Different from "no autonomy" stance. Need to diagnose:

  • Is the concern about individual driver tracking? If yes, ensure logging is at shipment level not driver level. Aggregate by region not individual.
  • Is the concern about discipline based on log? Commit in writing: logs cannot be used in disciplinary actions against drivers.
  • Is the concern about job security? Commit to no force reductions tied to project. Co-sign by COO.
  • If still no: project doesn't proceed in unionized regions. Stay in non-unionized regions for v1, demonstrate value, revisit union with data.

Walking away from 30% of regions is acceptable in v1. Forcing it = company-wide work stoppage risk.

Q4: "What if SAP integration is too painful and adds 30 days to v1 timeline?"

A: Reverse scope. 2 options:

Option A: ship MVP with read-only SAP (just consume shipment data). Recommendations are logged + emailed to central dispatch. Dispatcher manually executes in SAP. This avoids write-back integration but reduces value.

Option B: ship MVP for single SAP region (1 customer's installation of SAP TM, not their global system). Validate architecture, then expand to other regions in phase 2.

My recommendation: Option A for proving model + Option B for proving write-back. Combine: read-only globally, write-back in 1 pilot region.

This is the scope reduction is FDE core skill moment. Customer wants global write-back day 1 — they're wrong about the cost.

Q5: "How does this scale to 50K shipments / day at peak 6K / hr?"

A: Latency targets:

  • Trigger detection: 1-min loop
  • Affected shipment query: < 10s
  • Re-route scoring per shipment: < 1s (rule-based scoring is cheap)
  • Manager notification: real-time push

Scaling:

  • Trigger detection runs as background job, not per-shipment
  • Shipment scoring is embarrassingly parallel: 6K/hr = 1.7/sec, trivial
  • Bottleneck is SAP TM API rate limits (typically 100-500 IDoc/min, vendor-specific)

Architecture for scale:

  • Trigger detector → SQS / Kafka queue
  • Scoring workers (horizontal scale, 5-20 workers)
  • SAP write rate-limited with backoff
  • Per-manager alert deduped (don't spam manager with 50 alerts for same weather event)

This is system design within the FDE answer, not the main exam. Mention it briefly, deep-dive if asked.
