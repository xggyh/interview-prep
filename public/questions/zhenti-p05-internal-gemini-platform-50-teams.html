Q-P5 · 内部 Google FDE — 给 50 个产品团队建 Gemini 统一平台

"You're an internal Google FDE supporting product teams. 50 product teams at Google (Maps, Photos, Workspace, Search, Cloud, Pixel, etc.) are using the Gemini API in their products. Three problems are growing: (1) cost is growing 20% month-over-month with no visibility into why, (2) prompt quality varies wildly — some teams have great prompts, some are spending tokens on bad ones, (3) there's no central observability — when Gemini has an issue, teams find out from customer complaints. Design the platform / governance layer to standardize Gemini usage across these 50 teams. 6-month plan."

中文翻译:

"你是 Google 内部 FDE, 支持产品团队. Google 内部 50 个产品团队 (Maps / Photos / Workspace / Search / Cloud / Pixel 等) 都在自己产品里用 Gemini API. 现在三个问题在恶化:

(1) 成本月环比涨 20%, 没人知道为啥; (2) prompt 质量天差地别 — 有的团队 prompt 写得超棒, 有的把 token 砸在烂 prompt 上; (3) 没有中心化的可观测性 — Gemini 出问题, 团队是从用户投诉里知道的.

设计平台层 / 治理层, 统一这 50 个团队的 Gemini 用法. 6 个月计划."

Round: Platform Design + Org Strategy (60 min) 出处: 🔮 预测题 — 针对 Google FDE 主场 (internal platform team 是 Google FDE 经典场景) 行业 / 约束: Internal platform / 50 teams / governance vs autonomy / 6 个月 / paved road model / no mandate authority / 20% MoM cost growth / observability gap

📖 术语速查 (本题用到的)

这题里的平台 / governance / 观测词如果不懂, 后面架构图听不下去. 这张表 5 min 看完.

平台团队 / 组织模式 ⭐ 这题的关键

术语解释
Internal platform team ⭐内部平台团队. 服务的客户是公司内部其他工程团队, 不是外部客户. Google 经典模式 — Search infra / Maps infra / Cloud Spanner platform 都是.
Paved road (铺好的路) ⭐平台团队最重要的概念. 提供一条"已铺好的路"让用户走更快更容易, 但不强制. 如果他们选 off-road 也行 (自负盈亏). Google / Netflix / Facebook 都用这模式.
Golden path ⭐铺好的路的具体实现 — 一套标准 SDK + 模板 + 文档让团队 5 min 上手. 关键是 比裸调 raw API 更容易, 不是更难.
Mandate (强推)强制要求所有团队必须用平台. 这是 paved road 的反面 — Google 文化里通常失败 (除非高管层强烈背书 + 有意义的 enforcement).
Build vs adopt (建 vs 推广) ⭐平台团队 anti-pattern: 投 6 个月闭门造车, 上线发现没人用. 正确做法: 早期 MVP 给 2-3 个 lighthouse 团队验证, 再 scale.
Lighthouse team (灯塔团队) ⭐第一批 early adopter, 通常是高 visibility 团队 (Search / Maps). 他们用了, 别的团队跟着用.
Anti-pattern: build big then mandate反模式 — 闭门造一个庞然大物然后强推. Google 文化下 100% 失败.
Customer Engineer (CE) / FDE在内部场景, FDE = 帮内部团队上手 + 解决 deep technical issue 的人. 不只是 docs / sample code.
Office Hours / AMAs (Ask Me Anything)平台团队的 outreach 形式. 每周 1-2 小时开放 Q&A. 比 documentation 更 effective.
Internal Slack channelGoogle 内部叫 chat space. 平台团队的"前台". 反映出用户痛点比 GitHub issue 快.

Gemini / LLM 平台架构

术语解释
SDK / wrapper ⭐平台提供的 client library. 用户 import 这个而不是 raw Gemini API. 自动注入 telemetry / cost tagging / retry / cache.
API gateway网关层. 所有 Gemini call 经过它, 加 auth / rate limit / observability.
Service mesh (gRPC / Stubby)Google 内部用 Stubby (gRPC 前身). 服务间通信 mesh 自带 tracing.
Per-team cost tagging ⭐每个 API call 打 team_id / project_id / use_case tag, 写入 BigQuery, 可分摊到具体团队 / project. 没这个, cost 涨 20% MoM 永远查不清谁的锅.
Quota management配额管理. 防止单个团队失控烧光全公司 quota. Per-team token budget + 月预算.
Token budgetToken 预算. 给每个团队 / project 月级别 token 上限, 超了告警 / 限速 / hard cap.
Cache layer缓存层. 相同 prompt 直接命中. 命中率 20-40% 时省钱 + 加速.
Prompt registry ⭐Prompt 中心化仓库. 每个 prompt 有 owner / version / eval results / used-by teams. Git-backed 最 sane.
Prompt versioningPrompt 版本管理. v1.0 / v1.1 / v2.0. 不带版本号 = 改了 prompt 别人不知道.
Prompt eval pipelinePrompt 自动评估流水线. 改 prompt → run on golden set → compare metrics → approve/reject.
Shadow mode新 prompt / 新 model 并行跑, response 不返回用户, 只 log. 评估真实流量上的差异.
Cascade / model routing模型级联. Cheap model (Flash) 先答, 不行升级 Pro. 降本利器.

观测 / OpenTelemetry GenAI

术语解释
OpenTelemetry (OTel) ⭐开源 observability 标准. Trace / metric / log 统一格式. Google Cloud 原生支持.
OTel GenAI conventions ⭐OTel 2025 出的 GenAI 专用 trace schema — gen_ai.system, gen_ai.request.model, gen_ai.usage.input_tokens 等. 标准化 LLM observability.
Trace / span一个 request 的完整链路 (trace) + 单一操作 (span). LLM 调用是一个 span.
Per-team dashboard每个团队一个 Looker / Looker Studio 仪表盘, 显示自己的 cost / latency / error rate / quality metrics.
Anomaly detection异常检测. Cost / latency / quality 突变 → 自动告警.
Alert / paging告警 + 寻呼. 严重问题 page on-call. Google 内部用 SRE 模式.
SLI / SLO / SLAService Level Indicator (实际指标) / Objective (内部目标) / Agreement (对外承诺).
Error budget错误预算. SLO 99.9% = 0.1% 错误预算. 烧完了停发布. SRE 经典.
Cardinality explosion高基数爆炸. 给每个 user_id 打 tag → 标签数无限 → 监控系统挂. 设计 tag schema 时要小心.

Cost / FinOps

术语解释
Cost attribution ⭐成本归属. 把 $X 总账单分摊到具体 team / project / use_case. Cloud FinOps 核心.
Showback / chargebackShowback = 显示成本但不真扣钱 (内部 awareness); Chargeback = 真的从团队预算扣. 后者更有约束力.
Pareto (80/20) ⭐帕累托原则. 80% cost 来自 20% 团队. 这题第一步: 找 top 5 cost team, 优化它们 = 解决 80% 问题.
Cost per query / per user / per session单位成本. 总 cost 没意义, 单位成本是 actionable.
Unit economics单位经济. Cost per user vs revenue per user. 内部产品也要算.
Forecast预测. 基于当前增速预测 6 / 12 月 cost. 用于 capacity planning.

术语解释
Critical User Journey (CUJ)Google 内部术语 — 用户的关键路径. Maps 的 CUJ = 搜索地点 → 导航. Gemini call 通常嵌在某个 CUJ 里.

这道题在考什么

不是: 考你能不能 architect 一个 LLM gateway.

是: 考你能不能在 50 个团队跨 5+ org + 无 mandate authority + 6 个月 deadline + cost 失控 真实约束下做 平台团队的核心 trade-off — adoption vs control.

5 个 signal:

  1. Diagnose first, build second (先诊断, 后建) — 不要冲架构. 先做 1-2 周 audit: top 5 cost team 是谁? top 5 worst prompt 是哪些? 这才能决定 paved road 的形状.
  1. Paved road, not mandate (铺路而非强推) — Google 文化下 mandate 失败. 平台必须 比裸调 Gemini API 更容易. Wins by being easier, not by being required. 这是 staff-level platform thinker 的标志.
  1. Anti-pattern: build big then mandate — 闭门造一个庞然大物然后强推. 候选人 50% 会这么答, 立刻挂. 正确答案: 2 周 MVP + 2 个 lighthouse team + iterate.
  1. Adoption is the metric, not architecture — 6 个月成功 = 30+/50 团队用了平台, 不是 "我们造了世界上最好的 LLM gateway". 平台没人用 = 失败.
  1. Resume hook gold mine — Gao Xin 的 Internal Agent Platform at TikTok 是这题的直接 analog. 必须开口 5 分钟内 mention.

❌ 最常见的挂法

挂法 #1: 立刻冲 architecture, 6 个月闭门造 LLM gateway (闭门造车然后强推)

"I'd design a comprehensive LLM gateway with prompt versioning, cost attribution, observability, caching, A/B testing infrastructure. After 5 months of build, we'd mandate all 50 teams to migrate by month 6."

死. 这是 Google platform team 教科书级反模式:

  • 5 个月闭门造, 没人 review 你的设计
  • 第 6 个月 launch, 团队抵抗 ("我们的用例你没考虑")
  • VP 不会强推 (跨 5 个 org 没人有权)
  • 一年后 5/50 团队"在用", 平台 die, FDE 走人

挂法 #2: "我会 mandate 所有团队用我的 platform" (假设有 mandate 权力)

"I'll mandate all 50 teams to migrate by Q2."

死. 你没问:

  • 你的 platform team 在 org chart 哪里? VP 级背书吗?
  • 50 个团队跨几个 org? 每个 org VP 都 buy in 吗?
  • 团队不用平台的 penalty 是什么? (Google 文化通常没)
  • 平台没 ready 之前强推, 团队怎么活?

挂法 #3: 不做 diagnose, 直接 design 庞大架构

"Here's my 6-month plan: month 1 design, month 2-5 build, month 6 launch."

死. 你不知道:

  • top 5 cost team 是谁? (Pareto 80/20, 5 团队 = 80% cost, 解决它们 = 解决主要问题)
  • top 5 worst prompt 是哪些? 怎么烂法?
  • 现有团队各自怎么调 Gemini? (SDK? Direct HTTP? Vertex AI? AI Studio?) 不知道 baseline 没法设计 paved road.

挂法 #4: 把 platform 当产品做, 但忽略 customer development

"I'd talk to teams every quarter via surveys."

死. 平台的客户是工程师, 你必须 像 PM 一样做 user research: shadow 他们一天看怎么用, 每周 office hours, 主动找 top 5 cost team 喝咖啡. 季度调查 = 平台团队失败的早期信号.

挂法 #5: 忽略 governance vs autonomy 的 trade-off

"Everything goes through the gateway."

死. 50 个团队里, Search 和 Maps 是核心 product, 他们 latency 要求 50ms p99. 你的 gateway 加 20ms latency = 他们 opt-out. 必须 layered approach: 核心团队可以直连 Gemini API 但接 SDK 拿 telemetry, 一般团队全走 gateway.

"The critical one upfront: what's our authority — paved road or mandate? It changes everything."

G — Goal (→ feeds Decompose Step 1: KPI lock)

Q1: "When leadership says 'standardize Gemini usage', is the goal (a) save cost (the 20% MoM growth is the bleeding), (b) lift quality (some teams have great prompts, raise the floor), (c) avoid incidents (centralize observability), (d) enable new capabilities (e.g. shared prompt library, model routing), or (e) all of the above ranked by...? Each scenario changes the 6-month priority."

Q2: "What does success at month 6 look like? Is it (a) X% of teams using the platform, (b) Y% cost reduction, (c) Z incidents prevented, or (d) leadership-credible 'we have a unified Gemini story'? Concrete success metric drives plan."

这层 → 解锁 Decompose Step 1: 答完 G 问题, 你就知道 KPI 是什么 (e.g., 30/50 teams on SDK + 15% cost reduction on adopters + per-team observability live + 0 platform-caused incidents), 后面 5 步的所有决策按这个 KPI 优化 — 也决定 cost-attribution-first vs prompt-library-first 的顺序.

O — Owner (→ feeds Decompose Step 2: Stakeholder map)

Q3: "What's the org structure of my platform team? Reports to whom? VP-level backing? How many engineers? Most importantly: do we have mandate authority across these 50 teams (cross 5+ orgs), or paved-road authority only? This changes the entire approach."

Q4: "Who are the highest-cost / highest-visibility teams I should partner with first? Maps and Search are usually anchor lighthouse teams. But which 5 teams want to talk to me? — those are my Wave 1. And: any teams politically off-limits (e.g. Search runs own infra, won't adopt)? Define out-of-scope upfront."

这层 → 解锁 Step 2: 答完 O 问题, 你画出 stakeholder map (sponsor = AI Infra VP / champion = top-5 willing teams / blocker = Search-style off-limits orgs / SME = Workspace prompt-eval team / user = 50 team eng leads) — 知道哪 5 个 Wave-1, 哪 10-15 个 Wave-2, 哪几个永远不进 scope.

D — Data (→ feeds Step 3: 数据 inventory)

Q5: "Cost data granularity: do we currently know cost per team? Per app? Per use case? If billing is bulk 'Gemini bill = $5M/month', I need to add cost attribution as month 1 work before anything else. If we already have team-level granularity, I skip to optimization."

Q6: "Quality data + existing surfaces: any team has eval pipelines and golden sets I can learn from? Some lighthouse teams (Workspace, Search) probably already do this well — I want to steal their patterns as platform default. And: what surfaces are teams using today — direct API, Vertex SDK, AI Studio, internal wrappers? 50 surfaces = discoverability problem before architecture."

这层 → 解锁 Step 3: 答完 D 问题, 你能画 inventory 表 (50 teams × current surface × $/month × eval maturity × prompt-library readiness × politically-onboardable) — 用这张表直接做 Wave 1/2/3 rollout matrix.

D — Deadline (→ feeds Step 4: 子问题排序)

Q7: "Why 6 months specifically? Is it (a) cost growth crisis (20% MoM compounding = $5M → $15M in 6 months), (b) incident that triggered leadership attention, (c) budget cycle (need to lock platform funding for next FY), (d) competitive pressure, or (e) arbitrary executive target? Driver determines what's compromisable."

Q8: "Worst-case + reversibility: a team migrates to platform, then platform has a bug → their product breaks. Do teams need (a) instant fallback to direct Gemini API, (b) opt-out at any time, (c) blast-radius isolation between teams? No team adopts a platform they can't escape from in 5 minutes. What's the leadership tolerance for a Wave-1 lighthouse team failing publicly?"

这层 → 解锁 Step 4: 答完 Deadline 问题, 你知道为什么 6 个月这个数 (e.g., 20% MoM cost growth + VP board commit by H2-end), 才能 push back. Sub-problems 按 (cost-bleed-stop × adoption-momentum × reversibility-risk) 排序 — cost attribution + opt-out path 排最前 (blockers for any adoption), prompt library + model routing 推到 Wave-2.

S — Scope cut (→ feeds Step 5: Walking-skeleton MVP)

Q9: "In 6 months with paved-road-only authority, would you accept: (a) SDK + dashboard adopted by top-10 willing teams (Pareto, ~60% of $-spend covered) + paved-road for the rest, or (b) all 50 teams on the platform (probably needs mandate authority you may not have, risk of forcing adoption + backlash)? My instinct: (a) — make it irresistible for the top 10, document the paved road for everyone else, measure adoption as a 12-month trajectory not a 6-month gate."

Q10: "What's explicitly out of scope for 6-month MVP — (a) Search org (won't adopt anyway), (b) model fine-tuning capability (big project, defer), (c) cross-team prompt-sharing library (needs governance), (d) auto-routing across models (needs more data), (e) any team < $10K/month spend (not worth onboarding effort)? My recommendation: MVP = SDK + cost attribution + observability + opt-out path + 10 Wave-1 teams; defer prompt library, model routing, fine-tuning, Search, low-spend tail to v2."

这层 → 解锁 Step 5: 答完 S 问题, MVP 边界明确. 你知道哪 80% 砍掉先不做 (Search org, model fine-tuning, cross-team prompt library, auto-routing, low-spend tail, mandate-required adoption), 哪 20% 是 walking skeleton (SDK + per-team cost attribution + dashboard + opt-out env var + 10 lighthouse teams + Workspace-borrowed eval template).

面试官 likely 回答:

  • (a) cost save + (c) observability are P0; (b) quality + (d) capabilities are P1
  • Success = 30/50 teams using SDK by month 6 + 15% cost reduction on those + per-team observability live
  • Platform team = 6 engineers + 1 TPM + 1 PM, reports to AI Infra VP. Paved road authority only, no mandate.
  • Wave 1: Maps, Pixel, Workspace, internal Gemini Studio team, Customer Support bot team — these 5 want to talk
  • Currently: 30 teams use Vertex AI SDK direct, 15 use raw HTTP, 5 use AI Studio
  • Off-limits: Search has own infra, won't adopt
  • Cost data: org-level granularity only (5 orgs, not 50 teams). Need to add team-level cost attribution as month 1 priority.
  • Workspace has best prompt eval pipeline — borrow it as platform default.
  • Reversibility: SDK must allow opt-out via env var. 5-min rollback.
  • 6 months driven by: 20% MoM cost growth + AI Infra VP committed to board for "unified Gemini platform" by H2 end

→ Real scope: in 6 months, build paved-road SDK, add team-level cost attribution + observability, onboard 30/50 teams by being easier than raw API. Search and some politically tough teams stay direct but adopt SDK for telemetry only.

详细分析 + 回答 (sample 60-min walkthrough with ASCII diagram)

Phase 1: Clarify (8 min)

(执行上面的 G·O·O·D-F·T 10 个问题)

Phase 2: Reframe — adoption is the metric (4 min)

"Most important reframe before I touch architecture: platform success = adoption rate × value delivered, NOT feature count.

Anti-pattern Google has seen 100 times: platform team spends 6 months building world-class infra, mandates teams to migrate, mandate fails because no VP has authority, platform has 5/50 adopters, gets shut down at next reorg.

Correct framing: the platform competes with raw Gemini API for developer mindshare. It must be easier than raw API, not "required" or "approved." Wins by being the path of least resistance. This is paved road, not mandate."

Phase 3: Diagnose first (6 min)

"Before building anything, 2 weeks of audit. Building uninformed is the second-biggest platform-team failure mode."

Week 1-2 audit work:

Audit #1 — Pareto cost analysis:

  • Pull billing data → identify top 5 cost teams (likely 60-80% of $5M/month total)
  • For each: interview tech lead, shadow one engineer for 4h
  • Find: what's their use case, why is cost growing 20% MoM?
  • Hypothesis: 1-2 teams are doing things like "no caching" or "verbose prompts" that are responsible for the growth spike

Audit #2 — Worst-prompt sweep:

  • Sample 200 prompts across 50 teams (4 per team avg)
  • Score on: length, redundancy, model misuse (Pro for trivial task), missing system prompt
  • Find: top 5 worst prompts probably consume 30%+ of cost
  • This data drives the prompt registry value prop: "if you adopt the platform, you can see how other teams write better prompts"

Audit #3 — Surface mapping:

  • 50 team survey: which API are you calling? Vertex AI SDK / Direct HTTP / AI Studio / Wrapper?
  • Output: discovery of fragmentation
  • Reveals: there's probably already an internal wrapper one team built that some teams copy — that's the platform team's secret weapon (don't compete, absorb).

Audit #4 — Quality + observability gap:

  • 10 team interviews: how do you know if Gemini is working?
  • Find: most teams find out from customer complaints or internal QA
  • Confirms: observability is the killer feature — first thing teams will adopt for

Output of 2-week audit:

Findings:
  Cost:
    Top 3 teams = 65% of total ($3.25M of $5M/month)
    Customer Support team alone = $1.2M/month, growing 35% MoM
    Why: 2M context prompts where 200K would suffice (engineer didn't profile)
  
  Quality:
    Workspace team has gold-tier eval pipeline (steal as default)
    Maps team has 3 prompts that hallucinate 8%+ (need help)
    20+ teams have 0 eval, 0 golden set

"I appreciate the offer, but mandate authority is the worst thing that could happen to this platform. Three reasons:

  1. Mandate triggers compliance-only adoption. Teams will integrate the minimum surface area to comply, not actually use the platform. We'd hit 50/50 'adoption' on paper, but 5/50 actually using cost / observability / prompt registry. Adoption rate without value capture is worse than partial true adoption.
  1. Mandate destroys the feedback loop. When teams choose us, they tell us why they chose us (and what we're missing). When they're forced, they don't give feedback — they go around us. We become guessing what they need.
  1. Mandate exposes us politically. The day a mandated team has an outage they blame on our platform (even if not our fault), the mandate gets rescinded. Better to have 30/50 evangelists than 50/50 hostage takers.

What I'd ask for instead: 'strongly encouraged' messaging from VP at all-hands. Strong enough to signal direction, weak enough to preserve paved-road framing.

If you really want acceleration, give me 2 more engineers and 1 more PM instead of authority. Same speed-up, none of the political downside."

Q2: "如果 Search 团队公开拒绝 platform, 影响其他团队 fence-sitters. 怎么办?"

A: Pre-empt with a graceful deal.

"Search is politically off-limits. Don't force adoption. Instead, two paths:

Path 1 — Sell them a smaller deal:

  • 'You don't need our SDK. Just inject our OTel telemetry library in your existing wrapper. We get observability data, you keep your infra. 1 day of work, you remain independent.'
  • This is 'compliance-only' but framed politically: Search 'on the platform' for the org-wide narrative, but they keep autonomy.

Path 2 — Carve out scope:

  • Publicly redefine 'Search is out of scope for the platform — they have their own infra, intentional.' Owns the narrative.
  • Then to fence-sitters: 'Search is a special case (built their own years ago). For new teams + most teams, platform is the path.'

Worst response: try to force Search. Lose the fight publicly, all fence-sitters see they can resist too. Discretion is power."

Q3: "你的 SDK 上线 3 个月后, 一个 lighthouse team 报告 SDK 引入 50ms latency 回归. 他们要 opt out. 怎么处理?"

A: This is the moment of truth for paved-road framing. Don't fight, fix.

"Opt-out is allowed by design. But before they leave, three steps:

Step 1 — Diagnose with them in the room (same day):

  • 50ms regression where? Cache lookup? OTel emit? Quota check? Network hop?
  • Likely culprit: cache lookup blocking call (should be async)
  • If diagnosed in < 2 hours: 'Here's the fix, give us 1 week, we'll redeploy.'

Step 2 — Provide bypass while we fix:

  • 'Set SDK_MODE=fast env var. Disables cache + cascade but keeps telemetry. You get 0ms regression, we still get observability.'
  • This shows we adapt to them.

Step 3 — Public post-mortem:

  • Internal blog: 'We found a 50ms regression in v2.1. Maps team caught it, we fixed it in 6 days. Here's what we learned.'
  • Establishes that the platform listens and fixes. More credibility than 50 successful adoptions.

Never tell a team 'no you can't opt out'. The moment we do, paved road becomes mandate in their eyes."

Q4: "Cost growth 20% MoM 你说 2 周 audit 能 diagnose. 如果 audit 完发现 cost growth 是 legitimate (新产品上线, 真实用量增长), 你怎么交代?"

A: This is scope honesty.

"If audit shows the 20% MoM growth is legitimate volume growth (e.g. new product launches drove 2x users), then 'cost optimization' alone can't solve it. The 6-month goal shifts to:

  1. Make cost growth observable: was hidden, now visible. VP / Finance can attribute growth to specific teams / products with confidence. Visibility itself is the deliverable.
  1. Reduce cost-per-unit, not absolute cost: even if total Gemini bill grows from $5M → $10M over 6 months (legitimate user growth), platform can drive cost-per-query down 30% (cache + cascade + better prompts). Same business outcome, lower unit cost.
  1. Forecast accuracy: with team-level attribution + use-case granularity, Finance can forecast next quarter's spend confidently. No more 'we don't know why it's growing'.

The story to VP changes from 'we cut $X' to 'we made cost visible, attributable, and on a per-unit declining trajectory'. Both are wins. Honesty about which we're delivering matters.

Trap to avoid: promising 'we'll cut absolute cost' if drivers are legitimate growth. Set up for failure."

Q5: "6 个月 deadline 太短, audit + design + ship 不够. 你 push back 还是接?"

A: Reverse scope, don't push back deadline.

"Don't push back the deadline — VP committed to board. Push back on scope.

Original scope (implied): 'standardize Gemini across 50 teams in 6 months'

Reversed scope (what's actually shippable):

  • Month 6 deliverable: 30/50 teams adopted SDK (60% adoption), per-team cost attribution live (100% of platform users), prompt registry seeded with 20+ battle-tested prompts, observability dashboards for all platform users.
  • Not in month 6: full feature SDK (no cascade for all use cases, just lighthouse), no shadow mode helper for all teams, no comprehensive cost forecasting model.
  • Phase 2 (month 7-12): hit 40/50, add advanced features.

Story to VP:

'We can hit board-credible milestone at month 6 (60% adoption + observability live + $1M annual save tracked) by being disciplined about scope. Trying to do all of "standardize" in 6 months = ship a half-baked platform that becomes 'that other platform team' instead of 'the one we use'. Phase 1 lands a strong story, Phase 2 finishes the work.'

This is reverse-scope thinking — not changing deadline, changing what 'done' means at deadline. Same as the OCC exam pattern in the bank fraud question."

❌ 死路答法 (top 8)

  1. 闭门造 6 个月 LLM gateway, 然后 mandate 全部 50 团队
  2. 假设有 mandate authority (大概率没有)
  3. 不做 2 周 audit, 直接 design 庞大架构
  4. 把 platform 当 infrastructure 而非 library (SDK 应该薄, 不是 gateway)
  5. 忽略 observability 作为 killer feature (这是团队最先看见的 ROI)
  6. 不允许 opt-out (违反 paved-road, 立刻丧失信任)
  7. 季度 surveys 代替 weekly office hours (脱离用户)
  8. 接受 6 个月内 50/50 adoption 目标 (不现实, reverse 到 30/50)

✅ 加分项 (top 10)

  1. G·O·O·D-F·T 10 个问题, 强调 "paved road vs mandate" — 立刻 signal staff-level platform thinking
  2. 2-week audit BEFORE building — diagnose-first, anti-pattern recognition
  3. Paved road 概念明确, anti-mandate — 体现 Google 文化理解
  4. SDK 是 library 不是 gateway — 工程细节专业
  5. OTel GenAI conventions — 2025-2026 行业标准, 不是自己发明
  6. Lighthouse team 策略 (Customer Support 第一个) — 适应顺序正确
  7. Cost attribution + cardinality 风险 — 体现做过真实 telemetry
  8. Prompt registry + eval CI — 不只是观测, 还要 lift 质量
  9. TikTok Internal Agent Platform 直接对照 — 简历转化清晰, 70%+ 重叠
  10. Reverse scope (60% adoption month 6, not 100%) — 反时间压力的成熟判断

一句话总结

Google 内部 Gemini 平台 50 team = "诊断先于建造" + "paved road 不 mandate" + "SDK 是 library 不是 gateway" + "lighthouse 团队优先, 不是 announcement" + "adoption rate 是 metric, 不是 architecture quality".

真正的 win 不是造一个最强的 LLM gateway, 是让 30/50 团队主动选择用, 因为它比裸调 Gemini API 更容易. 6 个月 = 2 周 audit + 1 个 lighthouse team 验证 + 3 个月扩到 5 个 + 后 2 个月 broad adoption. 反 mandate, 反 build-then-mandate, 反 6 个月闭门造车. Adoption is sold one team at a time, 不是 mailing list 公告.
