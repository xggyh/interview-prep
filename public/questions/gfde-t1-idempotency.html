T1.1 · 设计一个 idempotent tool 接口（agent 反复调用不出事）

Google FDE Senior+ 原题 ↗
Google FDE · Senior+ · 📋 8 · 🕒 Mid May, 2026
📝 在 github.dev 打开 📄 raw .md

Problem Statement

Agent 自动 retry → 同一 tool 可能被调 3 次。设计 tool 接口让重复调用安全（idempotency key、deduplication window、natural idempotency）。

我的思路与解法

题目

"Design an idempotent tool interface for an agent that may retry. The tool transfers money between two accounts."

或更开放版本:

"Your agent's transfer_funds tool can be called multiple times due to network retry, model re-issuing, parallel execution. How do you ensure at-most-once semantics from the agent's perspective without sacrificing at-least-once delivery guarantees from the system?"

Round: Tool Calling System Design (45 min)

这道题在考什么

Idempotency 是 production agent 的必修课:

  1. Agent retry semantics —— LLM 可能 re-issue tool call, runtime 可能 retry on timeout
  2. Idempotency key 设计 —— 谁生成？怎么 dedup window?
  3. Tool 接口 contract —— 谁负责: tool 自己 idempotent 还是 wrapper?
  4. Edge cases —— retry 期间 first call still running, idempotency_key collision, key expiry

不只是知道 "用 idempotency_key", 而是知道所有 corner case.

必问 clarifying

1. Idempotency source

"Is the idempotency key generated by the LLM, the agent runtime, or the tool server? Each has tradeoffs."

2. Dedup window

"How long do we remember keys — minutes (transient retry) or hours (full session)?"

3. Failure modes to cover

"Network timeout (don't know if executed), LLM re-issue (clear duplicate), parallel agents on same user (race), key collision (rare)?"

4. Underlying API

"Does the bank API already accept idempotency_key (Stripe-style)? Or do we need to add a layer?"

5. Cost of double-execute

"Worst case if we double-charge — UX issue (refundable) or compliance event (audited)?"

我会这样答（sample）

"Clarify — [假设: bank API 不原生支持 idempotency_key, dedup window 24h, worst-case double charge = compliance event, agent runtime owns the key].

3-layer design:

Layer 1: Idempotency key generation (at agent runtime, not LLM)

def make_idempotency_key(session_id, tool_name, args):
    content = json.dumps({
        'session': session_id,
        'tool': tool_name,
        'args': args  # sorted dict
    }, sort_keys=True)
    return hashlib.sha256(content.encode()).hexdigest()[:32]

Why agent-side, not LLM-side: LLM might generate slightly different keys across retries (token sampling). Runtime deterministic.

Why include session_id: prevents cross-session collision (user A's transfer_funds in same args as user B).

Layer 2: Dedup at tool wrapper

def transfer_funds(from_acc, to_acc, amount, _idem_key):
    # Check Redis
    cached = redis.get(f'idem:{_idem_key}')
    if cached:
        status = json.loads(cached)
        if status['state'] == 'completed':
            return status['result']
        if status['state'] == 'in_flight':
            # Wait + poll, OR return 'in progress' error
            return wait_or_409(_idem_key)
    
    # Mark in-flight (atomic set-if-not-exists)
    ok = redis.set(f'idem:{_idem_key}', 
                   json.dumps({'state': 'in_flight', 'started_at': time.time()}),
                   ex=86400, nx=True)
    if not ok:
        # Race: another concurrent retry won
        return wait_or_409(_idem_key)
    
    try:
        result = bank_api.transfer(from_acc, to_acc, amount)
        redis.set(f'idem:{_idem_key}',
                  json.dumps({'state': 'completed', 'result': result}),
                  ex=86400)
        return result
    except BankAPIError as e:
        # Don't mark completed; allow retry
        redis.delete(f'idem:{_idem_key}')
        raise

Layer 3: At-most-once enforcement at API boundary

Even if our wrapper is correct, the underlying bank API may have its own at-least-once (network retries). So:

  • Pass our _idem_key as a header to bank API if it supports it (Stripe-style)
  • If not, wrap the bank call with synchronization so only one in-flight per key

Edge cases:

EC1: In-flight first call still running, second arrives

  • set nx returns false for second
  • Second polls Redis every 200ms up to 10s
  • If first completes → return its result
  • If timeout → return 409 Conflict to caller, let agent decide

EC2: Idempotency key expires (24h passed)

  • 老 key 在 Redis 没了
  • Second call 看似 new, 重新 transfer → 双花
  • Defense: bank API 自己 ledger 应该有 transaction_id dedup. Our 24h is short-term safety net.

EC3: Key collision (different intents, same hash)

  • SHA256-32 → collision prob 1 in 2^128. Negligible.
  • But if user retries 'transfer $100 A→B' 24h later (legitimately new), key collides with old one → second is no-op
  • Mitigation: include timestamp_bucket (day-level) in key derivation? But this breaks legitimate retries.
  • Better: short dedup window (5 min for transient retry) + bank-side ledger (long-term)

EC4: Agent retries with different args after partial failure

  • First: transfer $100, fails midway
  • LLM retries: transfer $100 (same args) → idempotent, OK
  • LLM 'fixes' args: transfer $110 → different key → new transaction, 100 already happened
  • This is on the LLM, runtime can't catch. Need prompt-level guidance: "if you got an error, retry with EXACT same args first."

Production hardening:

  1. Monitoring: count idempotency hits (cache hits = dedup working), p99 of in-flight wait time
  2. Cardinality: 1M sessions × 10 tool calls = 10M keys. Redis cluster handles fine.
  3. Failure mode: Redis down → fail closed (don't allow tool call, error to agent). Better than fail-open + double charge.
  4. Audit log: every idempotency hit logged with reason (retry / dup / collision suspicion)
  5. Decay: 24h TTL covers most retry windows; bank ledger covers long-term dedup."

主动 quote:

"On the voice agent, we hit this exact issue. Network retry made one customer get 2 SMS notifications. We added Redis-based dedup keyed on user_id + call_id + tool_name + sha256(args), 1h window. Hit rate ~2% (real retries). Zero duplicate SMS in subsequent 6 months."

5 follow-ups

Q1: "If Redis goes down, what's the policy — fail open or closed?" A: Fail closed for destructive tools (transfer / charge), fail open for reads (search / lookup). Worse to over-execute than under-respond. Fall back to local in-memory dedup with stricter window (5 min).

Q2: "Bank API does have idempotency_key support but expires after 5 min. Yours wants 24h." A: 2-layer: bank's 5 min handles transient retry, ours 24h handles cross-session dedup. If user retries 6h later legitimately (genuinely new transaction), they should use different intent → different key. Document this.

Q3: "Agent decides to retry with adjusted args (e.g., +$10) after error. New idem_key. But original might still execute." A: This is the LLM's error. Mitigations:

  • Prompt-level: "On error, retry SAME args first. Only adjust after confirming original didn't execute."
  • Tool returns a transaction_id on success; LLM can get_transaction(id) to verify before retrying.
  • Compensating action: explicit cancel_transfer(id) available.

Q4: "How would you test idempotency?" A:

  • Unit: 2 concurrent calls with same key → 1 execution, both get same result
  • Integration: inject network failure mid-call, verify retry idempotent
  • Chaos: kill Redis mid-flight, verify recovery
  • Property test: random arg fuzz, never double-execute

Q5: "What if the tool is a 3rd-party API we don't control?" A: Wrapping layer owned by us:

  • Our wrapper has idempotency contract
  • Our wrapper internally retries underlying API with backoff
  • Underlying API failure within wrapper → ours retries with same args (idempotent from agent view)
  • Underlying API has no dedup → wrapper's Redis state is source of truth

❌ 易错点

  1. Tool 内部不 idempotent — 依赖外层 retry, 风险全堆在边界
  2. Idempotency_key 由 LLM 生成 — non-deterministic, 不可靠
  3. 没考虑 in-flight race — set nx 是关键
  4. TTL 太长 — collision risk, 也浪费 memory
  5. TTL 太短 — 跨 session 重试漏 dedup
  6. Fail-open on Redis 挂 — 默认越界, 可能双花
  7. 没 audit log — dedup hit 应该可观察

✅ 加分项

  1. Agent-side key gen + sha256 hashing
  2. In-flight state machine (in_flight / completed / failed)
  3. set nx + 短 poll 处理 race
  4. Stripe-style key passthrough to underlying API
  5. Fail-closed on destructive tools
  6. Cardinality math (10M keys × Redis cluster handles fine)
  7. Audit hit logging
  8. Property test mention
  9. Quote voice agent SMS dedup story

Cheat Sheet

Idempotency key:
  Source: agent runtime (not LLM)
  Composition: session_id + tool_name + sha256(sorted args)
  Length: 32 hex chars
  Source-system passthrough: if Stripe-style supported

State machine:
  None → in_flight → completed (or failed → none)

In-flight handling:
  redis.set(key, in_flight, nx=True)
  If exists: poll up to 10s, then 409

TTL:
  Transient retry: 5 min
  Cross-session: 24h
  Compensated by underlying ledger long-term

Failure policies:
  Redis down → fail closed (destructive tools)
  Network mid-call → mark failed, allow retry
  Key collision → 2^-128 negligible

Audit:
  Every hit logged (retry / dup / suspicion)

Anti-patterns:
  - LLM-generated key (non-det)
  - Fail-open on infra failure
  - TTL too long (collision)
  - Tool inner not idempotent
