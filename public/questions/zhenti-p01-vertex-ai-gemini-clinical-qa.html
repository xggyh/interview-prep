这道题在考什么

不是: 考你能不能 design 一个 RAG.

是: 考你能不能 (a) 选对 Google primitives (b) 整合 BigQuery + Vertex AI Search + Gemini grounding + Workspace (c) 在 HIPAA 红线下面做 90-day MVP.

4 个 signal:

  1. Don't re-invent what Vertex AI Search already does (不要重复造轮子) — 90% 候选人答 "我自己装 OpenSearch + 自训 embedding". 错. Google FDE 面试 = 用 Vertex AI Search managed retrieval. 自己装 = 显示你不懂 Google ecosystem.
  1. Grounding ≠ prompt-engineered citation (Gemini grounding 是 native API feature) — 这是 Google 跟 OpenAI/Anthropic 最大的差异化能力. 必须提到 grounding API + grounding confidence score. 否则你"不像懂 Gemini".
  1. Workspace integration is the UX win (Workspace 整合是 UX 的关键加分) — doctor 已经在 Gmail / Docs 里. 不要再做一个 web app, 做 Workspace Add-on. 这是 "FDE 理解 customer ecosystem" 的标志.
  1. HIPAA in Google Cloud has different controls than AWS (HIPAA 在 GCP 上是不同的控件) — 不能 copy/paste AWS HIPAA 答案. Google 特有: VPC-SC perimeter, Cloud DLP, Cloud Healthcare API, BigQuery column-level security, Org Policy constraints. 提这些 = signal "我真的用过 GCP".

❌ 最常见的挂法

挂法 #1: 自己装 vector DB + embedding pipeline, 不用 Vertex AI Search

"I'd extract notes from BigQuery, chunk them, run embeddings via Vertex AI embedding API, store in pgvector on Cloud SQL, then call Gemini 3 Pro for generation."

死. 你忽略了:

  • Vertex AI Search 是 Google 给 FDE 的官方 RAG building block — 你不用 = signal 你不懂 Google stack
  • pgvector 在 20M docs scale 性能崩 (latency 2s+)
  • 自己装意味着你要自己做 chunking, reranking, hybrid search, grounding — 全部 90 天做不完
  • Vertex AI Search 已经过 HIPAA BAA, pgvector 在 Cloud SQL 也 ok 但 hospital legal 还得再 review

挂法 #2: 不提 grounding, 用 prompt "Cite sources" 模仿 citation

"I'd put 'Always cite sources as [doc_id]' in the system prompt and parse citations from the response."

死. Gemini 有 native grounding API — 强制 source attribution + confidence score + URL anchor. 不用 grounding = 你不懂 Gemini 的差异化能力. 在 Anthropic/OpenAI 上你能用 prompt engineering, 在 Gemini 上是 API feature.

挂法 #3: 自己做 PHI redaction, 不用 Cloud DLP

"I'd use Presidio + medspaCy to redact PHI in a Dagster pipeline before chunking..."

可以这么答但不加分. 因为 Google 有 Cloud DLP with medical infoTypes (NPI / MRN / DEA / HIPAA Safe Harbor templates). DLP 是 Google managed service, 已经过 HIPAA BAA, 比自托管 Presidio 维护成本低 10×. FDE 面试 = pick Google native.

挂法 #4: 接受 90 天 MVP 不 push back / 不 phase

"Yes, 90 days is doable. Week 1-4 ingestion, week 5-8 retrieval, week 9-12 UI..."

死. 20M docs + HIPAA BAA + Workspace integration + drug interaction cross-patient analytics + doctor UX = 6-9 个月真实工作量. 必须 phase: 90 天做 single-patient Q&A in 1 department (e.g. cardiology) → Phase 2 cross-patient → Phase 3 全院.

挂法 #5: 忽略 Workspace 入口, 自己做 web app

"I'd build a Next.js web app where doctors log in and ask questions..."

死. 客户已经在 Workspace. 入口是 Gmail / Docs 侧边栏 (Workspace Add-on). 自建 web app = 多一个 doctor 不去用的网址 + 多一套 SSO 配置. Workspace Add-on = OAuth 已经 SSO 过, doctor 在写病历的同时直接侧边问问题.

挂法 #6: 把 "drug interaction across patients" 当 simple retrieval

"Same RAG flow — retrieve patient's prescriptions, ask Gemini."

死. 这是 cross-patient analytics — "我所有的病人里, 谁现在的处方有 drug interaction". 这不是 RAG, 这是 BigQuery analytical query (跑 SQL 找所有该 doctor 的 patient 现有 active medication, 然后跑 drug interaction matrix). RAG 只在 narrative notes 上, 不在 structured medication list 上. 必须区分 structured vs unstructured retrieval.

G — Goal (→ feeds Decompose Step 1: KPI lock)

Q1: "When you say 'clinical Q&A assistant', do you mean (a) single-patient history retrieval (most common — 'tell me this patient's med history'), (b) cross-patient analytics ('which of my patients have drug interaction risks'), (c) clinical decision support ('should I prescribe X'), or (d) all three? These are 3 totally different products. (a) is RAG, (b) is BigQuery SQL + RAG, (c) is FDA Class II medical device territory which I'd push back hard."

Q2: "What's the success metric? Time saved per chart review? Number of medication errors caught? Doctor NPS? Compliance audit pass? Different metrics drive different design — if it's audit pass, citation faithfulness is north star; if it's time saved, latency < 3s is north star."

这层 → 解锁 Decompose Step 1: 答完 G 问题, 你就知道这道题的 KPI 是什么 (e.g., citation faithfulness ≥ 95% + 30% chart review time saved + 100% JCAHO audit pass), 后面 5 步的所有决策按这个 KPI 优化.

Phase 6: Cross-patient analytics path (Phase 2, 6 min)

"The 'drug interaction across my patients' question is NOT RAG. Let me explain why this matters."

Why not RAG for this:

  • "Which of my patients have drug interactions?" requires reasoning over the structured medication list of EACH patient, not the narrative note.
  • 20M notes ≠ 20M patients. ~50K patients × 5 active meds each = 250K medication facts. Tiny dataset.
  • Drug interaction checking is deterministic lookup against a drug interaction matrix (DrugBank, FDA Orange Book, Lexicomp). Not LLM territory.

Right path:

-- BigQuery analytical query
WITH active_meds AS (
  SELECT 
    p.patient_id,
    m.medication_rxnorm_code,
    m.dose,
    m.start_date,
    m.end_date
  FROM medications m
  JOIN care_team p ON m.patient_id = p.patient_id
  WHERE p.provider_id = @doctor_id
    AND p.active = TRUE
    AND m.status = 'active'
    AND (m.end_date IS NULL OR m.end_date > CURRENT_DATE())
),
pairs AS (
  SELECT 
    a.patient_id,
    a.medication_rxnorm_code AS med_a,
    b.medication_rxnorm_code AS med_b
  FROM active_meds a
  JOIN active_meds b ON a.patient_id = b.patient_id AND a.medication_rxnorm_code < b.medication_rxnorm_code
)
SELECT 
  p.patient_id,
  p.med_a,
  p.med_b,
  d.severity,
  d.mechanism,
  d.recommended_action
FROM pairs p
JOIN drug_interactions d 
  ON p.med_a = d.med_a_rxnorm AND p.med_b = d.med_b_rxnorm
WHERE d.severity IN ('major', 'contraindicated')
ORDER BY 
  CASE d.severity WHEN 'contraindicated' THEN 1 WHEN 'major' THEN 2 END;
