BNPL 客服 Agent · 技术设计文档（面试背诵版）

用途：明天面试背诵。每个模块统一用 可背诵三段式： ① 一句话总纲（脱口而出）｜② 设计要点 + 选型理由（trade-off）｜③ 关联考点 & 可能追问 关联考点对应《高难度大模型面试题精选》的题号，用 【Q?】 标注。 RAG 作为横切能力，在每个相关模块用 🔎RAG触点 标出。

0. 如何用这份文档背（先背这页）

背诵优先级：先背 §1 的 30 秒电梯陈述 + §2 架构图（能在白板画出来）→ 再背每个模块的「一句话总纲」→ 最后背「trade-off + BNPL 的坑 + 追问答法」。

面试心法（一句话）：

「已知任务走确定性的 skill/workflow，未知任务才放 agent loop；越确定越可测越可靠。动钱的操作一律幂等 + fail-safe + 人确认。可靠性脊柱（tracing/eval/guardrails/幂等）先于花哨能力。」 —— 这句话能解释我 80% 的设计选择，被问住时就回到它。

1. 场景与需求边界

① 一句话总纲

一个面向 2M+/天 请求、APAC 多市场（EN/马来/泰/印尼） 的 BNPL（先买后付）客服 Agent，要在 sub-2s 内、合规可审计地解决账户/还款/退货/争议/欺诈/hardship 等场景，涉及真金白银，错一次就是事故。

② 需求要点 + 为什么

典型场景清单（按执行模式分类，面试时能报出来就赢一半）：

场景例子适合的执行模式
账户/额度查询余额、可用额度、账单日A 单工具
BNPL 用不了结账被拒：额度不足/风控拦截/逾期冻结/KYC未完成/商户不支持B 动态多工具诊断
还款查还款计划、提前还款、改还款日、扣款失败C 预设 workflow（动钱）
退货退款怎么退、退款进度、退款如何冲销分期C workflow + D 政策RAG
争议/拒付未收到货、重复扣款、金额错、未授权交易C skill（dispute）
欺诈/未授权报欺诈、冻结账户C skill + 强制 escalate

硬约束（写进需求才算数）：

  • 延迟：端到端 sub-2s，要做延迟预算分配。
  • 规模：2M+/天 → 跨用户隔离是红线，缓存/模型分层是刚需。
  • 合规：新加坡 PDPA + APAC 各市场监管 + 催收行为规范 + 弱势客户话术红线；全程 audit trail。
  • 金融属性：写操作/动钱必须幂等 + fail-safe；记忆/缓存绝不能当账实来源。

③ 成功的定义（被问「怎么衡量好不好」时答这个）【Q12】

别只看「有没有回话」，按任务级多指标一起看：

  1. Task completion rate（任务真完成）
  2. Containment rate（没转人工就解决的比例）
  3. Correct-action rate（做对了动作，尤其动钱）
  4. 合规违规率（目标 ≈ 0）
  5. 延迟 SLO 达标率
  6. Fallback / Escalation 率

金句：「单看任一指标都会骗自己——containment 高但 correct-action 低，是在错误地'自己硬扛'。」

③ 关联考点 & 追问【Q1】

  • Agent 五大核心组件（被问「Agent 由什么组成」直接背）：感知 → 记忆 → 推理/规划 → 行动 → 评估/反思，形成闭环。
  • 追问「你这架构哪里体现了组件协作？」→ Router=推理入口，工具层=行动，记忆+RAG=记忆，guardrails+eval=评估反思，闭环直到任务完成或 escalate。

3. 意图识别与路由（你最关心的那块）

① 一句话总纲

Router 不只是分类器，它是「置信度门控 + 执行模式选择 + 工具/技能子集收敛」三合一；并且优先走最确定的路径（workflow > sub-agent > 自由 loop）。

② 设计要点 + 选型理由

A) 你提的 3 类 → 我帮你补成完整的「执行模式」taxonomy。

你原来的 3 类：

  1. 单工具直答（账户信息）
  2. 动态多工具协作（工具间配合没预定义）→ 是的，这就是一个 sub-agent（见下）
  3. 预设 workflow（节点式）

直接回答你的问题：这 3 类能覆盖所有场景吗？——能覆盖「执行/动作」这一维度，但不完整。 因为这 3 类只回答了「要不要调工具、调几个、路径定不定」，漏了「不调工具」和「不该自己干」的分支。补全后是 5 类：

模式是什么BNPL 例子关键特征
A 单工具直答一次函数调用解决查余额/额度即使单工具也要挂 fallback（服务挂了不能编余额）
B 动态多工具 = sub-agent工具间配合不预定义，模型边想边调「为什么 BNPL 用不了」要查额度+查风控+查逾期+查商户有 ReAct / Plan-Execute loop，有步数/时间/成本预算上限
C 预设 workflow / skill节点式状态机，路径确定发起还款、退货、dispute确定性高、可审计、动钱首选
D 纯知识问答（RAG）不调工具，检索政策/FAQ 作答「怎么退货」「利息怎么算」🔎核心 RAG 路径，必须带引用
E 澄清 / 升级 / 拒答非动作分支意图不清→澄清；hardship/欺诈→转人工；越权金融建议→拒答「转人工」本身就是一种成功

背诵口诀：「一具、多具、定流、查知、兜底」 = A 单工具 / B 多工具 / C 定 workflow / D 查知识 / E 兜底升级。

B) 为什么模式 2 是 sub-agent？【Q15, Q29】

sub-agent = Router 委派出去的、带自己作用域工具集 + 预算（max steps/time/cost）+ 专属 guardrails + 成功判据的有界 ReAct/Plan-Execute 循环，跑完把结果交回。 它和 C 的区别是确定性：C 是预先画好的 DAG/状态机；B 是模型动态规划路径。能用 C 就别用 B（确定性=可测=高成功率）。

C) 路由怎么做（不止一个 LLM 分类）：

  • 分层：先规则/关键词粗筛（快、便宜）→ 再小模型语义分类（兜底）→ 低置信才上大模型。【Q16 模型分层补偿】
  • 置信度门控：高置信→直接执行；中置信→先澄清/补槽位；低置信→转人工。
  • 意图驱动收敛：意图一旦定了，就只 expose 对应的工具/技能子集（见 §5 discovery），这是工具选择准确率的关键。
  • 槽位补全（slot-filling）：缺必填槽位（如退货要订单号）就反问，别瞎调工具。

🔎RAG触点：意图不清时，可先用语义检索把用户 query 匹配到 FAQ/skill 库做意图消歧。

③ 关联考点 & 追问【Q2, Q29, Q30】

  • 追问「ReAct 和 CoT 区别？」→ CoT 只是把推理写出来（开环、纯内省、无外部交互）；ReAct 是「推理→行动→观察」闭环，能调工具拿外部真值、能纠错。 模式 B 用 ReAct。
  • 追问「CoT 和 Planning 区别？」→ CoT 是把思考过程写出来；Planning 是生成一张「可执行的任务表」（如先查额度再查风控）。模式 B/C 是 Planning。
  • 追问「3 类不够时怎么办？」→ 答 5 类 taxonomy + 「determinism ladder：能确定就确定」。

3.5 路由进阶：SFT 分类器 + 校准门控 + 错分自愈 + 训练飞轮

这是全文最硬的一节，也是面试官最爱追的「你整个系统都挂在 router 上，它错了怎么办」。

① 一句话总纲

路由不靠「分得准」保正确，靠两条腿：(1) SFT 小模型 + 校准置信度——把准确率和「知道自己没把握」做上去；(2) 错分自愈——能力包含、skill-as-tool、handler 回弹、危险类高召回、escalation 兜底接住残差。而自愈产生的信号又反哺 SFT 训练飞轮，越用越准。Router 是优化提示，不是不可逆承诺。

② 三块展开

A) 为什么这里就该 SFT（封闭集 + 高流量 + 低延迟 + 校准）【Q16】

意图分类是「该上 SFT」的教科书场景：

  1. 准确率：封闭标签集，把领域黑话（「用不了」「卡了」「扣两次」）烧进权重，in-distribution 稳赢 few-shot prompting。
  2. 延迟/成本：微调小模型就是 §14 分层里那个「便宜快」的底座，2M+/天扛得住，大模型只留长尾。
  3. 校准（最被低估）：①里的「置信度门控/弃权」靠一个可信的置信度。LLM 自报把握出了名地不准、还能被 prompt 带偏；训练分类器的 softmax（+ temperature/Platt 校准）是真概率、单调、可阈值。→ SFT 不只提准确率，它让整套门控真正成立——否则阈值建在沙子上。

微调什么（具体到架构）：

  • 头部高频意图：多语 encoder（XLM-R / mBERT / embedding + 分类头），tiny、<10ms、给校准 softmax、覆盖 EN/MS/TH/ID。
  • 复合/难句：小 decoder（LoRA）输出结构化 {intent, slots, 置信信号}，处理多意图，配约束解码。
  • 分层即此：encoder 走快路 → 小 decoder 兜复合 → 大模型只啃长尾。
  • 铁律：微调「意图」、不微调「模式映射」。intent 语义稳定 → 烧进权重；mode = f(intent) 留在 registry/config，把某 skill 从 C 改到 B 不用重训。

B) 错分自愈（六机制，按「错误代价」设计而非追求 100% 准）

模式之间不是互斥硬墙，能力是包含关系；错分 ≠ 失败，因为路径能自愈。

#机制怎么救错分
1能力包含 + 错向偏置（最重要）B ⊇ A（sub-agent 本就能只调一次工具）→ A→B 错分无害。不对称：A→B 代价小（多点 token），B→A 代价大（单工具 handler 干不了多步→失败）。不确定时偏向更通用模式，动作类默认兜底走 B。
2Skill 也注册成 sub-agent 可调的工具router 错把 dispute 路由成 B 时，sub-agent 跑着发现「这是争议」→ 把 dispute skill 当工具调进来。C 的能力对 B 可达。
3Handler 能 say-no 回弹（re-entrant router）handler 自检「不是我」→ 带富化上下文弹回 router 重路由（A→needs_replan→B；C 撞预设外分支→升 B/转人工）。重路由预算 ≤1~2 次，否则乒乓【Q7 防死循环】。
4D（RAG）当软着陆找不到可执行意图但能用知识答 → 先落 D 检索政策作答，再考虑放弃。
5危险类高召回（recall 优先）欺诈/hardship/未授权/投诉配故意过度触发的检测器，宁可误升级不漏——漏一个欺诈代价 >> 多一次人工。
6Escalation 兜所有漏网低置信/反复失败/handler 喊搞不定 → 带完整上下文转人工。这就是「转人工=成功」。

C) 训练飞轮（自愈信号 = SFT 的标签来源，点睛之笔）【Q26, Q12】

  • 冷启动：大模型自动打标 + 人审种子集；按意图合成 paraphrase（尤其泰/印尼低资源语）。
  • 生产飞轮：B 里那些兜底机制正好就是 SFT 的标签来源——
  • 重路由事件 = 「原分类错了」负样本；escalation / 用户重述 = 弱标签；低置信/规则与模型分歧 → active learning 优先送人审。
  • → 自愈路径同时在生产训练数据，错分越多、数据越肥、下一版越准。
  • 重训纪律：每次必过 eval + canary/shadow；macro-F1 涨了但欺诈 recall 掉了 = NO-GO，危险类按错误代价单独盯 recall。
  • 建设顺序：全新无流量 → 先 规则 + prompt 大模型 跑起来收数据 → 攒够量再 SFT。

③ 关联考点 & 追问【Q16, Q12, Q13, Q26, Q7, Q18】

  • 「怎么保证五分类准？」→ 别让模型在 5 个模式里猜，先识别意图再查表推导模式；SFT 提准确率 + 给校准置信度；剩下靠自愈。
  • 「router 错了整条链就废了吧？」→ 不会：B⊇A、skill-as-tool、handler 回弹、高召回、escalation——错分能自愈。
  • 「SFT 是不是就不用兜底了？」→ 反了。SFT 抬地板、不拆网：分类永远不完美（分布漂移/新意图），而且自愈信号正是 SFT 的训练数据，两者互补。

🎯 本节金句

「我不靠 router 分得准来保证正确——分类是封闭集 + 高流量 + 低延迟，正该 SFT，它既提准确率、又给我校准过的置信度让门控成立。但 SFT 抬地板不拆网：模式能力是包含关系（B⊇A）、skill 能被 sub-agent 当工具调、handler 能 say-no 回弹、危险类高召回、escalation 兜底；而这些自愈信号又反过来喂 SFT 的训练飞轮，越用越准。我微调意图不微调模式映射，每次重训按错误代价过 eval 才上线。」

4. 执行模式详解（A/B/C/D 各怎么落地）

① 一句话总纲

四条执行路径共用同一套工具层、记忆、容错；区别只在谁决定路径：A 无需规划、B 模型规划、C 预先规划、D 不规划只检索。

② 要点 + 理由

模式 B（sub-agent）规划范式怎么选【Q29, Q31, Q32】：

  • Plan-Then-Act（先整体规划再执行，如 SayCan/TaskWeaver）：适合步骤可预先想清、要可审计的——BNPL 诊断类首选。
  • ReAct + 轻规划（边做边调整）：适合中间结果会影响下一步的。
  • ToT / LATS（树搜索/MCTS）：探索多路径找最优解，贵、慢，BNPL 客服基本用不上（留给离线/高价值决策），但要会讲：相比线性规划能回溯、能比较多条路径。
  • 鲁棒重规划【Q31】：某步失败（API 超时/返回格式错）→ 不是整个重来，而是局部重试→换路径→重规划，并保护已完成步骤的状态。

防死循环（必背）【Q7】：

  1. 轨迹检测：检测连续重复的 (tool, args) 或重复输出 → 中断。
  2. 预算上限：max steps / max time / max cost，超了强制收口（转人工或降级答案）。

这两条是有限状态自动机思路，不靠模型自觉。

模式 C（workflow/skill）= 确定性状态机【Q9】：

  • 节点 = (校验 → 调工具 → 等确认 → 写操作 → 回执)；每个节点可持久化、可断点续跑。
  • 动钱节点前强制人确认 + step-up 鉴权。

🔎RAG触点：模式 D 是纯 RAG（见 §9）；模式 B/C 里也会调「政策检索工具」来给答案找依据。

③ 追问【Q20】

  • 「为什么不全用自回归 LLM 规划？」→ 自回归规划在可解释性/最优性/约束满足上弱于符号规划（PDDL/HTN）；BNPL 用「LLM 规划 + 确定性 workflow 兜约束」来弥合，不引入完整符号系统。

5. 工具层：Registry + Discovery

① 一句话总纲

Registry 管「目录里有什么」，Discovery 管「这一轮给 LLM 看哪几个」——后者才决定调用准确率；工具元数据里没有「副作用等级」和「幂等键」，后面的重试和确认全是空中楼阁。

② 设计要点 + 理由

A) Tool Registry 必填元数据（被问「你的工具怎么定义」时报字段）：

  • name / description / 参数 schema（基础）
  • 副作用等级：只读 / 写 / 动钱（决定要不要确认、能不能重试）
  • 是否幂等 + 幂等键（动钱重试的命根子）
  • 所需鉴权 scope（决定 discovery 收敛和 step-up）
  • per-tool 超时 + p99 SLA（吃进延迟预算）
  • 可重试错误集 + 退避策略
  • 降级目标（替代 tool / 缓存 / 放弃）
  • PII 标记（决定日志脱敏）
  • 版本号
  • 实现：声明式 + 启动时 schema 校验 + 热注册（不重启加 tool），对外用 MCP 做互通。

B) Tool Discovery【Q38】：

  • 区分「目录里有什么」vs「这一轮 expose 哪几个」。
  • = 按意图 + 用户权限动态收敛子集（语义检索 description + 规则按 intent 分类）。
  • 每轮 expose 上限（≤8）：工具一多，选择准确率掉、token 涨。
  • 权限外的 tool 连看都看不到（entitlement 收敛）。

C) 工具描述 & 参数 Schema 设计【Q5, Q37】（高频考点，必背）：

  • description 要让模型知道「何时用、为何用」，参数 schema 让模型知道「填什么、怎么填」。
  • 负向约束（negative constraints）：明确写「不要在 X 情况下用」。例：refund_tool 的 description 写「仅用于已结算订单；未结算退款用 cancel_order，不要用本工具」。
  • 给调用策略：例「金额不确定时先调 get_order_detail，不要猜金额」。

🔎RAG触点：Discovery 的「语义检索 description」本身就是一次小型 RAG（对工具库做向量检索）。

③ 追问【Q18, Q38】

  • 「工具一多模型选不准怎么办？」→ 分层过滤 + 基于检索的预选（≤8）+ 工具类别层次。
  • 「模型知道做什么但不会调工具？」→ 从表示学习角度：工具调用是稀疏信号；缓解靠演示检索（few-shot 调用样例）、工具原型网络、解耦推理与执行，而非单纯堆大模型。

6. 技能层：Skill Registry + Discovery（融合 Anthropic 内部 Skills 一手经验）

本节融合 Anthropic 官方复盘《Lessons from building Claude Code: how we use Skills》。面试里能说「我参考了 Anthropic 公开的内部 Skills 实践」= 可信度 + 前瞻性。

① 一句话总纲

Skill 不是几段提示词，是「围绕一个任务组织起来的工作材料文件夹」——SKILL.md（目录）+ 参考文档 + 脚本 + 模板 + 示例 + hooks + 可持久化数据。Claude 调用时拿到的是「完成这件事的整套工作材料」。它给你 workflow 的确定性 + 可审计，同时靠 progressive disclosure 省 token。

② tool vs skill + Discovery

  • 分清：tool = 一次函数调用；skill = 打包好的「做法」（流程 + 要用的 tools + 专属 guardrails + slots + 成功判据）= 模式 C 的 workflow / 模式 B 的 sub-agent handler。
  • Discovery：意图 → 候选 skill（语义 + 规则）→ JIT 加载（只在命中时进 context）。🔎RAG触点：候选召回 = 对 skill 库语义检索。
  • 聚焦 > 大而全（Anthropic 强调）：能干净落进某一类的 skill 更稳；想一次覆盖太多目标会把模型带乱。← 呼应全文「确定性」主线。
  • BNPL skill 举例：dispute交易 / 设置还款计划 / 报欺诈 / hardship协助 / 解释某笔费用 / 退货退款（每个带自己的合规约束、可复用）。

③ Anthropic 内部 9 类 Skill → 映射到 BNPL（背这张表 = 显示你想全了）

9 类连起来就是一条完整工作流：补知识 → 验证 → 取数 → 流程 → 脚手架 → 质量 → 发布 → 排障 → 运维。

Anthropic 9 类BNPL 客服 Agent 对应
1 Library/API reference内部账务/风控 SDK 怎么用 + gotchas（字段命名、append-only 表）
2 Product verification（最值钱）动钱后到底成没成的端到端验证：headless 跑还款/退款 + 对 ledger/payment_events 程序化断言
3 Data fetching & analysis取数 skill（账户/交易/对账），封装表结构与字段约定 ← §14 NL2SQL
4 Business process & automation内部运营流程：批量争议、合规报表、催收名单生成
5 Code scaffolding & templates（偏研发，BNPL agent 用得少，一句带过即可）
6 Code quality & reviewadversarial-review 子 agent 给「新鲜视角」挑错，可接 CI
7 CI/CD & deploymentbabysit-pr / deploy：agent 自身发布、放量、错误率对比、回滚 ← §15 canary
8 Runbooks「症状 → 排查」：用户报「扣两次/退款没到」→ 映射查哪些系统 → 结构化结论；也用于 agent 自身 on-call
9 Infrastructure operations破坏性操作（清理/成本/依赖）必须 guardrail：先通知 → 确认 → 执行 ← §12 自主边界

④ 怎么写「对」一个 Skill（6 条铁律，全是反直觉的干货）

  1. 别写显而易见的：补模型默认拿不到的（团队 design taste、避坑点），不是教它本来就会的。
  2. SKILL.md 做目录、细节分文件按需加载：卡住读 stuck-jobs.md、API 签名进 references/、模板进 assets/——这就是 progressive disclosure；文件系统本身就是上下文工程。
  3. 别写太死：给关键规则 + 留判断空间，否则一换情境就卡。
  4. setup 前置：缺的用户上下文放 config.json，缺了就问（结构化多选可调 AskUserQuestion）。例：争议发到哪个 Slack 渠道、退款审批人是谁。
  5. description 写给模型看、直接服务触发：系统开局扫所有 skill 的 name+description 决定触发——它不是摘要，是触发条件说明。把关键词（"dispute"/"退款"/"还不上"）、会上传的文件、激活场景直接写进去。
  6. 最有信号量的是 gotchas（精华）：模型本来会写代码读库，真正值钱的是「把它从默认思路里拽出来」的细节。BNPL 例：
  • 分期/订阅表是 append-only，要找最高 version，不能只看最新 created_at；
  • 同一字段 gateway 里叫 txn_ref、billing 里叫 loan_id、风控里叫 account_ref；
  • 退款 API 返回 200 ≠ 钱到账，得去 payment_events/ledger 看真实结算状态。

🚨Anthropic 最看重「验证」：模型最爱给「已经做完了」的错觉，最易掉链子的恰是最后一步验证；值得让工程师单独花一周把验证类 skill 做硬。两招：让 agent 录测试过程视频 + 关键节点加程序化断言（状态变没变、事件落没落库、终态对不对），绝不靠「看起来差不多」。← 直接接 §11 动钱 fail-safe + §15 eval。

⑤ Skill 用深了，先长出三样：记忆 / 脚本 / hooks

  • 记忆：per-skill 日志——dispute skill 把每次处理记进 disputes.log，下次先读历史；简单用 append-only/JSON、复杂用 SQLite，存在稳定持久化目录。← §8。
  • 脚本：「能给模型的最强工具之一就是代码本身」。预置取数/对账/分析 helper，模型不再每次重写样板，把回合花在编排和下一步上。← §14 省延迟。
  • on-demand hooks（只在该 skill 调用时、只在当前会话生效）：
  • /careful 拦 refund / charge / waive-fee / close-account 这类动钱或破坏性操作；
  • /freeze 排障时只读、禁止越界 Edit/Write，防「一边查一边改坏」。
  • → 动钱红线的一手背书落地机制，比空谈「要加确认」更硬。← §11/§12。

⑥ 前瞻：Skill 规模化——分发 / 治理 / 度量 / 组合（内部 Agent 平台雏形）【Q17 AaaS】

  • 分发：repo ./.claude/skills check-in（小团队）↔ 内部 marketplace（团队大更优：按 market/角色自助安装，省「人人可见」的上下文负担）。BNPL 多市场（APAC）→ 倾向 marketplace。
  • 治理（不搞中央审批）：谁有 skill 想分享 → 传 GitHub sandbox → Slack 试用 → 有 traction 后 owner 提 PR 进 marketplace。轻流程，符合「skill 靠真实使用长出来」。
  • 度量：用 PreToolUse hook 记 skill 使用率 → 看哪些热、哪些「该触发却没被想起」。← 呼应 §3.5 飞轮 + §15 可观测。
  • 组合（skill composition）：退货 skill 调退款 skill 调对账 skill——直接引用名字即可串。
  • 一句话：分发 + 治理 + 度量 + 组合 = 内部 Agent-as-a-Service 平台雏形。BNPL 把每类客服能力做成可治理、可度量、可组合的 skill，就是「客服 Agent 平台化」的前瞻路线。

⑦ 关联考点 & 追问【Q17, Q6, Q9, Q12】+ 金句

  • 「为什么不把指令都塞 system prompt？」→ 窗口有限 + 干扰 + token；progressive disclosure 只在命中时加载。
  • 「skill 之间有依赖怎么管？」→ 目前靠引用名字 + 模型串（composition）；强一致的动钱链路再叠 saga（§11）。
  • 🎯金句：「Skill 的价值不在教模型它本来就会的，而在把团队人人知道、模型默认不知道的 gotcha 和验证方法固化下来；最好的 skill 一开始只有几行 + 一个 gotcha，越用越全。聚焦、可验证、可治理、可组合——这才是客服能力平台化的样子。」

7. 规划与编排（多工具：依赖 / 并发 / 聚合）

① 一句话总纲

多工具不是「列个清单挨个调」，而是用 DAG 表达依赖、能并行的并行、动钱的串行加锁、结果做冲突解决后聚合。

② 要点 + 理由【Q6】

  • 依赖：从「顺序」升级到 DAG（显式依赖图）；无依赖的并行（吃延迟预算）。
  • 并发冲突：读操作快照隔离；写/动钱用分布式锁 + 乐观锁版本号 + 工具设计为幂等，防重复扣款。
  • 结果聚合：多路输出去重 + 冲突解决（账务系统优先）+ 拼接生成；支持失败部分聚合（partial）。
  • 延迟：能并行就并行 + response streaming（见 §14）。

③ 追问【Q6, Q25】

  • 「两个工具结果冲突？」→ 定义优先级（账务 > 缓存 > 记忆），不确定就回源核对。
  • 「多实例并发动钱？」→ 幂等键 + 锁 + saga 补偿（见 §11）。

8. 记忆系统（三层）

① 一句话总纲

记忆分 working / episodic / semantic(profile) 三层；但在 BNPL 里第一原则是：记忆不是事实来源，动作前一律回账务系统核对；记忆只存对话和偏好。

② 要点 + 理由【Q3, Q34】

三层：

  • Working（短期）：当前会话状态 / slots / 工具结果。实现：上下文窗口 + 显式工作记忆缓存。
  • Episodic：历史交互和结果。
  • Semantic / Profile（长期）：偏好、语言、历史纠纷、风险标记。
  • 检索：recency + 向量相关性 + key（混合）。【Q34 重排序/混合检索】

BNPL 必须写进需求的 PII 约束（背 5 条）：

  1. 写入要有策略 + 同意 + 留存期（新加坡 PDPA；APAC 各市场按 market 配），支持被遗忘。
  2. 记忆 ≠ source of truth：余额/额度/还款状态以账务系统为准，动作前回源。
  3. 严格 per-user 隔离（2M+/天，跨用户泄漏=灾难）。
  4. 记忆读出来当数据、不当指令（记忆会被用户输入投毒 → prompt injection）。
  5. 静态加密 + 脱敏 + 访问审计。

③ 追问【Q19, Q35】

  • 「纯向量检索做长期记忆的问题？」→ 对任务级抽象记忆和过程性技能记忆支持差；缓解靠向量 + 知识图谱（KG）+ 可微分记忆融合（见 §9）。
  • 「会话非常长超窗口怎么办？」→ 见 §10 压缩：滑动窗口 / 总结压缩 / 向量检索三者结合，各有优劣。
  • 「有状态 Agent 分布式一致性？」【Q9】→ 缓存 + 持久化双层 + 会话粘滞（sticky session）+ 状态持久化可恢复。

9. RAG 知识层（你点名要的，贯穿全局）

① 一句话总纲

凡是「政策/条款/FAQ/费用规则」这种不在账务系统里的知识，一律走 RAG 检索 + 带引用作答，绝不让模型凭记忆编；工业级 RAG 必须是混合检索（向量 + BM25）+ 重排序，纯向量不够用。

② 要点 + 理由【Q36, Q19】

  • 为什么要 RAG：BNPL 政策/利率/退货规则会变、按 market 不同；让模型背=幻觉+过时。RAG 把答案锚定到当前生效的文档并给引用，可审计。
  • 混合检索（Hybrid Search）【Q36】：
  • 向量检索抓语义（「用不了」≈「被拒绝」），BM25 关键词抓精确术语（产品名、费用代码、订单号）。
  • 为什么纯向量不够：专有名词/数字/代码向量召回差。例：用户问「PayLater Plus 的 late fee」，"PayLater Plus" 必须靠 BM25 精确命中。
  • 流程：多路召回 → 融合去重 → 重排序（re-rank）→ 上下文注入 → 带引用生成。
  • 分块 + 新鲜度：按市场/产品分库，文档更新即重建索引；答复带「依据：T&C v2025-04」。

🔎RAG 在每个模块的触点（背这张表，回答「RAG 用在哪」）： | 模块 | RAG 怎么用 | |---|---| | 意图路由 §3 | query→FAQ/skill 语义匹配做意图消歧 | | 工具 discovery §5 | 对工具库语义检索收敛子集 | | 技能 discovery §6 | 对 skill 库语义召回候选 | | 记忆 §8 | episodic/semantic 的向量检索 | | 知识问答 §4-D | 政策/FAQ/费用规则检索作答（主战场） | | 缓存 §14 | FAQ 语义缓存（命中直接返回） | | 合规 §12 | 把监管/披露要求作为知识锚定输出 |

③ 追问【Q19, Q34】

  • 「向量记忆的根本局限 + 替代？」→ 任务级抽象 & 过程性技能记不住；KG（实体关系，如用户↔订单↔争议）+ 可微分记忆网络融合，图增强的记忆读写。
  • 「RAG 怎么防过时/防错引用？」→ 文档版本化 + 新鲜度过滤 + 强制引用 + 检索不到就 fail（不编）。

10. 上下文管理与自动压缩

① 一句话总纲

触发阈值后做压缩：旧轮 rolling summary、近几轮留原文、工具大结果 elide（只留摘要+可回取 handle）；但要定义一组压缩时绝不能丢的「受保护状态」，且结构化信息单独存、不揉进散文。

② 要点 + 理由【Q22, Q35】

  • 触发：context 用量 % / 轮数 / 每次调用前检查。
  • 策略：
  • 旧轮 → rolling summary；近几轮 → 原文。
  • 真正大头是工具结果（交易清单、日志）→ elide：全量存 context 外，里面只留摘要 + handle 可回取。
  • 受保护状态（绝不能压掉）：待确认的写操作、active 任务的 slots、鉴权状态、合规相关陈述（用户刚说的 hardship/dispute 理由）、安全标记。
  • 结构化与散文分开：金额、交易 ID 单独用一个 state object 存，和 prose summary 并行，别让 summary 把数字揉丢。
  • 审计：不管 context 怎么压，全量 transcript 落库做审计回放。

③ 追问【Q35】

  • 「滑动窗口 vs 总结 vs 向量检索？」→ 滑动窗口简单但丢远端；总结省 token 但可能丢细节；向量检索精准召回但要额外存储。工业上三者结合：近窗口原文 + 远端总结 + 关键信息向量可回取。

11. 容错、降级与幂等（动钱红线）

① 一句话总纲

错误先分类（可重试 vs 不可重试），重试用指数退避 + jitter + 最大次数 + 总时限上限，连续失败开 circuit breaker；降级是一条 ladder；写/动钱的重试必须带幂等键，不确定时对钱 fail-safe——宁可不做，绝不瞎猜。

② 要点 + 理由【Q8, Q31】

  • 错误分类：可重试（超时/5xx/限流）vs 不可重试（4xx 校验/鉴权/业务拒绝——重试只会更糟）。
  • 重试：指数退避 + jitter + max 次数，一定有总时限上限（否则吃穿 2s 预算）；连续失败到阈值 → circuit breaker。
  • 降级 ladder：重试同 tool → 换 provider（多供应商 failover）→ 用缓存/稍旧数据（带说明）→ 给降级答案 → 转人工/转异步。
  • 🚨BNPL 红线：
  • 动钱 tool 重试必须带幂等键，否则一次重试 = 一次重复扣款，「成功的双扣」就是事故。
  • 对钱 fail-safe：不确定就别做。查余额服务挂了 → 只能降成「现在拿不到，要不要我提醒你」，绝不编一个余额；发起还款失败 → 直接 fail，不能降成「大概成功了」。
  • 工具幻觉容错【Q8】：预校验层拦掉「调用不存在的工具/参数非法」；schema 强约束；调用前校验、调用后核对返回格式。
  • Saga / 事务完整性【Q6, Q25】：多个 tool 串起来动钱 → 补偿回滚，跨系统保证 exactly-once 效果。

③ 追问【Q31】

  • 「多步任务中间步失败？」→ 局部重试 → 回滚（saga 补偿）→ 重规划，保护已完成状态，不整体重来。

12. 安全、合规、沙箱与鉴权（横切，BNPL 的命门）

① 一句话总纲

输入侧防 PII/注入/越狱/跑题；输出侧不给越权金融建议、不编账户事实、不承诺系统兑现不了的事、对弱势客户和催收语境守话术红线；叠加 APAC 各市场监管 + 全程 audit trail；工具按最小权限 + 沙箱隔离。

② 要点 + 理由【Q10, Q11】

Guardrails：

  • 输入侧：PII 检测、prompt injection、jailbreak、跑题。
  • 输出侧：不给未授权的金融/投资建议、不编账户事实、不承诺兑现不了的事、弱势客户话术红线（催收语境尤其硬）。
  • 叠加各 APAC 市场监管 + 催收行为规范 + 必要披露 + audit trail。

鉴权 + Step-up + 身份：

  • 用户是谁、认证到没到这个动作要求的等级；敏感/动钱操作做 step-up；工具/skill discovery 按 entitlement 收敛（权限外不可见）。

沙箱 & 数据最小化【Q10, Q11】：

  • 数据最小化：只给 Agent 完成任务所必需的数据（最小化 API，不直接给 SQL）。
  • 可审计：记录所有数据访问、不可抵赖（全链路审计日志）。
  • 访问控制：行级安全（RLS）+ 字段级权限 + 动态脱敏。
  • 若有代码/外部系统执行：容器级隔离 + 命令白名单 + 网络隔离 + 资源限制（防耗尽）。

自主行动的边界（你问的「agent 自主去做」）：

  • 自主 loop 必须有预算上限（步/时/钱）；动钱/写操作一律 human-in-the-loop 确认；不确定 → fail-safe；全程审计。

③ 追问【Q11】

  • 「怎么保证敏感数据最小化 + 可审计？」→ 最小化 API + RLS/字段权限 + 动态脱敏 + 全量审计日志 + 不可抵赖。

13. 转人工 / Escalation

① 一句话总纲

带完整上下文（摘要 + transcript + 状态）的 warm handoff；触发条件含 hardship / 欺诈 / 投诉 / 低置信 / 反复失败 / 监管要求；对难 case，转人工本身就是一种成功，别为了 containment 硬扛。

② 要点 + 理由

  • warm handoff：把对话摘要 + 全量 transcript + 当前任务状态 + 已采取动作一并交给人工，客户不用重说一遍。
  • 触发器：低置信、反复失败、hardship、疑似欺诈、投诉、监管要求场景。

③ 追问

  • 「containment 越高越好吗？」→ 不是。错误地硬扛会出合规事故；正确的 escalate 是高质量结果。

14. 性能与延迟（你的主场，sub-2s）

① 一句话总纲

sub-2s 靠延迟预算分配 + 能并行就并行 + response streaming + 模型分层 + 多级缓存五件套；目标是逼近物理延迟下限。

② 要点 + 理由【Q23, Q16】

  • 延迟预算分配：router + 检索 + LLM + tool 各分配多少 ms，超预算就降级。
  • 并行：无依赖工具并发。
  • Streaming：边生成边返回，降感知延迟。
  • 模型分层：小模型跑路由/简单意图，大模型啃难的。【Q16 推理瓶颈工程补偿】
  • 多级缓存：FAQ 语义缓存（🔎RAG）+ prompt cache + tool 结果缓存。
  • 解码优化【Q23】：投机解码、前缀缓存、约束解码（强制 JSON）。

③ 追问【Q23】

  • 「500ms 内完成输入→工具决策？」→ 三维度：解码优化（≤200ms）+ 工具路由（≤50ms，规则+轻语义）+ 并行执行（≤250ms）。

15. 可观测性 / 评估 / 自省（成功率的地基）

① 一句话总纲

可观测先于一切：router→skill→tool 每步结构化 span，可看 p50/p99、可整段 replay；每个 intent/skill 备 golden 用例跑 CI eval + canary/shadow 防回归；Agent 出错后能自省归因并修正策略。

② 要点 + 理由【Q12, Q13, Q27】

  • Tracing / Replay：每一步、每个决策、每次重试都结构化 span（OTel / Langfuse）；看不见就改不动，这是成功率地基。
  • Eval + 回归 harness【Q12】：先定义「成功」（§1 的多指标）→ 每 intent/skill 备 golden 用例 → 改 prompt/换模型/动 tool 都跑 CI eval + canary/shadow 流量。
  • 不稳定诊断【Q13】：分层排查——提示词 / 工具设计 / 模型选择 / 工作流 / 记忆，逐层定位。
  • 自省与策略修正【Q27】：Agent 执行错误后，做错误归因 → 修正后续策略（Reflexion 思路），无需重训基座模型；把「失败模式」写进记忆，下次避开。

③ 追问【Q27】

  • 「怎么让 Agent 不重犯同类错？」→ 错误归因 + 策略修正器 + 把教训写进 episodic 记忆做检索增强，下次同场景注入。

16. 多语言 / 本地化（APAC）

① 一句话总纲

马来/泰/印尼/英：语言检测 → per-language 的 prompt 和 skill → tool description 多语化 → 本地化回复 → locale-aware 合规。

② 要点 + 理由

  • 不是翻译一层皮：每个 market 的合规、披露、催收规范不同，prompt/skill/guardrails 都要按 locale 配。

③ 追问

  • 「多语言对 RAG 的影响？」→ 知识库按语言/市场分库；跨语言检索用多语 embedding 或先翻译再检索。

17. 工程化底座（先点名，被追问能接住）

  • 状态持久化 + 断点续跑：长流程（dispute 调查可能跨天）崩了能恢复。【Q9】
  • 异步 / 事件驱动 + 主动通知：退款到账、争议有结果 → 主动推。
  • LLM 多供应商兜底：单家挂了能切。
  • 成本 / 配额 / 限流。
  • 版本化 + 灰度回滚：prompt / tool / skill / model 全部可版本化、可灰度、可回滚。

18. 实施优先级（被问「先做什么」答这个）

① 一句话总纲

先搭可靠性脊柱（tracing + eval harness + 幂等 + guardrails）再上花哨 agent 能力；已知任务尽量用确定性 skill/workflow 而非放养 agent loop；然后打通「出错也优雅」的 fallback ladder + escalation。

② 顺序

  1. 可靠性脊柱：tracing/replay → eval harness → 幂等/saga → guardrails/合规/鉴权。
  2. 确定性优先：已知任务用 skill/workflow，少用自由 loop（确定性↑=成功率↑=可测↑）。
  3. 优雅失败：fallback ladder + escalation 打通。
  4. 再上花哨：动态 sub-agent、ToT 之类最后上。

③ 金句

「我宁可一个'笨但可测'的确定性 workflow，也不要一个'聪明但不可控'的自由 agent——尤其它在动钱。」

附录 A：面试速答卡（被问就背这几句）

  1. 整体一句话：横切层包住、Router 分发到 5 类执行模式、下挂工具/技能层和（记忆+RAG+容错）底座、账务系统是唯一事实来源。
