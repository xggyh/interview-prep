Tool calling layer

  • get_order_status(order_id) — read-only, no confirm needed
  • initiate_return(order_id, reason) — destructive wrapper: agent must show summary, customer types "confirm"
  • create_ticket(summary, customer_id) — idempotent via idempotency_key = sha256(session_id + summary)
  • Each tool: timeout 3s, 2 retries with exponential backoff, structured error → LLM gets {"error": "OUT_OF_STOCK", "user_msg": "..."}
  • Function schema in JSON, version pinned per agent release

RAG layer

  • Source: ~5K product docs + 2K help articles + 90-day return policies
  • Chunking: 512 tokens / 80 overlap; preserve product SKU as metadata
  • Embed: text-embedding-005 (Vertex), 768 dim; bilingual model (EN + ES)
  • Store: Vector Search w/ ScaNN, + BM25 hybrid via Discovery Engine (lexical for SKU codes)
  • Rerank: Gemini Flash rerank top-30 → top-5 (cheap, +8% recall)
  • Freshness: incremental index every 15 min from Shopify product DB

Serving / infra

  • Vertex Agent Engine as managed runtime (autoscale, no infra)
  • Prompt cache: Gemini explicit cache for system prompt (8K tok) → -50% input cost
  • Router: Flash classifies intent → 80% answered by Flash, 20% routed to Pro
  • Queue: Pub/Sub for async (returns processing, escalation enrichment)
  • Streaming: SSE to widget, p50 first-token 300ms

FDE delivery wraps

  • Customer-readable runbook: on-call escalation, kill switch, rollback to prev agent version
  • Permissions: agent service account scoped to read Shopify, write Zendesk only — no DB write
  • Workforce Identity Federation for support team to access dashboards
  • Weekly customer check-in: deflection / CSAT / top failure modes

Min 40-45 — Q&A drill

"What if Gemini drops a model version mid-quarter — how do you handle it?"
Pin model version in the agent config (gemini-3-flash-001 not gemini-3-flash-latest). Run eval suite on the new version in staging first. Canary 5% → 25% → 100% over a week. Keep last 2 versions hot for instant rollback.
"How would you detect prompt injection in customer messages?"
Model Armor as front gate (managed Google service for prompt injection + PII + jailbreak). Plus a thin LLM-judge that flags "instructions to ignore previous prompt" patterns. Tool layer is the real defense — agents only get scoped function access, not raw SQL.
"Spanish CSAT is 0.4 lower than English — what do you do?"
Three hypotheses: (1) RAG corpus is English-heavy → translate KB to Spanish, re-embed with bilingual model. (2) Tone mismatch → tune system prompt with LATAM-native examples. (3) Eval set was English → build native Spanish golden set. Probably all three — ship in that order.
"Customer wants to add voice channel — what changes?"
Latency budget collapses from 2s to 500ms. Switch to Gemini Live API for streaming ASR+LLM+TTS. RAG retrieval must finish in 200ms (use HNSW + cached top-K). Smaller context window (preserve only last 3 turns). Probably need Gemini Flash exclusively, no Pro routing. New eval dimension: speech recognition accuracy on accent variants.
在 TikTok 我做过 PayLater 跨 7 个市场的多语 voice agent — 同样的 routing pattern (Flash + Pro mix), 同样的 destructive wrapper (refund / 改卡限额). 当时印尼市场 OTP refund 投诉因为 retry idempotency 设计降了 47%. 这套对话 + 工具 + 多市场合规的 wiring 直接可以 port 到 retail 场景, 只是把 KYC / payments 换成 Shopify / returns API.

99% logistics 公司已经有 OR solver. Agent value 是 explanation + edge case + dispatcher dialog, 不是 raw optimization.

Min 40-45 — Q&A drill

"What's the difference between this agent and your existing OR solver?"
OR solver gives an optimal route given a fixed model of constraints. The agent interprets novel constraints (a hurricane warning, a contract clause), explains the OR output to a non-technical dispatcher, and captures dispatcher overrides as labeled data. The OR solver still does the optimization — the agent is the wrapper that makes it useful in messy reality.
"How do you handle a multi-region outage where 50 warehouses go offline at once?"
Circuit breaker on the tool layer — if capacity API returns errors > 10% for 60s, agent enters "degraded mode": no auto-execute, all reroutes go to dispatcher with a "data may be stale" badge. Pub/Sub queue absorbs the spike. We treat the outage itself as a runbook incident, not an agent decision.
"Why Gemini Pro and not a fine-tuned smaller model?"
Reasoning quality on multi-constraint trade-offs (cost vs SLA vs cargo type) is where Pro pays back its cost. We'd consider fine-tune after 6 months of dispatcher override data — then maybe fine-tune Flash on accepted reroutes for 70% of cases and reserve Pro for novel disruptions. Premature fine-tuning kills agility.
"What if the customer asks for full automation, no dispatcher?"
Push back. 99% on-time + zero human = liability. But propose a gradient: full-auto for low-value in-state same-day; review for everything else. Re-evaluate quarterly as agent's accept rate climbs above 90%. Skipping the dispatcher buy-in phase tanks adoption — that's FDE 101.
在 TikTok 我搭的 Internal Agent Platform 跑了类似的 "human-in-loop tool calling" pattern — agents propose, ops 1-click approve, override 都进 weekly training set. 12 周里 acceptance rate 从 62% 涨到 88%. 这套 dispatcher copilot 在 logistics 里完全适用, 只是 tool 从内部 OKR API 换成 SAP + OR Solver.

Min 40-45 — Q&A drill

"What if Google subpoenas data — how is the customer protected?"
Two layers: CMEK means Google can't decrypt without customer's KMS keys; customer can revoke. Plus Access Transparency logs every Google support access. Plus the contractual BAA + Google's customer-controlled subpoena policy (Google notifies customer before any disclosure unless legally prohibited). "How do you stop the LLM from making up a medication dose?"
Three defenses. (1) Structured tool: get_drug_info(drug_name) returns authoritative dose from First Databank — LLM cites it, never generates from memory. (2) Citation-only output: any drug claim without an inline [FDB:drug_id] marker fails LLM judge. (3) Red-team eval set of 200 known dangerous queries; any failure blocks release.
"What if a physician asks a question outside the agent's scope?"
Refusal-correctness eval drives this. Agent has a scope classifier (Flash, fast) — if intent matches "diagnose" or "prescribe", agent responds with information-only framing + "please consult clinical decision support certified by your institution." Refusal accuracy ≥ 99.5% before launch. We never silently expand scope.
"20M records — how do you incrementally index?"
Two indexes. Static index for guidelines/protocols, rebuilt weekly off-hours. Patient EHR is NOT bulk-indexed — we retrieve per-query from FHIR + embed on the fly (tiny corpus per patient, fits in 100ms). This sidesteps the "20M PHI vectors sitting in shared store" problem entirely. Each patient's retrieval is sandboxed.

Tool calling — idempotency is everything

  • Idempotency wrapper: every charge_payment call goes through Spanner write-then-check pattern. If Spanner row exists with status DONE → return existing txn_id. If PENDING → wait & poll. If new → insert PENDING → call processor → update.
  • Atomic insert + processor call: NOT possible (processor isn't transactional). Use compensating transaction — if Spanner inserts but processor call dies, a reconciler job runs every 60s to query processor status by our internal_ref and update Spanner.
  • get_account(account_id), offer_payment_plan(plan_id), flag_hardship(account_id, reason) — all w/ structured schema
  • Destructive wrappers: any settlement > $X requires human approver in HITL queue before tool actually fires
  • Retry policy: read tools 3x; charge tool 0 LLM retries — only reconciler retries

RAG — per-market legal templates

  • Corpus: 200 approved legal templates per market (TCPA-compliant scripts for US, LGPD wording for BR, OJK for ID) + hardship policy docs
  • Hard metadata filter: market = current_market; agent literally cannot retrieve another market's templates
  • Approved phrasing constraint: agent's reply must contain approved phrase boilerplate per market — checked by post-LLM compliance gate
  • Updated quarterly with bank legal team in the loop

Serving / infra

  • Multi-region deploy: us-central1, southamerica-east1, asia-southeast2 — data stays in-market
  • Per-market service accounts: ID agent SA has zero access to US data and vice versa (Workforce Identity Federation)
  • Reconciler service: dedicated Cloud Run job, polls Spanner PENDING rows every 60s, queries processor by internal_ref, updates state. Idempotent by design.
  • Allowed-hours gate: agent refuses to send outbound between TCPA-forbidden hours (8am-9pm local); enforced at outbound dispatch, not just prompt

FDE delivery wraps

  • Bank ops dashboard: market-specific compliance score, settlement queue, recovery rate
  • Cloud Audit Logs: every charge attempt + every settlement offer + every override, 7-year retention per market
  • Customer (bank) gets quarterly compliance attestation report — auto-generated from audit logs
  • Per-market kill switch — bank's compliance officer can shut down 1 market without touching others

Min 40-45 — Q&A drill

"The legacy processor doesn't even return a transaction ID synchronously — how does idempotency work?"
We mint our own internal_ref (UUID + account + amount + day-hash), pass it to the processor in a free-text field if available or via timestamp correlation if not. The reconciler polls the processor's status API by internal_ref every 60s. If the processor literally has no way to dedupe — we accept a small risk window (60s) and use the Spanner PENDING state to refuse a second concurrent call. Worst case: a duplicate is auto-refunded by reconciler within 60s. Document this in the runbook.
"How do you ensure the BR market doesn't accidentally use a US script?"
Three layers: (1) per-market service account — BR agent can only access BR corpus index. (2) Hard metadata filter at retrieval. (3) Post-LLM compliance gate — deterministic regex checks that the output contains the required Portuguese boilerplate and doesn't contain English-only phrases. Any layer failing blocks the send.
"What if a customer says 'I'll sue the bank' — what does the agent do?"
Classifier intent — instant HITL escalation. Agent responds "I understand your concern. I'm connecting you with a specialist who can help" + stops outbound campaign for this account + flags for legal review. Audit logged. Bank rep takes over within 5min SLA. We test this on 50 adversarial transcripts in the eval set.
"How would Indonesia's OJK regulations change the agent vs the US version?"
Different allowed-hours (8am-8pm local, no Sundays). Different mandatory disclosures (must identify as collections in first SMS, must mention complaint channel). Different escalation paths — OJK requires SLA logs filed quarterly. We bake all of this into the per-market config and prompt template; same code path, different declarative config. That's the FDE play — write the engine once, configure per market.

Min 40-45 — Q&A drill

"What if Gemini just isn't as good as OpenAI on one of the 12 apps?"
Exit criteria are explicit — if eval parity fails after 2 prompt iterations + RAG augmentation + (if applicable) Gemini fine-tune, that app stays on OpenAI via the gateway. We don't force migrations that lose customer value. We report it honestly in the steering and the customer makes the call. The gateway makes "keep this one on OpenAI" a 1-line config.
"Why build a gateway instead of just changing the SDK call site by site?"
Three reasons. (1) Centralized shadow/canary lets us migrate with real production data, not just offline eval. (2) Future-proofs against the next model swap (Claude 5, Gemini 4) — config change, not code change. (3) Per-app rollback in 30s vs hours of redeploy. The gateway pays for itself in the first wave's rollback alone.
"6 months is aggressive. What gets dropped if we slip?"
Scope cut order: (1) Defer the 1-2 lowest-traffic apps to phase 2 — keep them on OpenAI through gateway. (2) Defer multimodal-only gains. (3) Defer fine-tune migration; replace with RAG-only for the affected app and accept the accuracy delta if eval passes. We never cut: the gateway, eval rigor, or shadow-mode discipline. Those are load-bearing.
"How do you measure success at the end?"
5 metrics. (1) % of $2M/yr spend migrated. (2) Net annualized savings vs baseline. (3) Per-app eval-parity status. (4) Time-to-rollback measured in a fire drill. (5) Customer team self-sufficiency — they ran the last app migration without FDE help. The 5th one is the FDE-specific success criterion.
