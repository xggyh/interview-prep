A1 ASR ASR 三大架构范式: CTC vs RNN-T(Transducer) vs AED(attention seq2seq), 各自适合什么?
💡 思路 / 考点

这是 ASR 的'地图题', 答出三者的本质区别 + 流式性 + 适用场景就过关。一句话锚点: CTC 帧同步无自回归、RNN-T 帧同步带自回归、AED 标签同步全局注意力。

🗣 中文回答 (口播稿)

三大范式:
CTC —— 帧级输出 + blank token, 输出之间条件独立, 非自回归, 天然流式、快, 但语言建模弱 (每帧独立, 不看已输出的词)。
RNN-T (Transducer) —— encoder + prediction network + joint network, 帧同步但带自回归的 predictor, 既能流式又有语言建模。这是端侧 / 生产流式 ASR 的主力 (Siri / Google 那条线)。
AED (attention encoder-decoder, 即 Whisper 这种 seq2seq) —— 标签同步, decoder 对整段音频做 cross-attention, 精度高、上下文强, 但本质非流式 (要看到足够音频才解码)。
选型: 要低延迟流式、端侧 → RNN-T; 要最高精度、离线转写 → AED; 要简单快、对齐自由 → CTC, 常和 attention 混合 (hybrid CTC/attention)。

🔑 英文一句 (英文面直接说)

"Three paradigms: CTC (frame-sync, non-autoregressive, streams naturally but weak LM), RNN-T (frame-sync + autoregressive predictor — the on-device streaming workhorse), and AED/seq2seq like Whisper (label-sync, highest accuracy, fundamentally non-streaming)."

🔬 中文追问 (2)
追问: hybrid CTC/attention 为什么常用?
训练时 CTC 做对齐正则、attention 做精度, 解码时两者打分融合 (ESPnet 那套), 兼顾收敛稳定和精度。
追问: 端侧为什么偏 RNN-T?
帧同步天然流式 + 低延迟, predictor 提供语言建模, 模型可做小, 是 on-device 实时 ASR 的事实标准。
A2 ASR CTC 具体怎么工作?blank token / 对齐 / 条件独立假设 / 为什么能流式?
💡 思路 / 考点

考你懂不懂 CTC 的机制而不只是名字。关键词: alignment-free、blank、collapse 规则、条件独立、单调对齐。

🗣 中文回答 (口播稿)

CTC 解决的是'音频帧数远多于文字、又没有逐帧标注'的对齐问题。
做法: 模型每个时间帧输出一个分布 (含一个特殊的 blank token), 然后用一个 collapse 规则 —— 先合并连续重复, 再删掉 blank —— 把帧级序列折叠成最终文字。训练时对所有能折叠成正确文本的对齐路径求和 (前向-后向算法)。
两个关键性质: 一, 条件独立假设 —— 给定 encoder 输出, 每帧的预测彼此独立, 所以语言建模弱; 二, 单调对齐 —— 音频和文字顺序一致, 不会乱序。
为什么能流式: 因为是帧同步的, 每来一帧就能出一帧的预测, 配 causal / chunk encoder 就能边听边出, 不像 attention 要看全局。

🔑 英文一句 (英文面直接说)

"CTC outputs a per-frame distribution with a blank token, then collapses repeats+blanks to text, summing over all valid alignments. Conditional independence (weak LM) + monotonic alignment. It streams because it's frame-synchronous — emit as frames arrive with a causal encoder."

🔬 中文追问 (2)
追问: CTC 的弱点怎么补?
条件独立导致语言建模弱, 实践里外接一个 LM 做 shallow fusion / beam search rescoring, 或干脆上 RNN-T。
追问: blank 到底代表什么?
代表'这一帧不输出新符号', 用来处理帧多字少 + 重复字 (如 'hello' 的两个 l 要靠 blank 隔开才不被 collapse 合并)。
A3 ASR Whisper 是什么架构?为什么它本质上是非流式的?要流式怎么硬做?
💡 思路 / 考点

Whisper 是必考锚点。答出 encoder-decoder + 30s log-mel + multitask, 再点破它为什么非流式。

🗣 中文回答 (口播稿)

Whisper 是一个标准的 encoder-decoder transformer (seq2seq / AED), OpenAI 用 68 万小时弱监督多语数据训的, 鲁棒性极好。输入是固定 30 秒窗口的 log-mel spectrogram, decoder 用 special token 做多任务: 转写 / 翻译 / 语言识别 / 时间戳。
为什么本质非流式: 一, 它要把音频 padding/截断到 30 秒整窗再编码, encoder 对整窗做双向 attention; 二, decoder 是自回归地对整段音频做 cross-attention。所以它设计上是'拿到一整段再转写', 不是边听边出。
硬做流式的办法: 把音频切成小 chunk 滚动喂 + 维护一个滑动的上下文, 或者用 VAD 切句逐句转 —— 但这都是 hack, 会牺牲精度或带来重复/边界错误。真要低延迟流式, 应该用 RNN-T 而不是把 Whisper 掰成流式。

🔑 英文一句 (英文面直接说)

"Whisper is an encoder-decoder transformer trained on 680k hrs, fixed 30s log-mel input, multitask via special tokens. It's non-streaming by design — full-window bidirectional encoding + autoregressive cross-attention. Streaming it via chunking/VAD is a hack; for true low latency use RNN-T."

🔬 中文追问 (2)
追问: 那 Whisper 适合你的 voice agent 吗?
离线质检 / 批量转写很好; 但实时催收对话要 sub-2s 流式, 我不会把 Whisper 掰成流式, 会用流式架构, Whisper 留给 offline eval / 数据构造。
追问: Whisper 为什么鲁棒?
68 万小时弱监督 + 多语多场景, 见过大量噪声/口音, 所以 zero-shot 泛化强 —— 代价是大、非流式。
A4 ASR 流式 vs 非流式 ASR 的根本区别和 trade-off?
💡 思路 / 考点

这题是你的主场 (简历明写 streaming upgrades)。锚点: 延迟 vs 精度/上下文, 以及流式怎么用 chunk attention / look-ahead 找平衡。

🗣 中文回答 (口播稿)

根本区别在'能看到多少未来音频'。
非流式看整句, encoder 双向 attention, 精度最高, 但必须等说完才出 —— 延迟高。
流式只能看到当前 + 有限的未来, 用 causal 或 chunked attention、有限 look-ahead window, 边听边出 —— 延迟低, 但因为上下文少、精度略降。
核心 trade-off 就是 latency vs accuracy。实践里的旋钮: chunk size (块越大精度越高、延迟越大)、look-ahead 帧数、causal convolution。streaming Conformer 就是把这些做进去。
在我的 voice agent 里这是核心约束: 电话对话里沉默就是失败, 所以我宁可用流式 + 有限 look-ahead 把首字延迟压下来, 在精度上做可接受的让步, 再靠 LLM 端的纠错和确认步补回来。

🔑 英文一句 (英文面直接说)

"It's about how much future audio you can see. Non-streaming = full bidirectional context, highest accuracy, high latency. Streaming = causal/chunked attention + limited look-ahead, low latency, slight accuracy cost. The knobs are chunk size and look-ahead. In a phone agent, silence kills the call, so I bias to streaming and recover accuracy at the LLM/confirmation layer."

🔬 中文追问 (2)
追问: chunk size 怎么定?
看延迟预算反推: 首字延迟目标减去网络和 TTS 的开销, 剩下给 ASR, 再选最大的能塞进这个预算的 chunk —— 精度尽量高。
追问: 流式精度掉多少?
典型几个点 WER, 但用 look-ahead + 后处理 (LLM 纠错 / 重打分) 能补回大部分, 端到端体验上用户感知不到。
A5 ASR RNN-T 为什么是端侧 / 生产流式 ASR 的主力?
💡 思路 / 考点

承接 A1, 深挖 RNN-T 三件套和它的'既流式又有语言建模'优势。

🗣 中文回答 (口播稿)

RNN-T (RNN Transducer) 有三个组件: encoder (听音频)、prediction network (像个语言模型, 看已输出的文字)、joint network (把两者融合出下一个 token 分布)。
它的妙处: 帧同步所以天然流式 (每帧推进, 输出 blank 或一个 token), 同时 prediction network 提供了 CTC 缺的语言建模 —— 解决了 CTC 条件独立的弱点。
为什么端侧主力: 一, 低延迟流式; 二, 模型可以做得很小 (encoder + 小 predictor), 适合设备内存预算; 三, 没有 attention 对整段的依赖, 计算和内存随时间线性、可控。Siri、Google 的设备端 ASR 基本都是 RNN-T 家族。
这正好接 Apple 端侧的约束: 固定内存 + 实时 + 流式, RNN-T 是为这个场景生的。

🔑 英文一句 (英文面直接说)

"RNN-T has encoder + prediction network (the LM piece CTC lacks) + joint network. Frame-synchronous so it streams naturally, while the predictor gives language modeling. Small, low-latency, linear in time — which is why on-device ASR (Siri, Google) is RNN-T family. It's built for the fixed-memory real-time streaming constraint."

🔬 中文追问 (2)
追问: RNN-T 训练难在哪?
joint network 的输出是 (T×U) 的网格, 显存吃得猛, 要做 memory 优化 (function-merging / pruned RNN-T) 才训得动大词表。
追问: 和 CTC 比延迟?
都帧同步、都能流式, 但 RNN-T 精度更高 (有 LM), 代价是 decode 比 CTC 重一点。
A6 ASR Conformer 是什么?为什么是 ASR encoder 的 SOTA?
💡 思路 / 考点

常见追问。一句话: convolution-augmented transformer, 局部用 conv 全局用 attention。

🗣 中文回答 (口播稿)

Conformer = convolution + transformer 的结合。语音信号既有局部结构 (音素、共振峰, 适合卷积) 又有长程依赖 (韵律、上下文, 适合 attention)。Conformer 在每个 block 里同时放 self-attention (抓全局) 和 convolution module (抓局部), 加上 macaron 式的两个 feed-forward 夹住。
结果是它在 ASR encoder 上全面超过纯 transformer 和纯 CNN, 成了事实 SOTA encoder, RNN-T 和 AED 都常用 Conformer 当 encoder。
流式版本 (streaming Conformer) 把 attention 换成 chunked、conv 换成 causal, 就能边听边出。

🔑 英文一句 (英文面直接说)

"Conformer = convolution-augmented transformer: self-attention for global context + a conv module for local acoustic structure, macaron FFNs around them. It beats pure transformer/CNN and is the de-facto ASR encoder for both RNN-T and AED. Streaming variants use chunked attention + causal conv."

🔬 中文追问 (1)
追问: 为什么 conv 对语音重要?
音素和共振峰是强局部模式, 卷积的局部感受野和位置不变性正好抓这个, 比纯 attention 更高效。
A7 ASR LLM-based ASR (如 Qwen3-ASR / Qwen-Audio 路线) 和传统 CTC/RNN-T 比, 强在哪弱在哪?
💡 思路 / 考点

新趋势题。围绕'audio 接进 LLM'的概念讲清强弱, 模型具体细节标 [✏️ 核实] 别硬编。

🗣 中文回答 (口播稿)

LLM-based ASR 的思路是把音频编码 (audio encoder + adapter) 接进一个大语言模型, 让 LLM 来'读'音频出文字 —— Qwen-Audio / Qwen2-Audio 到 Qwen3-ASR [✏️ 核实 Qwen3-ASR 具体架构] 是这条线。
强在: 一, 语言建模和世界知识强, 长尾词、专名、上下文歧义处理好; 二, 多任务 / 多语统一 (转写 + 翻译 + 问答一个模型); 三, 可以用 prompt 注入上下文 (领域词表、对话历史)。
弱在: 一, latency / streaming —— LLM 自回归 decode 慢, 天然非流式, 实时场景吃力; 二, 幻觉 —— LLM 会'脑补'没说的词, 这在催收/支付这种场景是红线; 三, 大、贵, 端侧难塞。
我的判断: 实时端侧流式还是 RNN-T 这类专用架构; LLM-based ASR 适合离线、高价值、上下文重的转写, 或者作为流式结果的二次纠错重打分层。

🔑 英文一句 (英文面直接说)

"LLM-based ASR feeds an audio encoder into an LLM (Qwen-Audio → Qwen3-ASR line [✏️ verify specifics]). Strong on language modeling, rare words, multilingual unification, prompt-injectable context — but weak on latency/streaming (autoregressive, non-streaming), prone to hallucination (a red line in payments), and large. I'd keep RNN-T for real-time on-device and use LLM-ASR offline or as a rescoring layer."

🔬 中文追问 (2)
追问: 幻觉在 ASR 里具体什么样?
LLM-ASR 会输出音频里根本没说的、但语言上很顺的词 —— 比如把含糊的金额'补'成一个整数。CTC/RNN-T 受限于声学帧不会这样, 所以动钱场景我更信帧级架构。
追问: 能两者结合吗?
能 —— 流式 RNN-T 出初稿压延迟, LLM 做二次纠错/重打分补精度和上下文, 这是我会用的混合。
A8 ASR 多语种 ASR 的难点?(你 7 市场 CN/EN/JP/KR/MY/ID/TH 的真实经验)
💡 思路 / 考点

🟢 你的真实差异化 —— 7 市场、低资源语、code-switching。讲真实坑。

🗣 中文回答 (口播稿)

我在 voice agent 跨 7 个市场 (CN/EN/JP/KR/MY/ID/TH) 踩过的真实难点:
一, code-switching —— 用户一句话里中英夹杂、或本地语夹英文专名, 单语模型直接崩, 要么多语联合训练要么语言无关的建模单元。
二, 低资源语言 —— 泰语、印尼语的标注数据远少于中英, ASR 基线明显低, 我们靠多语迁移 + 本地数据构造 + 领域适配把它拉上来。
三, 建模单元和字符集 —— 中文用字 (CER 而非 WER)、日语有汉字假名混合、泰语没有词边界, 分词和评估口径每个市场都不一样。
四, 数字和实体 —— 支付场景金额/日期/OTP 跨语言格式差异大, 这是错误重灾区, 我专门做了 normalization 和确认步。
这套'多语 + 低资源 + 领域适配'的经验, 正好对 Apple 服务大中华区 + 多市场本地化的需求。

🔑 英文一句 (英文面直接说)

"Across 7 markets I hit: code-switching (mixed CN/EN in one utterance), low-resource languages (TH/ID have far less labeled data — solved via multilingual transfer + local data construction), modeling-unit/charset differences (Chinese uses CER not WER, Thai has no word boundaries), and cross-lingual number/entity formats (the error hotspot in payments). That maps directly to Apple's Greater-China + multi-market localization need."

🔬 中文追问 (2)
追问: 低资源语言怎么提升?
多语联合预训练做迁移 + 针对性数据构造 (TTS 合成 + 真实数据增广) + 领域微调, 别从零训单语。
追问: CER 和 WER 区别?
WER 按词算错误率 (英文), 中文/日文没有天然词边界, 用 CER 按字算更稳定, 评估口径要按语言切换。
A9 ASR ASR 怎么评估?WER / CER / RTF / 延迟, 流式怎么测?
💡 思路 / 考点

评估题, 给全维度 + 区分离线/流式指标。

🗣 中文回答 (口播稿)

离线质量: WER (词错误率, 英文) 或 CER (字错误率, 中文/日文); 进一步看 substitution / insertion / deletion 拆分定位问题。
速度: RTF (real-time factor, 处理时长 / 音频时长, <1 才能实时); 端侧还要看 energy-per-utterance。
流式专属: 首字延迟 (从说话到第一个字出来)、尾字延迟 / endpoint latency (从说完到确定结束)、以及 partial/final 的稳定性 (partial 结果会不会反复跳变)。
生产: 不能只看平均 WER, 要按市场 / 口音 / 噪声分层, 盯长尾; 业务上看下游指标 (理解成功率、转人工率)。
我做流式升级时, 主指标就是首字延迟和 partial 稳定性, 同时守住 WER 不退 —— 这是个多目标。

🔑 英文一句 (英文面直接说)

"Offline: WER (or CER for Chinese/Japanese), broken into sub/ins/del. Speed: RTF<1, plus energy on-device. Streaming-specific: first-token latency, endpoint latency, and partial-result stability. Production: stratify by market/accent/noise, watch the tail, tie to downstream success rate. My streaming work optimized first-token latency + partial stability while holding WER."

🔬 中文追问 (1)
追问: partial 稳定性为什么重要?
流式 ASR 的中间结果如果反复跳变, 下游 LLM 会被噪声触发、用户也会困惑; 稳定的 partial 才能让 agent 提前规划。
A10 ASR endpointing / VAD 在流式 ASR 里的作用?早切 vs 晚切怎么权衡?(接 barge-in)
💡 思路 / 考点

接你的 barge-in / 打断处理经验。讲 VAD + endpoint 的 latency-误切 trade-off。

🗣 中文回答 (口播稿)

VAD (voice activity detection) 判断'有没有人在说话', endpointing 判断'这句说完了没'。在流式语音 agent 里它们决定两件事: 什么时候把识别结果交给 LLM, 以及什么时候允许打断 (barge-in)。
核心 trade-off 是早切 vs 晚切: 切早了 —— 用户还没说完就抢话, 体验差、还可能漏信息; 切晚了 —— 尾延迟高, 对话像卡顿。旋钮是静音判定阈值 (等多少 ms 静音算说完) + 语义/声学的联合判断。
barge-in 这块我专门做过: 用户在 bot 说话时插话, VAD 要立刻检测到语音、打断 TTS 播放、把控制权交回, 还要处理回声 (AEC) 防止把 bot 自己的声音当成用户输入。
我的做法是动态 endpoint: 结合声学静音 + 语义完整度 (这句话意思完整了吗) 来决定切点, 而不是固定静音阈值, 在抢话和尾延迟之间找平衡。

🔑 英文一句 (英文面直接说)

"VAD detects speech, endpointing decides when an utterance is done — together they control when to hand off to the LLM and when to allow barge-in. The trade-off is cut-early (interrupting the user) vs cut-late (tail latency). For barge-in I detect user speech mid-TTS, stop playback, hand control back, and run echo cancellation so the bot's own voice isn't mistaken for input. I use dynamic endpointing — acoustic silence + semantic completeness — instead of a fixed silence threshold."

🔬 中文追问 (2)
追问: 回声为什么是问题?
bot 的 TTS 声音会被麦克风收进去, 不做 AEC (acoustic echo cancellation) 就会把自己说的话当成用户输入, 触发误打断。
追问: 固定阈值不行吗?
固定静音阈值在'用户停顿思考'和'用户说完了'之间分不清 —— 加语义完整度判断能少抢话又不增尾延迟。
T1 TTS 现代 TTS 的 pipeline 演进?从 Tacotron 到 codec/LLM-based 到 flow-matching
💡 思路 / 考点

TTS 地图题。讲清四代演进 + 每代的核心变化。

🗣 中文回答 (口播稿)

大致四代:
一, 拼接 / 参数合成 (concatenative / HMM) —— 老派, 机械。
二, 神经两阶段: 声学模型 (Tacotron2 / FastSpeech 把文字 → mel spectrogram) + vocoder (HiFi-GAN 把 mel → 波形)。这一代质量飞跃, 但要训两段。
三, codec-based / LLM-based TTS (VALL-E 路线): 把音频用 neural codec 编成离散 token, 再用一个自回归 transformer 像语言模型一样预测这些 audio token, 最后 decode 回波形。带来零样本音色克隆 + 天然流式。
四, flow-matching / diffusion TTS (NaturalSpeech / F5-TTS 这类): 用连续表征 + 流匹配/扩散生成, 质量和自然度更高、更稳, 但流式更难。
我评估的那几个引擎 (VoxCPM2 / Qwen3-TTS / OmniVoice / F5) 基本落在第三、四代, 选型就是在质量、流式性、并发、成本之间权衡。

🔑 英文一句 (英文面直接说)

"Four generations: concatenative/parametric → neural two-stage (Tacotron/FastSpeech acoustic model + HiFi-GAN vocoder) → codec/LLM-based (VALL-E: audio codec tokens + autoregressive transformer → zero-shot cloning + streaming) → flow-matching/diffusion (F5/NaturalSpeech: higher quality/stability, harder to stream). The engines I evaluated sit in gen 3-4; selection trades quality vs streaming vs concurrency vs cost."

🔬 中文追问 (1)
追问: 为什么 codec token 能流式?
离散 audio token 是自回归一个个出的, 出几个就能 decode 几个播出去, 和 LLM 出字一样天然增量; diffusion 要迭代去噪整段, 流式难。
T2 TTS Codec-based / LM TTS (VALL-E 路线) 怎么工作?为什么能零样本克隆?
💡 思路 / 考点

深挖第三代。关键: neural audio codec 离散化 + AR transformer + in-context 克隆。

🗣 中文回答 (口播稿)

三步: 一, 用一个 neural audio codec (如 EnCodec / SNAC) 把波形编码成离散 token —— 类似给音频造了个'词表'; 二, 用一个自回归 transformer, 条件是文字 (+ 一段参考音频的 token), 预测目标音频的 token 序列; 三, 用 codec 的 decoder 把 token 解回波形。
为什么能零样本音色克隆: 因为它是 in-context 的 —— 你给一段 3 秒的参考音频 token 当 prompt, 模型就把目标文字'用这个音色'读出来, 不用为每个说话人重训。这跟 LLM 的 few-shot 是一个道理。
代价: 自回归 + 离散 token 有时不稳定 (漏字、重复、跳音), 所以生产里要加重复检测、长度控制、或上 flow-matching 那代换稳定性。

🔑 英文一句 (英文面直接说)

"Three steps: a neural audio codec (EnCodec/SNAC) discretizes waveform into tokens; an autoregressive transformer predicts target tokens conditioned on text + reference-audio tokens; the codec decoder reconstructs waveform. Zero-shot cloning is in-context — a 3s reference as prompt, like LLM few-shot. Cost: AR instability (skips/repeats), mitigated with detection or flow-matching."

🔬 中文追问 (2)
追问: codec 的 token 是怎么来的?
RVQ (residual vector quantization) —— 多层码本逐层量化残差, 又是 codebook/VQ 那套, 和量化是同一个数学。
追问: 不稳定怎么治?
重复/静音检测 + 强制对齐约束 + 长度预测; 或者直接用 flow-matching TTS 换更稳的生成。
T3 TTS Vocoder 是什么?两阶段 vs 端到端 TTS?
💡 思路 / 考点

基础概念题。vocoder = mel→波形, 讲清两阶段和端到端取舍。

🗣 中文回答 (口播稿)

Vocoder 是把中间声学表征 (通常是 mel spectrogram) 转成最终波形的模块, 代表是 HiFi-GAN (GAN-based, 快且高质)。
两阶段 TTS: 声学模型 (文字→mel) + vocoder (mel→波形) 分开训。好处是模块清晰、可单独优化、可换 vocoder; 坏处是两段之间有 mismatch (声学模型训练时见的是真 mel, 推理时 vocoder 吃的是预测 mel), 要联合微调。
端到端 TTS: 文字直接到波形 (如 VITS), 或 codec token 直接 decode。少了 mismatch、延迟更低, 但训练更难、可解释性差。
端侧 / 实时场景我偏好少阶段 + 流式友好的方案, 减少级联延迟。

🔑 英文一句 (英文面直接说)

"A vocoder turns mel-spectrogram into waveform (HiFi-GAN). Two-stage (acoustic model→mel→vocoder) is modular and swappable but has train/inference mel mismatch; end-to-end (VITS / codec-decode) removes mismatch and cuts latency but is harder to train. For real-time on-device I prefer fewer, streaming-friendly stages."

🔬 中文追问 (1)
追问: mismatch 具体什么问题?
vocoder 训练吃真 mel, 推理吃声学模型预测的 mel, 分布不一致 → 杂音/金属感; 解法是用预测 mel 微调 vocoder 或端到端。
T4 TTS 流式 TTS 的关键: time-to-first-audio (TTFA) 怎么压?
💡 思路 / 考点

🟢 你的主场 (简历 streaming + latency)。TTFA 是电话场景的命根子。

🗣 中文回答 (口播稿)

TTFA (time-to-first-audio) —— 从拿到文字到第一段声音播出的延迟, 这是电话对话里用户感知最强的指标, 沉默超过几百毫秒就显得卡。
怎么压:
一, 增量合成 —— 不等整句, 按短语 / 句子片段一来就合成播放, 边生成边播 (和 LLM streaming 配合, LLM 出一句就喂 TTS 一句)。
二, 选 AR token TTS 而非 diffusion —— 自回归 token 天然增量出, diffusion 要迭代整段, TTFA 差。
三, chunk 调度 —— 第一个 chunk 做小一点先出声, 后面追上, 在 TTFA 和音质连续性之间平衡。
四, 模型 / 推理优化 —— 量化、KV-cache、warmup 避免冷启动。
我在 voice agent 里做的 streaming 升级核心就是这个: 把首音延迟压到可接受, 同时处理好 chunk 边界不破音、和打断时立刻停。

🔑 英文一句 (英文面直接说)

"TTFA — time from text to first audio out — is what users feel on a call; a few hundred ms of silence reads as lag. Compress it via: incremental synthesis (synthesize per phrase as the LLM streams), AR-token TTS over diffusion (AR emits incrementally), small first-chunk scheduling, and model/inference optimization (quantization, KV-cache, warmup). My streaming upgrade centered on TTFA plus clean chunk boundaries and instant stop-on-barge-in."

🔬 中文追问 (2)
追问: 第一个 chunk 太小会怎样?
太小可能 prosody 不自然 (一个词一个词蹦), 要在'先出声'和'韵律连续'之间调 chunk 边界, 通常按短语切。
追问: 和 LLM streaming 怎么配?
LLM 出第一个完整短语就立刻送 TTS, 不等整句; pipeline 并行起来, 端到端首音延迟才压得下去。

T9 TTS AR token TTS vs diffusion/flow-matching TTS 的 trade-off?为什么实时/端侧偏 AR?
💡 思路 / 考点

把第三代和第四代对立起来讲取舍, 落到端侧/实时为什么偏 AR。

🗣 中文回答 (口播稿)

AR token TTS (VALL-E 路线): 自回归一个个出 audio token。优点 —— 天然增量流式、TTFA 低、零样本克隆方便; 缺点 —— 可能不稳定 (漏字/重复)、长句误差累积。
Diffusion / flow-matching TTS (F5 / NaturalSpeech 路线): 用连续表征迭代生成。优点 —— 音质和自然度更高、更稳、并行生成整段快; 缺点 —— 要迭代多步、对整段生成, 流式难、TTFA 差。
为什么实时 / 端侧偏 AR: 电话场景 TTFA 是硬约束, AR 能边出边播; diffusion 虽然质量高但要等整段去噪完, 首音延迟吃不消。端侧还要考虑 diffusion 多步迭代的算力/功耗。
所以我的选型在实时催收场景偏 AR 或流式友好的方案, 把质量做到过线而不是用 diffusion 追极致音质。

🔑 英文一句 (英文面直接说)

"AR token TTS streams naturally (low TTFA, easy cloning) but can be unstable (skips/repeats). Diffusion/flow-matching gives higher quality and stability but iterates over the whole segment — bad TTFA, hard to stream, and costly multi-step on device. Real-time/on-device favors AR because TTFA is the hard constraint; I take good-enough quality over diffusion's peak quality."
